====================================================================
★ 设计总纲：一个"做东西"的工具，不是一个"看东西"的玩具 (2026-08-09)
====================================================================
一个引擎有没有实际价值, 只有一个标准:
    用它能不能做出一件"能玩/能用/能发布"的东西。
不能"做东西"的编辑器, 配置再全也只是大号玩具。

"做东西" = 一条完整的创作闭环, 缺一环就产不出东西:
    [布置场景] → [赋予行为] → [试玩验证] → [打包发布]
      ✓ 已有       ✗ 缺失        △ 半有         ✓ 已有
   (编辑器/保存    (脚本/逻辑)   (播放需退出     (Nuitka exe)
     /加载)                    编辑器单独跑)

所以这条排在所有功能之前, 是**最重要的设计要求**:
    ① 引擎必须能驱动行为: 场景里的东西能动、能响应输入。
       行为靠"脚本/组件"挂到物体上(类 MonoBehaviour),
       不能只靠摆静态物体。
    ② 编辑必须能马上试: 编辑器里按"播放"就能跑, 退出干净还原,
       不用退出编辑器单独跑 --run。
    ③ 一切改进都围绕闭环: 每个新功能都问一句
       "它让哪一步创作更顺?" 让"做东西"更快的功能优先,
       只让"看东西"更炫的往后放。

"能做什么东西"的定位 (Python 引擎的现实目标):
    - 可交互的小游戏 / 玩法原型 / 技术演示
    - 可视化与教育工具(把数据/几何变成能转能看的场景)
    - 生成式/参数化创作工具(用 Python 代码批量造场景)
    它们的共同点 = 需要"行为逻辑", 这正是我们和"静态摆件工具"
    的分水岭。

关键优势: 引擎本身就是 Python —— 脚本语言 = Python 自己。
    Unity 要 C# 脚本 + 编译; 我们直接用 Python 当脚本层,
    编辑器即解释器, "改脚本 → 按播放 → 看到效果" 没有编译等待,
    迭代最快。规模不大时, 这个闭环比 Unity 还顺。

一、游戏引擎到底是什么
--------------------------------------------------------------------
游戏引擎 = 一组可复用的"运行时框架 + 编辑工具", 让你不用从零写
渲染、物理、输入、资源管理, 而是专注做游戏内容和逻辑。

现代主流引擎参考: Unity, Unreal, Godot。下文主要讲 Unity 的设计,
因为它和"组件化 + 场景树"的模式最典型, 也最适合中小型项目参考。


二、核心设计理念 (现代引擎的共性)
--------------------------------------------------------------------
1) 组合优于继承 (GameObject + Component)
   场景里每个东西都是 GameObject(物体), 它本身没有行为, 只是一张
   "身份证"。行为来自挂在上面的组件 (Component):
        GameObject "立方体"
        ├── Transform        (位置/旋转/缩放, 每个物体必有)
        ├── MeshFilter       (指向一个网格资产)
        ├── MeshRenderer     (把网格画出来, 用什么材质)
        ├── BoxCollider      (物理碰撞体积)
        ├── Rigidbody        (物理刚体)
        └── MyScript         (用户逻辑脚本)
   "能干嘛"由组件叠加决定, 而不是靠继承树。系统之间解耦。

2) 场景 = 一棵变换树 (Transform 层次)
   场景文件里所有物体组成一棵树, 每个物体的 Transform 存的是
   "局部变换"(相对父物体)。世界变换 = 沿父链一路合成。
   所以拖动父物体, 子物体跟着走, 而子物体自身的位置数字不变。
   选中框、gizmo、保存/加载全部建立在这棵树上。

3) 资产(Asset) 与 场景对象(Scene Object) 分离
        ┌──────────────┬──────────────────────────────────┐
        │              │ 资产 Asset            │ 场景对象 Scene Object │
        ├──────────────┼──────────────────────┼──────────────────────┤
        │ 存在哪       │ 磁盘文件(.fbx/.png/.prefab) │ 场景文件(.unity)里      │
        │ 身份         │ GUID(全局唯一)       │ 场景内 instanceID      │
        │ 复用         │ 被多个场景引用        │ 场景内唯一             │
        └──────────────┴──────────────────────┴──────────────────────┘
   关键机制:
   - GUID 引用: 所有跨文件引用都记 GUID 而非文件名/路径, 所以改
     名/移动文件引用不断。
   - Prefab(预制体): 把场景里一个物体或一棵子树另存为资产。场景里
     放的是它的"实例", 实例只记录"和模板不同的字段"(override 列表)。
     改模板, 所有实例跟着变, 除非某实例覆盖过。
   - 场景文件本身: 逐个对象写所有组件的完整字段(文本格式)。

4) 引擎 / 编辑器 分层, 依赖单向
       核心引擎 (Runtime)     —— 场景对象/变换/渲染/物理/序列化
       编辑器 (Editor)        —— 依赖引擎: 检查器/场景视图/gizmo/撤销
   引擎不 import 编辑器, 编辑器才 import 引擎。这样才能把编辑器剥掉,
   只发布"Player"(游戏本体)。这就是为什么 Unity 发布的游戏没有编辑器。

5) 数据驱动 + 序列化
   一切场景状态都写成可序列化数据(位置/旋转/缩放/颜色/可见性/引用),
   可以保存、加载、版本迁移。游戏内容 = 数据, 代码只负责"解释数据"。

6) Undo/Redo (撤销系统): 编辑器可信度的根基
   Unity 里每一个编辑器修改都经过撤销系统(命令模式/快照), Ctrl+Z/Y。
   没有撤销的编辑器, 误操作一次就可能毁了整个场景。

7) 旋转内部用四元数, 编辑器才显示欧拉角
   内部存储用四元数(无万向锁、插值平滑), Inspector 显示欧拉角只是
   展示层的换算。欧拉角三元组在轨道动画/父子旋转合成时会有万向锁。


三、一个现代引擎通常包含哪些功能模块
--------------------------------------------------------------------
□ 场景管理 (Scene)      —— 场景的新建/加载/保存, 场景内对象树
□ 变换与层次 (Transform)—— 位置/旋转/缩放, 父子层级, 世界/局部换算
□ 渲染 (Rendering)      —— 网格、材质、着色器、相机、光照、后处理
□ 物理 (Physics)        —— 碰撞检测、刚体、关节、射线
□ 输入 (Input)          —— 键盘/鼠标/手柄/触屏, 抽象成"动作"
□ 音频 (Audio)          —— 播放、混音、3D 音效
□ 动画 (Animation)      —— 关键帧、骨骼、状态机、混合
□ 粒子/特效 (Particles) —— 粒子系统、shader 特效
□ UI 系统               —— 画布、控件、布局(编辑器 UI + 游戏内 UI)
□ 资源管理 (Assets)     —— 导入(模型/贴图/音频)、GUID 引用、加载/卸载
□ 序列化/持久化         —— 场景文件、版本迁移、容错加载
□ 编辑器 (Editor)       —— 场景视图、层级面板、检查器(Inspector)、
                           资产浏览器、gizmo(平移/旋转/缩放手柄)、撤销
□ 脚本/逻辑层           —— 用户逻辑挂到物体上, 每帧/事件驱动
□ 构建/打包 (Build)     —— 把项目导出成可发布的 exe/平台包


四、Unity 各核心系统是怎么设计的 (细节)
--------------------------------------------------------------------
[场景视图]
    = 运行时相机 + 叠加编辑辅助层(gizmo/网格/选中框), 不干扰真实渲染。
    你项目里的视口 + gizmo 已经是这个思路。

[检查器 Inspector]
    = 通用属性表单: 反射出选中物体的字段, 自动生成输入控件, 改完写回。
    你项目里的"检查器"面板就是这个, 目前只支持位置/旋转/缩放/颜色。

[层级面板 Hierarchy]
    = 展示场景树的组件列表, 点击选中, 拖拽调整父子关系。
    你项目里有"层级面板", 但目前是扁平列表, 没有父子关系。

[序列化格式]
    Unity 场景是 YAML 文本, 每个对象:
        - 唯一 instanceID(场景内)
        - 所有组件的全部字段
        - 对其他对象/资产的引用(存 GUID)
    Godot 场景是类似缩进文本(.tscn), 也会存每个节点的属性和引用。
    你项目现在的 scene.json(camera + objects) 思路一致, 只是还缺
    GUID、资产引用、版本字段、容错。

[编辑器的撤销实现]
    常用命令模式: 每个操作包装成可逆对象, do()/undo(), 栈式存储。
    简单替代: 每步存整个场景快照(内存贵, 但实现简单)。


五、ECS / DOTS 什么时候才需要
--------------------------------------------------------------------
ECS(实体组件系统)是数据导向的高性能写法: 实体不装组件对象, 而是
分列存数据(Position[] / Rotation[]), 系统用数组循环批处理——为的是
十万级实体的性能(大量同质物体的子弹/鱼群/城市)。
你的场景几百个物体、每帧算几个矩阵, 完全不需要 ECS, 上了反而
把代码复杂化。明确跳过。

七、下一步迭代框架建议 (按依赖排序, 建议顺序 M14→M15→M18→M16)

     - 场景文件加 version 字段 + 迁移逻辑; 加载容错(未知类型降级);

     - 收益: 存档不再轻易损坏, 未来改格式可迁移。

M16  资产/Prefab 与 GUID 引用
     - 每个物体加稳定 id(GUID); 场景里对象引用资产用 GUID。
     - "保存为 Prefab": 选中物体(含子树)导出 .prefab 资产;
       场景放实例, 记录 override(和模板不同的字段)。
     - 目录: assets/ 存资产, scenes/ 存场景。
     - 收益: 可复用模板, 批量改模板全场景生效。

M17  引擎/编辑器分层(为打包铺路)
     - EditorApp 改为"依赖" GLEngine 而非继承; 入口做成 --editor /
       运行场景两种模式。
     - 收益: 打包版可只带运行时, 更小更快。

远期(暂不急): 四元数旋转、材质系统(目前单色)、多选/编组、光照。

九、追赶 Unity：设计理念精要 + 路线图 (2026-08-09 追加)
====================================================================

为什么说"像 Linux 模仿 UNIX"：
   Linux 不是照抄 UNIX 的代码，而是吸收 UNIX 的设计哲学(小而美的
   工具 + 一切皆文件 + 组合), 用自己的实现落地, 才成了更好的系统。
   我们追 Unity 也是同一路数: 不抄 Unity 的功能清单, 而是吸收它的
   设计理念, 在 Loom 里用我们自己的实现把每条理念落地。

--------------------------------------------------------------------
9.1 Unity 的设计理念精髓 (6 条, 弄懂这 6 条就懂了大半)
--------------------------------------------------------------------

【1】组合优于继承 —— Unity 的灵魂
    Unity 里 GameObject 是"最空的容器", 它本身没有行为, 行为全来自
    挂上去的组件:
        加 Rigidbody   -> 物体会掉下来
        加 Light       -> 物体会发光
        加 AudioSource -> 物体会出声
    "一个物体能干嘛" = 它装了哪些组件, 而不是它继承自哪个父类。
    Transform 也只是一个组件(管位置/旋转/缩放 + 父子层次)。
    每个组件只干一件事(Transform 管位置、Renderer 管画、Collider 管
    碰撞体积、Rigidbody 管物理运动), 它们协作, 各自独立。
    → 你现在的 ModelState 是一棵"什么都有的大类", 追赶的第一步就是
      拆成"容器 + 组件", 见 M25。

【2】数据即内容, 代码只解释数据 (一切皆可序列化 + 资产与场景分离)
    Unity 里的所有东西都是"数据":
      - 场景对象(场景里的立方体)存"实例数据": 它的变换、它引用了哪个
        资产、它覆盖了哪些字段。
      - 资产(网格/材质/Prefab/ScriptableObject)存"共享数据", 是磁盘上
        的独立文件, 靠 GUID 被场景引用。一份数据多处用, 内存只有一份。
    Prefab = 可复用模板(场景放的是实例, 只记和模板不同的字段)。
    ScriptableObject = 纯数据容器资产, 让策划不改代码就能调数值。
    → 你现在已有 Prefab 和 scene.json(带 GUID), 缺的是"共享数据资产
      化"(材质从物体身上抽出来, 见 M23)。

【3】所见即所得 + 编辑/播放模式隔离
    Unity 编辑器的核心体验: 你在编辑器里摆的样子 = 游戏跑起来的样子
    (WYSIWYG)。点"播放"时, Unity 会把场景**重新加载一份副本**来跑:
      - 游戏里生成/销毁/改动的对象, 退出播放就还原, 不会弄脏你编的
        场景(保护作者数据)。
      - 只有资产(ScriptableObject/材质/网格)的改动会保留。
    → 你现在有 --editor 和 --run 两种模式, 但还没有"编辑器里按一下
      播放、结束自动还原"的体验, 见 M26。

【4】引擎/编辑器分层, 依赖单向
    核心引擎(Runtime)只做运行时的事: 场景/变换/渲染/物理/序列化。
    编辑器(Editor)依赖引擎: 检查器/场景视图/gizmo/撤销。
    引擎绝不 import 编辑器。这样打包时把编辑器剥掉, 就是纯 Player。
    → 你已有 runtime.py(PlayerApp) + editor.py(EditorApp), 分层已成立,
      继续深化(编辑器专属功能都放 editor 层, 别污染引擎)。

【5】渲染管线可编程: 稳定内核 + 开放定制
    老 Unity 渲染是"黑盒"(C++ 写死, 改不动)。Unity 2018 起改成
    Scriptable Render Pipeline (SRP): 渲染的每一帧怎么组织由 C# 脚本
    决定, GPU 工作仍走原生 API。衍生出 URP(全平台高性能)和 HDRP(顶级
    画质)两套, 正计划用 Render Graph 统一。
    哲学: 底层稳定基础 + 上层深度可定制("build on top, stable base")。
    → 你的 _FRAG_SRC 硬编码在 engine.py 里, 下一步是让材质(shader +
      参数)作为可切换资产, 见 M23。

【6】性能向数据导向演进 (DOTS/ECS) —— 同一理念的另一极
    Unity 自己也承认老组件系统(OOP 实现)有性能问题: 组件散在内存、
    GetComponent 到处找、大对象在缓存里跳动。于是推出 DOTS:
      - ECS: 把数据按"列"存(Position[] / Rotation[]), 同质实体连续
        内存, CPU 缓存命中率高。
      - Job System: 安全的多线程。
      - Burst: LLVM 把 C# 编译成原生码。
    关键: Unity 明确说 OOP 和 DOD **不是二选一, 可以共存**, 且正要把
    ECS 和 GameObject 在引擎层统一(ECS for All, 渐进迁移)。
    → 我们当前几百个物体不需要 ECS, 但"数据是核心、行为只是解释数据"
      这个理念(M25 组件化)正是通向 DOTS 的起点, 理念上同源。

9.3 一句话总结
--------------------------------------------------------------------
Unity 之所以是 Unity, 靠的是"组合胜过继承 + 一切皆数据 + 所见即所得 +
引擎编辑器分层 + 稳定内核开放定制"这套哲学。我们追赶它的方式不是照抄
菜单, 而是每个里程碑都问一句"Unity 在这个问题上靠什么理念解决", 再用
我们自己的代码把理念落地 —— 这就是 Linux 学 UNIX 的做法。

(本节理念来自 Unity 官方文档/官方博客: object-oriented-development 手册、
DOTS/ECS 官方博客与 Unity Learn、SRP/URP/HDRP 设计资料; 2026-08-09 整理。)
