# 如何使用 loom-lint-except（小白版）

本工具检查你的 Python 代码里有没有「**出错了但没人知道**」的地方。

---

## 一、它解决什么问题（30 秒看懂）

假设你写了这段代码：

```python
try:
    data = json.loads(text)
except Exception:
    pass
```

`text` 格式不对时，`json.loads` 会抛异常，被 `except` 抓走，`pass` 什么都不做。

结果就是：**`data` 没被赋值，程序继续跑，但没人知道解析失败了。**

你以为是「没有数据」，实际上是「解析炸了被吞了」。排查这种问题可能花掉半天。

这个工具就干一件事：**扫你的代码，把所有「静默吞错」的 `except` 列出来，告诉你哪一行有问题。**

---

## 二、30 秒上手

### 方式 A：Windows 用户（最简，不需要 Python）

1. 解压 `loom-lint-except-0.1.0.zip`
2. 把 `loom-lint-except.exe` 复制到**你想检查的项目目录**
3. **双击 `loom-lint-except.exe`**

exe 是打包好的独立程序，**不需要安装 Python**。

如果目录里没有 `.py` 文件，它会自动演示自带的 `examples/`。

### 方式 B：有 Python 环境（可看源码，便于二次开发）

```bash
cd loom-lint-except-0.1.0
python try_it.py
```

或 Windows 双击 `try_it.bat`。

---

## 三、检查你自己的项目

### 用 exe（推荐给小白）

1. 把 `loom-lint-except.exe` 复制到你项目的根目录
2. 双击它

它会自动扫描当前目录及所有子目录里的 `.py` 文件。

### 用命令行

```bash
python loom_lint_except.py D:\你的项目\
```

或者进入项目目录后：

```bash
cd D:\你的项目\
python D:\path\to\loom_lint_except.py .
```

## 四、报告怎么看

### 运行后的输出长这样

```
=========================================================================
ERROR (3) - 必须修复
=========================================================================
  D:/my_game/main.py:42  [silent-pass]  exc=Exception
    上下文: fn:load_config
    except 体无任何上报，也无 _ignore_ 标记。

  D:/my_game/net.py:15  [silent-pass]  exc=(TypeError, ValueError)
    上下文: fn:parse_response
    ...
```

### 每条报告告诉你三件事

| 部分 | 含义 |
|---|---|
| `D:/my_game/main.py:42` | **哪个文件的第 42 行** |
| `fn:load_config` | **在哪个函数里**（`fn:` 函数，`class:` 类） |
| `silent-pass` / `no-handling` | **问题类型**（见下方） |

### 三种结果

| 结果 | 含义 | 要做什么 |
|---|---|---|
| **ERROR** | 静默吞错：`except` 里没 `raise`、没 `print`、没写日志、也没 `# _ignore_` 标记 | **必须处理** |
| **WARN** | 有 `_ignore_` 但没写理由，或者 `except Exception` 太宽没声明 | 建议处理 |
| **PASS** | 没问题 | 不用管 |

### ERROR 里的两种类型

- `silent-pass`：`except` 里只有 `pass` 或 `continue`（最典型的静默吞错）
- `no-handling`：`except` 里有代码，但代码没有告诉任何人「出错了」（比如 `x = 0` 这种静默默认值）

修复方式一样，只是报告分类不同。

## 五、怎么修（二选一）

工具给你两条路，**必须显式选一条**。

### 路径 A：确实出错了，应该让某个人知道 → 上报

```python
# 原来（错误示范）
try:
    data = json.loads(text)
except Exception:
    pass

# 修复 1：打印出来
try:
    data = json.loads(text)
except Exception as e:
    print('解析失败: %r' % e)
    data = {}

# 修复 2：抛给调用方处理
try:
    data = json.loads(text)
except Exception as e:
    raise ValueError('配置解析失败: %s' % path) from e

# 修复 3：返回错误字典（让调用方判断）
try:
    data = json.loads(text)
except Exception as e:
    return {'ok': False, 'error': str(e)}
```

工具认识这些上报方式：
- `raise` / `print` / `sys.stderr.write` / `logging.error` / `warnings.warn`
- `traceback.print_exc()` / 写日志文件 / `return {'error': ...}`
- UI 提示（`toast` / `show_error` 等）
- `_report_error(...)`（引擎统一通道）

### 路径 B：这个错误确实无所谓 → 加 `_ignore_` 标记

```python
# 原来（错误示范）
try:
    ctx.viewport = (0, 0, w, h)
except Exception:
    pass

# 修复：加标记 + 写理由
try:
    ctx.viewport = (0, 0, w, h)
except Exception:
    pass  # _ignore_, GL 上下文未就绪时设置视口无效，下一帧会重试
```

**关键：标记后面必须写理由。**

| 写法 | 结果 |
|---|---|
| `# _ignore_, GL 上下文未就绪时设置视口无效` | PASS（有理由）|
| `# _ignore_,` | WARN（有逗号但理由空）|
| `# _ignore_` | WARN（格式不完整）|
| 没有标记 | ERROR |

**为什么必须写理由**：半年后回来看这段代码的人（可能是你自己）需要知道「作者是深思熟虑后决定忽略，还是随手写的 pass」。理由就是给这个判断用的。

## 六、特殊情况：`except Exception` 太宽

如果你确实需要 `except Exception`（比如执行用户回调，什么都可能抛）：

```python
try:
    user_script.update(dt)
except Exception as e:  # _broad_, 用户脚本可能抛任意异常，必须兜住防崩溃
    print('脚本异常: %r' % e)
```

加 `# _broad_, <理由>` 声明「我知道这里宽，是因为它必须是宽的」。

不加这个标记，工具会报 WARN 提醒你考虑细化异常类型。

## 七、完整用法（命令行）

```bash
# 基本用法
python loom_lint_except.py                   # 检查当前目录
python loom_lint_except.py src/ lib/         # 检查指定目录
python loom_lint_except.py --summary         # 只看统计（不列明细）
python loom_lint_except.py --json            # JSON 输出（CI 用）

# 严格模式
python loom_lint_except.py --warn-as-error   # WARN 也当 ERROR（退出码 2）
python loom_lint_except.py --strict-return   # return None 也算未处理
python loom_lint_except.py --no-broad        # 关闭「过宽异常」检查
```

### 退出码（适合写进 CI 脚本）

| 退出码 | 含义 |
|---|---|
| `0` | 全部通过 |
| `1` | 有 ERROR |
| `2` | 有 WARN 且加了 `--warn-as-error` |

## 八、常见问题

### Q1：它会改我的代码吗？

**不会**。纯静态分析，只读不写。

### Q2：会不会误报？

会有一小部分边界情况。如果看到「明明上报了却报 ERROR」，跑：

```bash
python loom_lint_except.py my_file.py --json
```

看具体是哪一行，然后告诉我（贴代码），我加到白名单里。

### Q3：我的项目有几千个文件，跑得慢吗？

单文件解析是毫秒级，几千个文件大约 3-5 秒。慢的话用 `--summary` 只看统计。

### Q4：我想先把所有 `_ignore_` 都加一遍，然后慢慢处理？

可以。工具的意义就是「让你显式声明意图」，加 `_ignore_` 本身就是一种声明——哪怕理由写「暂时忽略，待处理」也比直接 `pass` 好，因为**半年后 `grep _ignore_` 能找出所有待处理的坑**。

### Q5：exe 报「找不到 Windows 版本」或「缺少 DLL」？

exe 是 64 位的，需要 Windows 10 或更高版本。如果你的系统是 32 位，请用 Python 版本（`python loom_lint_except.py`）。

### Q6：exe 双击闪退？

两种可能：
1. **杀毒软件拦截**：把 exe 加白名单
2. **没有 .py 文件**：exe 需要在有 `.py` 文件的目录里双击，否则扫不出东西

如果是第二种，会显示「没找到任何 .py 文件」。

## 九、附录：标记速查表

### 标记格式

```python
# _ignore_, <为什么可以忽略这个错误>
# _broad_, <为什么这里必须用宽异常类型>
```

### 判定表

| 有上报 | 有 `_ignore_` | 有 `_broad_` | 结果 |
|---|---|---|---|
| 是 | — | — | PASS（宽异常需 `_broad_`）|
| 否 | 是（带理由）| — | PASS |
| 否 | 是（无理由）| — | WARN |
| 否 | 否 | — | ERROR |
| — | — | 缺（当使用 `Exception` 时）| WARN |

### 什么算「上报」（工具认识的方式）

| 方式 | 例子 |
|---|---|
| raise | `raise ValueError(...)` |
| print | `print('失败: %r' % e)` |
| stderr | `print(..., file=sys.stderr)` |
| logging | `logging.error(...)` / `logger.warning(...)` |
| warnings | `warnings.warn(...)` |
| traceback | `traceback.print_exc()` |
| 错误字典 | `return {'error': str(e)}` |
| 错误字符串 | `out['status'] = 'err: %r' % e` |
| UI 提示 | `toast(...)` / `show_error(...)` |
| 统一通道 | `_report_error(...)` |

### `return` 的判定

| 写法 | 结果 |
|---|---|
| `return {'error': ...}` | 已处理 |
| `return 某个变量` | 已处理（保守判断）|
| `return None` | 未处理（丢失错误信息）|
| `return`（裸 return）| 未处理 |
| `return 0` / `''` / `False` / `[]` / `{}` | 未处理（静默默认值）|
