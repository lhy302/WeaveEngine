**77 条的分类草案（我的判断，等你裁决）**：

| 类 | 含义 | 条数 | 处置 |

## 1 口径（v1）与已知盲区

### 1.1 口径定义（与 beta6 审计同口径，因此 105 / 38 / 77 三个数字可以直接对账）

- **成员** = 类体内的 `def`（含 `@property` / `@staticmethod` / `@classmethod`）；
- 名字**不以** `_` 开头（`_private` / `__dunder__` 全部排除）；
- **递归收集基类**（GL 侧 8 个 mixin 全算进来），同名按 MRO 最近者为准；
- **普通类属性不计入**；
- 只看**存在性**，不看签名、不看语义。

**为什么沿用这个口径**：登记表与接手须知里写的「GL 105 / VK 38 / GL-only 77」是 beta6 末期审计的口径。
本次独立复算**逐位复现**了这三个数字（`--list` 可复跑），说明口径没漂 —— 于是新门可以拿它当基线，
而不必先花时间对账。**如果换口径，下面所有数字都不可比，必须重新登记。**

### 1.2 已知盲区（**这是本次取证发现的新问题，必须记账**）

1. **属性面没进矩阵**。GL 侧有 4 个公开**属性**（`mouse_locked` / `mouse_lock_allowed` /
   `mouse_unlock_requested` / `render_api_current`），VK 侧有 2 个 `@property` + 1 个属性。
   把属性算进去，数字变成 **GL 109 / VK 39 / GL-only 80**。
   属性也是脚本会读的 API 面（`engine.mouse_locked`），**`IEngineAPI` 必须覆盖它** —— 见 Q-B7-24-2。
   本次门暂不覆盖属性（沿用 v1 口径以便与历史数字对账），**这是有意的跳过，不是漏做**。
2. **签名未比对**。同名方法在两端参数个数/默认值/返回类型可能不同（例：`get_render_api` 两端都返回
   硬编码常量，见 `engine.py:919` / `scene_driver.py:831`）。本门不查签名，签名一致性属契约正文的事。
3. **语义未比对**。存在 ≠ 一致。语义一致由 §6.4 的 P1~P5 门与 B7-22 负责。
4. **`script_keys` 口径疑点（未核）**：VK 侧是 `@property`（`scene_driver.py:1132`），GL 侧同名成员
   在本次口径下**不是方法**（推断为普通属性，故未进 GL 的 105）。其 docstring 自称「GL 侧同名按键快照」。
   **两端到底是不是同一语义，未核**（需读 `loom_input.py` 与 `scene_driver.py` 的赋值点）。

### 2.1 复算

```powershell
$env:LOOM_NO_DIALOG='1'
py -3.13 Loom/tests/test_engine_api_matrix.py          # 门：绿 = 没有新增漂移
```

门不 import 引擎（纯 AST 解析），**无 GPU / 无窗口 / 无 GL 上下文也能跑**，耗时 < 0.2s，已进 `tests/run_all.py` 全量回归。

### 2.2 门的判定逻辑（四种情形，两个方向）

| 情形 | 判定 | 为什么 |
|---|---|---|
| 出现「只有 GL 有」的新方法 | **红** | 新增漂移 —— 这正是 beta6 产生 B13/B14/B15/B7-21 的方式 |
| 基线里有条目已经不再差异（已补齐） | **红** | 逼你从基线删行并写进契约，**防基线腐烂成过期表** |
| 「只有 VK 有」新增 | **红** | 同上（反向漂移） |
| VK 基线条目已不再差异 | **红** | 同上 |
| GL / VK 公开方法总数变化 | **红** | 防「两端同时改名」这种集合差异看不出来的漂移 |

### 2.3 「修前必红」实证（2026-11-17，跑过，不是推断）

用 `Loom/tests/_tmp/_teeth_api_matrix.py`（探针，不复制门文件，直接 import 真门再篡改基线常量）：

| 篡改 | 期望 | 实测 |
|---|---|---|
| 不动（基线正常） | 绿 | `rc=0` `ALL PASS` |
| 从 `EXPECTED_GL_ONLY` 删掉 `render`（模拟新增漂移） | 红 | `rc=1` `FAIL 没有新增「只有 GL 有」的公开方法  新增: render` |

| 从 `EXPECTED_VK_ONLY` 删掉 `step` | 红 | `rc=1` `FAIL 没有新增「只有 VK 有」的公开方法  新增: step` |

**四个方向都有牙**，不是「测试通过只因为它什么都没测」。

## 3 GL 独有 77 条（逐条，含分类草案）

> 「调用分布」= 全仓 `.方法名(` 的出现次数按文件分组（`engine`=Loom/ 下非编辑器非播放器文件，
> `editor`=`editor*.py`，`player_pack`=播放器/打包/运行时，`examples`/`tests`/`tools` 各自）。
> **只作证据，不作判据**：次数多不等于必须进契约，次数 0 也不等于死代码（可能是「只有脚本才会调、而仓库里没有脚本」）。

## 4 VK 独有 10 条（**全部是 B 类：GL 侧已有等价物**）

见上表 §3 之后的「VK 独有（GL 缺）」段。结论：**VK 没有一条「GL 完全没有的能力」**。
10 条全部是「同一件事换了个形态」：

| VK 方法 | GL 侧的对应形态 | 形态差异的根因 |
|---|---|---|
| `step` / `render_pose` | `advance_logic` / `render` | GL 把「逻辑推进」和「渲染一帧」拆成两个入口；VK 的 `step` 是二者合一的兼容入口 |
| `load_from_data` | `load_scene` | GL 从文件路径装配，VK 从已解析 dict 装配 |
| `camera_pos` / `camera_target` / `camera_distance` | `camera_world_position` / `CameraState` 字段 | VK 相机不是场景实体（GL 已「相机物体化」），只能暴露轨道参数 |
| `feed_mouse_rel` / `consume_mouse_input` | `loom_glfw_window._update_mouse_rel`（私有） | GL 由 GLFW 回调直接喂；VK 由播放器/宿主主动喂 |
| `apply_dev_camera_mouse` | `apply_orbit_camera` / `rotate_camera` / `move_camera` | 同「相机不是实体」 |
| `script_keys`（`@property`） | 同名（GL 侧为普通属性，未进 105） | 口径差异，**语义是否相同未核**（§1.2 第 4 条） |

**这条结论很重要**：它说明 beta7 的工作量不在「给 VK 加功能」，而在
**「把两端本来都有的东西，收敛成一套名字 + 一套形态 + 一套语义」**。这与 beta7 定位（纯地基、零功能）完全吻合。

## 5 四类的定义与处置（草案）

| 类 | 判据（可审计） | 处置 | 进 `IEngineAPI`？ |
|---|---|---|---|
| **A** | 语义上是「脚本/内容/工具链会调用的能力」（装配、查找、层级、物理查询、LayerTag、键位、暂停、坐标换算） | VK 必须补齐，并有对拍断言 | **是**（核心） |
| **B** | 两端都能做到，但名字/形态不同 | 统一成一种形态（多数情况：改 VK 侧名字 + 薄适配，或把 GL 侧的形态定为契约形态） | **是**（同一套名字） |
| **C** | 只有某一端才有意义：GL 立即模式绘制、GLFW 窗口回调、GL 帧循环入口、诊断/插桩 | **不进**契约；在契约正文里**显式列出「仅 GL」并给出替代路径**（VK 走 FramePlan / render_pose / step） | **否**，但**必须可见** |
| **D** | `public` 但语义是内部助手（transform 内部换算、批量矩阵、选中态、guid 解析、防环判断） | 建议改名为 `_xxx` 转私有；若不改，则并入 C 并声明「非契约面」 | **否** |

> **纪律依据**（`docs/guides/AI协作工程方法论_合并版_20261117.md` §2.4）：
> C 类必须走「合法域 / 非法域 / 边界带 / 接口缝」的显式声明 —— **允许差异，但不允许差异是隐形的**。
> 静默降级与「恰好没炸」正是 beta6 那一串缺陷的成因。
