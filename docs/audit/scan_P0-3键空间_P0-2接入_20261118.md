## 1 一句话

按审查清单做了 P0-3（统一键空间）+ P0-2（vk_player 接入 `handle_key_event`），
**改完后 3 个测试文件变红**，逐层排查后发现是「`script_keys` 被多处写入方共同拥有」这个
**既有耦合**没被算进来。**已整批回退**，不留在仓库里。本文记录失败点与下次的可行路径。

## 2 目标设计（这个设计本身是对的，问题在迁移路径）

| 名字 | 语义 | 谁写 | 谁读 |
|---|---|---|---|
| `_key` | 动作名 → pygame 键码 | `_init_input_state`（来自 `KEY_BINDINGS`） | 相机/选中逻辑 |
| `key_state` | **键码 → bool** | `handle_key_event`（唯一入口） | `sync_script_keys` |
| `script_keys` | **键名 → bool** | `sync_script_keys`（派生） | `is_key` / `get_action` / 解锁键轮询 |

统一后：VK 不再需要「`script_keys` 是 `key_state` 的只读 property」这个补丁；
`vk_player` 也只调 `handle_key_event`，与编辑器/GL 播放器同一个入口。

## 3 失败点（按发现顺序，全部实测）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | `AttributeError: property 'script_keys' has no setter` | VK 的 `script_keys` 是只读 property，而内核 `sync_script_keys` 要写它 | 删 property → 引出 #2 |
| 2 | 编辑器 WASD 全失效、`test_scripts_collision` 红 | `sync_script_keys` **整表重算**覆盖了 GLFW 事件泵直接写的 `script_keys = _kp`（**多处写者**） | 改成「只增不覆盖」 |
| 3 | 解锁键轮询全部失灵（`test_unlock_key` 7 项红） | `sync_script_keys` **重新绑定** `self.script_keys = 新dict` —— 宿主/测试持有旧引用，写入落到旧字典 | 改成**原地改**（`sk[name] = ...`） |
| 4 | 删 property 时留下**悬空 `@property` 装饰器**，把下一个方法变成了 property | 我的行级切割把 `def` 删了、把 `@property` 留了 | 手工删掉 → 恢复 #5 |
| 5 | 仍红：`test_render_api` / `test_vk_camera_align` 的「Tab 可解锁」`(True, False)` | 测试写 `d.key_state['Tab'] = True`（**键名**）后调 `poll_unlock`；VK `poll_unlock` 里加了 `sync_script_keys()` 仍不翻转 —— **具体链路未查明** | **停手回退** |

第 5 条**未核**：我已确认 `sync_script_keys` 会把 `ks['Tab']` 并入 `script_keys`，
`get_action('解锁鼠标')` 也应读到，但实测仍不翻转。**缺的一步**：在 `_poll_mouse_unlock_key`
里打点，看它到底在哪一行 `return False`（候选：`UNLOCK_ACTION not in actions`、
`mouse_lock_allowed` 为 False、`_unlock_key_prev` 边沿状态被 `sync` 干扰）。

## 4 为什么选择回退而不是继续

- 3 个测试文件红 = 仓库不可交付；继续在红状态下叠改动违反「修前必红 → 修后必绿」纪律；
- 根因已经清楚：**`script_keys` 有多个写者**（GLFW 事件泵、editor 帧头、外部 ctx 路径、测试夹具），
  把它改成「单一派生属性」是一次**输入子系统重构**，不是一次顺手的 P0 补丁；
- 回退后基线 clean（`run_all` 173.5s 全绿），下一个 agent 可以从干净状态重新开始。

## 5 下次的正确做法（建议）

**分两步，每步都能独立变绿：**

### 步 1：只做「`key_state` 键码化」，不动 `script_keys` 的归属

1. `handle_key_event` 写 `key_state[键码]`（已在上次改动里验证可行，独立审查也确认这是对的）；
2. `sync_script_keys` **不改**（保留 GL 现有实现），只在 VK 侧新增一个**独立**的
   `_sync_script_keys_from_state()`，并在 VK `advance_logic` 帧首调用；
3. `script_keys` 在 VK 上**保留 property 别名**（暂时），但改成**双向**：读时先派生再返回。
   → 这一步不触碰 GL 路径，风险最小。

### 步 2：把 `script_keys` 收敛成唯一派生属性

前置条件（必须先做完，否则会重演本次失败）：

- grep 出**所有**写 `script_keys` 的地方并逐个迁移（已知：`loom_glfw_window.py:320`、
  `loom_input.py:271`、`editor.py:2446`、`vk_player` 旧路径、若干测试夹具）；
- 迁移后加一条门：**`script_keys` 只允许被 `sync_script_keys` 写**
  （可用 `__setattr__` 钩子或只读 property + 内部 `_script_keys`）；
- 再把 `vk_player._on_key` 改成 `handle_key_event`。

### 必须补的门（本次失败的教训）

现有门**没有一条**覆盖「宿主写键 → 脚本 `is_key` 读到 → 解锁键翻转」这条链。
建议新增 `test_input_chain_parity.py`：同一串物理键事件 → 两端
`key_state` / `script_keys` / `is_key` / `get_action` / `poll_unlock` **逐项相等**。
