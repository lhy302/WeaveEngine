## 1 段序实测（插桩，同一逻辑帧）

用**实例级插桩**记录两端一个逻辑帧内的段调用顺序（不锁源码字符串）：

```
GL 段序: FixedUpdate -> scripts -> animations -> physics -> physics -> audio -> prep -> dispatch -> interp
VK 段序: audio:MISSING -> prep:MISSING -> dispatch:MISSING
         -> FixedUpdate -> scripts -> animations -> physics -> physics -> interp
```

（{BT}physics{BT} 出现两次是因为 30Hz 逻辑帧下物理子步数 N=2；{BT}:MISSING{BT} 是插桩时发现该属性不存在的标记，
不是真的在帧首被调用。）

| 段 | GL | VK | 后果 |
|---|---|---|---|
| FixedUpdate | ✅ | ✅ | — |
| scripts | ✅ | ✅ | — |
| animations | ✅ | ✅ | — |
| physics ×N | ✅ | ✅ | — |
| **audio** | ✅ {BT}update_audio{BT} | ❌ **不存在** | VK 下 {BT}AudioSource{BT} 的 play/stop **永不发生**；3D 音源位置永不更新 |
| **prep** | ✅ {BT}_logic_prep{BT}（AABB / 光源 VP / 碰撞对） | ❌ **不存在** | VK 无碰撞对来源 |
| **dispatch** | ✅ {BT}_dispatch_collision_events{BT} | ❌ **不存在** | 脚本 {BT}on_collision_start/end/stay{BT}、{BT}on_trigger_enter/exit/stay{BT} 在 VK 下**永不触发** |
| interp 翻页 | ✅ | ✅ | — |

## 2 能力面实测（{BT}hasattr{BT}）

```
hasattr(SceneDriver, "audio")                     -> False
hasattr(SceneDriver, "update_audio")              -> False
hasattr(SceneDriver, "_call_collision_cb")        -> False
hasattr(SceneDriver, "_dispatch_collision_events")-> False
hasattr(SceneDriver, "_logic_prep")               -> False
hasattr(SceneDriver, "collider_bounds")           -> False
hasattr(SceneDriver, "compute_world_matrices")    -> False
```

**这不是「忘了调用」，是「整条链都不存在」**：派发函数不存在 → 回调不可能被调用。
所以「VK 下 {BT}on_collision_*{BT} 永不触发」是**结构性**结论，不需要靠造夹具去撞。

## 3 为什么不能直接「调 GL 那几个方法」

GL 的碰撞事件链是 {BT}PhysicsMixin{BT} 上的方法，但它们各自还依赖一串 SceneDriver 没有的东西：

| GL 依赖 | 在 SceneDriver 里 |
|---|---|
| {BT}_collision_pairs_parallel(){BT}（SAP 粗筛 + C 内核 {BT}loom_collide_pairs{BT} + ancestry 判重） | ❌ |
| {BT}collider_bounds(){BT}（世界空间碰撞体数据） | ❌ |
| {BT}compute_world_matrices(){BT}（批量世界矩阵） | ❌ |
| {BT}_related(){BT}（同树不算碰撞） | ❌ |
| {BT}_call_collision_cb(){BT}（{BT}loom_frame_components.py:114{BT}，12 行） | ❌ |
| {BT}self.audio{BT}（音频后端） | ❌ |
| {BT}_PAIR_GEN_NUMPY_MAX{BT} / {BT}__phys_bridge{BT} 等常量与状态 | ❌ |

而 VK 侧的碰撞查询走的是**另一条路**：{BT}physb{BT}（Culverin/Jolt 桥）—— {BT}get_collisions{BT} / {BT}collider_hit{BT} /
{BT}move_with_collision{BT} 全是 {BT}if physb is None: return [][BT] 的薄包装。

## 4 配对来源：两条路，必须人类选（这是路线，不是实现细节）

| 方案 | 做法 | 好处 | 代价 / 风险 |
|---|---|---|---|
| **A. 用 GL 那一套配对管线**（把 {BT}_collision_pairs_parallel{BT} / {BT}collider_bounds{BT} / {BT}compute_world_matrices{BT} / {BT}_related{BT} / {BT}_call_collision_cb{BT} 抽成共享模块，两端都调） | 与 B7-20 门面收敛同一件事的第一块 | **culverin 缺失时两端行为一致**（GL 这套是纯 Python/numpy/C 内核，不依赖 Jolt）；配对数与顺序与 GL 逐位一致，事件序列可直接对拍 | 等于提前做 B7-20 的一部分；{BT}compute_world_matrices{BT} 在 VK 侧要多算一遍世界矩阵（可复用 VK 已有的 {BT}world_matrices{BT}） |
| **B. 用 VK 的 Jolt 桥取接触对**（{BT}br.post_step(){BT} 暴露 contacts） | 不碰 GL 代码 | 物理权威源是 Jolt，接触更真实 | **culverin 不可用时 VK 完全没有碰撞事件**（GL 仍有）→ 两端行为又分叉；Jolt 接触对与 GL 的 AABB 配对**语义不同**（接触 ≠ AABB 相交），事件序列无法逐条对拍 |

**我的建议：A。** 依据是「两端同一份内容同序进入必须同结果」（I1 不变量），
而 B 会让「有没有 culverin」变成一个**看不见的**行为开关 —— 正是 beta6 那串缺陷的成因。

## 6 留痕（跳过 / 未核）

| 项 | 处置 | 理由 |
|---|---|---|
| **未纳入**：碰撞回调次数对拍 | 门里只做「能力面缺失」+「段序缺口」 | 想造两端**同源**夹具时发现：VK 无 {BT}add_model{BT}，一端只能走 {BT}add_model{BT}、一端走 {BT}load_from_data{BT}；实测该夹具下 GL 也是 0 次 → 说明夹具没造出可触发对（不是引擎问题）。真正的事件序列对拍等方案 A 落地后补（届时两端同源） |
| **未核**：VK 侧 {BT}_logic_prep{BT} 该不该真算「光源 VP / AABB 缓存」 | 未核 | VK 的 VP 在 {BT}vk_renderer._pack_light_vps{BT} 里每帧算（B7-21 刚改过），AABB 缓存是 GL 渲染侧的优化。VK 补 prep 时可能只需要「碰撞对」这一项 —— 需在实现时逐项核对，不能照抄 |
| **未核**：{BT}_disp_gen{BT} 节流在 VK 侧是否需要 | 未核 | GL 用它防「同一逻辑帧同一份 pairs 被渲染侧再派发一次」；VK 渲染侧不派发碰撞事件，可能不需要，但要看补完 prep 后的实际路径 |
