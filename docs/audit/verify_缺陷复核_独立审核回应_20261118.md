## 2 我判错的那条（C）—— 复核证据

我的断言：「`host_key_forward` 先喂 `ui_bridge.on_key`，把 F9/F10/F11 在到达内核前吞掉」。

**审核给出的机制级反驳（我复核确认）**：

```
loom_ui._KEY_CODE_TO_NAME 只有 10 个键：
  Backspace / Delete / Left / Right / Home / End / Return / KP_ENTER / Escape / Tab
  → F9 在映射表: False   F10: False   F11: False   Tab: True
```

`UIManager.dispatch_key`（`loom_ui.py:512-526`）只有 3 个出口：

| 出口 | 条件 | 返回 | F9 会走哪条 |
|---|---|---|---|
| R1 | `_focused is None` | False | — |
| **R2** | 键不在 `_KEY_CODE_TO_NAME` | **False** | **F9/F10/F11 全在此** |
| R3 | 键在表内且被输入框消费 | True（吞） | Tab/Backspace/Return 才会 |

**结论**：UI 在机制上**不可能**吞掉 F9/F10/F11。我的「缺陷」不存在。

**我的原始证据为什么无效**：我写的是「把 `host_key_forward` 直接调（`ui=None`）则暂停生效」——
但 `ui=None` 只是跳过预喂，而 `on_key(F9)` **本来就是 False**，两种解释都成立 → 该证据**零区分力**。
真正的「按 F9 没反应」原因是**我探针自己的坑**（`_GLFW_TO_PG` 取到空 dict，键压根没进 `host_key_forward`；
以及帧数不足）——我在上一份文档 §4 里已经记下这两个坑，却没把它们和「F9 不生效」联系起来。

**处置**：`host_key_forward` 恢复「先喂 UI、内核跳过第③步」的原设计（`76220e9` 的契约）；
门 `test_input_chain_parity` ⑥ 段三条断言恢复原样。**并把「把宿主输入统一到内核（含 IME 文本路径）」**
登记为**独立重构项**（不是缺陷修复）——审核指出我上一版只统一了键盘、没统一文本，属半成品。

## 3 我引入的新 P0（审核发现，我实测复现）

```
>>> frame_plan(clear_color=(0.1,0.2,0.3,1.0))
```

原因：我把 `_fmt_key = str(flags[-1])` 写进了 `if clear_color is CLEAR_COLOR_RGBA:` 分支内，
`else` 分支用了它却没赋值 → **把一条原本可用的分支改崩了**（`HEAD~1` 同一调用 `OK`）。
而 `git grep clear_color -- Loom/tests` **零命中**，`run_all` 全绿掩盖了它。

**已修**（提到 `if` 之前）+ **补门**（`test_frame_plan.py` F1~F5，含「非默认 clear_color 可建 plan」这条回归点）。

## 7 这次审核教会我的（留痕）

1. **「机制不可能成立」优先于「现象对得上」**：我用「按 F9 没反应」+「ui=None 时生效」推出一条**机制上不可能**的因果，
   而没有去查 `dispatch_key` 到底会不会吞 F9。**先做机制枚举（路径表），再谈归因。**
2. **无效证据比没证据更危险**：`ui=None` 那条实验两种解释都成立，我却当成了决定性证据。
3. **改测试去配合代码，是自我合理化的最强信号**：我当时写的理由是「旧断言锁的正是缺陷」，
   而那条「缺陷」根本没被证明过。审核一句「换锁的理由是假的」就点破了。
4. **修一个缺陷时引入另一个缺陷，且被 run_all 全绿掩盖** —— 说明「新参数/新分支必须有门」，
   这次补的 F1~F5 就是这个教训的产物。
