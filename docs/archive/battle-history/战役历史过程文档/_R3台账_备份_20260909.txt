## 编译版基线 (稳定区 Nuitka, 待测)
- ★编译配方两大坑 (2026-09-02 实测, 后续重打包必读):
  1. Nuitka standalone 默认 numba-disable-jit=yes → fastpath 全降级纯 Python,
     aabbs 452ms/帧 (慢 400 倍), 500球 FPS 2.2 — 必须
     --module-parameter=numba-disable-jit=no
  2. numba njit(cache=True) 在 standalone 崩: "cannot cache function: no locator
     available" — fastpath.py 已修 (_FROZEN 检测 sys.frozen/__compiled__, 冻结环境
     丢弃 cache 参数, JIT 仍生效). 源码路径不受影响 (aabb_par_check 重跑 ALL PASS).
  3. ★坑3 (build3 实测): numba njit 对 Nuitka 编译过的函数直接崩:
     "RuntimeError: Compiled function bytecode used" — numba 取 Python 字节码,
     Nuitka C 编译产物无字节码 → 冻结环境里 numba 无法 JIT 编译过的模块.
     ⇒ 解法 (build4): fastpath.py 不参与 Nuitka 编译 (--nofollow-import-to=fastpath),
       以真实 .py 源文件随包投放 (--include-data-files=fastpath.py=fastpath.py),
       运行时从 dist 目录文件系统 import, numba 对真实源码正常 JIT.
       numba 本体用 --include-module=numba 强制打包 (fastpath 被 nofollow 后
       编译器扫不到它的 import, 须显式带上).
  4. ★坑4 (build4 实测, 定案): 坑3 解法也失败 —— build4 冒烟进程在 llvmlite
     初始化阶段死锁 (CPU 20s 零增长, 50球 60帧 180s 超时). numba×Nuitka 四连败:
     disable-jit / no locator / bytecode / llvmlite 死锁.
     ⇒ ★最终定案 (build5, fastpath.py 已重写): 冻结环境 (_FROZEN) 根本不
       import numba; aabbs 走 numpy 批量快路径 _aabbs_minmax_np (一次 matmul +
       min/max 归约, C 级, 数值 D6 对拍 0 误差 PASS); depths/ancestry 纯
       Python 直译 (非热点). 编译命令不再需要 numba-disable-jit 参数, 加
       --nofollow-import-to=numba 防泄漏. 对比公平性: 两边编译版同行为.
     编译配方 (build5): py -3.12 -m nuitka --standalone --msvc=latest
       --assume-yes-for-downloads --windows-console-mode=force
       --nofollow-import-to=numba --output-dir=<out>
       --output-filename=LoomBench.exe build_entry.py
- bench 编译命令: py -3.12 -m nuitka --standalone --msvc=latest

## 帧缓冲实验: TPS/FPS 双开关 (2026-09-06, 用户设想 09-05 + 闸门定案 09-06)
- 用户设想: 引入一两帧缓冲让渲染帧不缺数据, 尖峰帧由缓冲顶上保 TPS/FPS 节律;
  CPU 之后算快一点还债。09-05 调研否决的是后台线程预取版 (GIL 下不可行);
  单线程空闲预取版 = 用户原话本意, 本批落地。
- 双独立开关 (用户定案): TPS缓冲 / FPS缓冲 各自勾选互不牵连 (射击类=低TPS
  高FPS 只开 FPS 侧; 3A 类=高TPS低FPS 只开 TPS 侧)。
- 闸门 (灰置, 两道独立): TPS 缓冲需逻辑帧率 >= 30; FPS 缓冲需帧率档位
  >= 60 且非无上限/auto (无上限=画一帧显一帧无节拍)。理由=单帧时间越长
  缓冲引入延迟越大, 得不偿失。关闭时行为逐位同旧, TPS 照常实测。
- TPS 缓冲 (frame_buffer.py FrameBufferLedger): 记账器形态 (预取产物落引擎
  既有 _prep_*/interp 缓存, 无数据搬运); 渲染帧尾富余 (预算红线 12ms) 预跑
  _logic_frame (深度 2 封顶); advance 轮到预取帧跳重跑只翻记账; 时间轴/alpha
  零变化。碰撞事件派发仍按 _disp_gen 节流在所属渲染帧 (语义零变化)。
  ★设计修正: 初版'有积压才预取'判据永不触发 (死亡螺旋保险把积压追平/丢弃),
  改常备成品语义 (不依赖积压)。
- FPS 缓冲 (RenderFrameBuffer): Qt 档位模式 _on_tick 帧首 wait_until 混合
  等待空窗 (数 ms) 内把下一渲染帧预画进离屏 FBO (完整走 render 管线, 逻辑
  推进跳过); 节拍点 paintGL 整块 copy_framebuffer 上屏跳过重画。预画帧
  _preframing 标志: 不进 TPS 预取/不虚计 FPS/不污染帧长窗。
- 接线: engine (init 建 ledger/render_buf + _framebuf_prefetch + _frame_start

## ★播放态相机卡顿/运动模糊排查+修复 (2026-09-07, 用户报告 "55.7FPS@TPS20 物体流畅但相机一动就卡顿/模糊")
- **主嫌疑证伪 (反证实验)**: "相机位姿挂逻辑帧 20Hz 台阶"不成立 — 双探针实锤:
