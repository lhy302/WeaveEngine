A1 [高] 碰撞对生成 = O(N²) 纯 Python 双循环 + 祖先链遍历
------------------------------------------------------------------------
  位置: Loom/engine.py:2675-2685 (_collision_pairs_parallel 候选对生成)
        + 2328-2330 (_related) + 2157-2164 (is_ancestor)
  问题语句: for a in range(len(cand)): for b in range(a+1, ...): 双循环,

        遍历。Nuitka 编译后仍是"C 执行 Python 对象操作", 与纯 C broadphase
        差距 100 倍以上 (这正是 08-15 记录的"播放期碰撞热点"轮廓)。
  备注: 只有"根-根对"走了快路径 (2679-2681); 任何有父物体参与的对都撞在
        Python 祖先遍历上。
  候选手段:
   ① numpy 化: 全候选对下标用三角索引一次性生成 (np.tril_indices 类), 先拿
      向量化 AABB 宽相过滤 (与 _pair_overlap_vec 同法), 再对幸存的少数对逐对
      查 _related —— 宽相后残余对数极少, Python 祖先遍历次数锐减;
   ② 每帧预计算 parent/depth 数组 (compute_world_matrices 已算 depth), 祖先
      判定 = depth 差 + 沿链跳查, 或直接预计算"同树外对"位掩码 (物体少时);
   ③ 最终解 = B1 物理换库 (Jolt 自带 broadphase), 本堵点可被其吸收。
  验证方法: 与 _collision_events_inline 的逐对结果逐位一致 (行为不改写),
        stress_probe + rigid 探针 FPS 对照。

B1 [最高] 自研物理+碰撞 (M28/M31) → Jolt Physics (Culverin) / PyBullet
------------------------------------------------------------------------
  现状内核: 刚体重力+速度积逐步进; 碰撞体仅 box/sphere; O(N²) 逐对无
        broadphase; 无摩擦/滚动/角速度/连续检测/关节; 碰撞响应=撞停
        (velocity=0)。表现偏差: 物体落地即死、滑墙不平滑、无弹跳手感、
        无碰撞事件回调质量 —— 正是"自研功能低效+表现偏差"的最大标的。
  库选择: 《库性能优化方向指导.txt》物理列 = Culverin (Jolt 桥接, ★物理
        更新释放 GIL → 解锁物理多核) / PyBullet (Bullet, 成熟) / Taichi /
        Warp (GPU/NVidia, 不选)。Jolt 单位置 = Godot 4.3+ 默认物理, 已证
        大厂级; Culverin 需 pip 实测存在性/版本/Nuitka 打包兼容 (单堵点内
        第一步 = 库调研探针)。
  工程范围 (保留语义, 换实现):
    - RigidbodyComponent (mass/gravity/kinematic/velocity) → Jolt body
      (动态/运动学/静态映射); 碰撞体映射 Jolt Box/Sphere 形状。
    - 引擎 API 不动: move_with_collision / get_collisions / collider_hit /
      on_collision_start / on_collision_end / 同树不互撞 / 编辑-播放快照。
    - 提交步进: step(dt) 释放 GIL 全步进 + 回读变换 (矩阵由引擎侧批量)。
    - ★同时修复: Vk 播放器 (SceneDriver) 目前**根本没有物理/碰撞** ——
      step() 只有脚本+动画+VP (Loom/scene_driver.py:107-115), 挂刚体/碰撞
      脚本 (fall/bounce/玩家控制器) 在默认 vulkan 后端下调用
      move_with_collision 会 AttributeError → 脚本标 broken → 游戏不动。
      这是发布铺开前必修的"表现偏差"级功能缺口, B1 一并解决。
    - 推荐后的 A1/A3 被整体吸收 (Jolt 自带 broadphase/连续检测); 碰撞池/
      FramePool 相关代码按剩余用途保留。
  风险: 行为对齐成本 (落地高度差 1e-4 级、碰撞事件时序), 库单体改动最大;
        必须先探针后动代码 (铁律)。GL/Vk 两条播放路径共用同一个
        SceneDriver 层物理 (后端无关) —— 正好符合架构。
  验证: 探针 rigid/落定结果 + 事件语义 + 全量回归; 万一库不可用 → 降级
        A1+A3(①) numpy 化自研 (第二预案, 不进本单)。

三、逐项 C 对照判决 (2026-08-29 用户定: 四类判决框架)
====================================================================

【判决框架 (用户原话精神)】
  Case1 优化到头: 执行逻辑已到极限 且 编译后性能与同功能 C 接近 →
          时间花得多也是必要开销, 不动。
  Case2 算法层优化: 编译后性能与同逻辑 C 差距不大, 但执行逻辑还有优化空间 →
          优化堵点的算法逻辑, 不换库 (卡点是执行逻辑, 不是 Python 执行器)。
  Case3 执行器拖后腿: 编译后明显低于同逻辑 C 且 算法已到头 → Python 执行器
          是元凶 → 换库替换低效 Python 执行。
  Case4 两者都有: 先优化算法逻辑, 再优化执行器效率。
  ★ 堵点不只时间花销多的: 逻辑简单但理论上有优化空间的也是执行堵点, 也要优化。

【口算依据 (量级估算, 每堵点开工前仍须探针实测)】
  C 等价: 简单浮点/指针 ~0.3-1ns/op, 函数调用 ~2-5ns, 每帧千级对象 ~µs 级。
  CPython 3.12: 循环 ~50-100ns/op; 属性链 (m.position.x ≈ 2 属性+索引) ~150-300ns;
    list.append ~50ns; dict 操作 ~50-100ns。
  Nuitka 编译后: 简单静态代码 ~2-5ns/op (近 C), 但**对象属性/装箱/方法分派仍走
    对象协议 (~50-200ns/op)** —— 这就是"编译后仍远差 C"的精确边界。
  numpy: 单次调用开销 ~0.5-2µs; 向量化 ~1-5ns/元素。
  GL 桥 (moderngl): 每次 uniform set / draw ~5-40µs (Python→C 封装)。
  对照基期: 50 球应力主线程 ~9ms/帧 (2026-08-15)。

------------------------------------------------------------------------
■ A1 碰撞对生成 (O(N²) 双循环 + 祖先遍历) —— 判决 Case 4→先算法
------------------------------------------------------------------------
  C 等价: N=51 → ~5µs; N=500 → ~50µs (int 循环+指针).
  现状 (Nuitka 后): 51 全根 ~0.1-0.3ms; 500 含父链 → **~20-150ms** (每对属性
  访问+祖先对象链). 差距: 中等场景 100-3000 倍.
  逻辑空间: **很大** — 全候选下标三角生成+向量化宽相 (numpy) + 祖先/层深
  预计算 O(1) 判定 → 算法后 N=500 ~1-5ms (numpy 375k 对) 且宽相把 O(N²)
  降到 O(N·k); 逻辑已到头才算对手.
  结论: 逻辑没到头 → 算法层优化 (numpy 化+预计算), 做完再评估; 预计收敛到
  "必要开销"级. 没必要先换库.

■ A2 渲染逐物体 draw call / uniform 上传 —— 判决 Case 2 (算法层)
------------------------------------------------------------------------
  C 等价 GL: 51 物体逐 draw ~0.3-0.5ms; N=500 ~3-5ms (纯 C GL 也累, 但小 10x).
  现状: 51 × ~50-90µs ≈ 2.5-4.5ms/帧 (f64→f32 转换+拷贝+uniform+draw 全在
  Python 桥); N=500 → 25-45ms (不可用).
  逻辑空间: **大** — 实例化批绘制 (Vk P4F 已实证 51 draw→2 draw +44%; 同一
  算法 GL 可用 moderngl 实例化) = 算法层优化, 同时把 Python 桥调用次数降
  为常数. 算法后与 C 差距收敛到必要开销级.
  结论: Case 2, 做实例化 (通用算法, 编辑器+GL 播放器共享); 不需要更替执行器.

■ A3 逐子步重算全网格 AABB —— 判决 Case 2 (算法层, 优先于任何库)
------------------------------------------------------------------------
  C 等价: 碰撞体缓存 (局部 8 角点 × 矩阵) ~1µs/步; 子步×对 ~10µs 级.
  现状: 每 (子步×对) 一次整网格 f64 变换 (2100 顶点 ~30-60µs) → rigid 场景
  ~10-60ms/帧 (08-15 修过一版仍是此形状).
  逻辑空间: **主要卡在"调用次数"非执行器** — 当帧全物体 AABB 已由阴影路径
  算过 (_model_aabbs_par, 08-15 共享机制), 子步内只重算**移动者自身** + 逐对
  判定用缓存 (行为逐位一致); 或传统做法: 碰撞体局部 AABB 一次缓存, 每帧
  8 角点变换 (行为比全网格略松 √3 内, 主流引擎如此, 备注可选).
  结论: Case 2, 先算法层 (帧缓存复用). 若 B1 先落地本项被吸收 (Jolt 一步).

■ A4 碰撞事件派发 O(N) 扫描 —— 判决 Case 2
------------------------------------------------------------------------
  C 等价: hash O(1)/事件 ~ns.
  现状: 每事件一条 O(N) Python 生成器扫描 (next(...)) + setdefault; 事件多时
  N×事件 放大.
  逻辑空间: 帧内 id→index 字典一次 (O(N) 建, O(1) 查) + 预分配集合 → 已到头
  级别微改, 与 C 差距收敛到必要开销. 结论: 算法层小改, 无库.

■ A5 compute_world_matrices 属性搬运层 —— 判决 Case 2 (轻)
------------------------------------------------------------------------
  C 等价: 3N 次字段读取 ~ns×N; N=500 ~5µs.
  现状: 3N×~250ns ≈ 40µs (51) / 450µs (500) — 绝对量已小, 大场景放大.
  逻辑空间: 变换数据平面化 (单次 np.fromiter 抽属性) + 深度链 DFS O(n) →
  差距收敛到必要开销级. 结论: Case 2 轻改; 数千物体级再用紧布局, 仍不算
  执行器问题, 不换库.

■ A6 动画采样线性扫帧 —— 判决 Case 2
------------------------------------------------------------------------
  C 等价: 二分+lerp ~200ns/物体.
  现状: 线性 scan+dict+元组推导 ~10-40µs/动画物体/帧.
  逻辑空间: clip 创建时归一化 numpy (times/pos/rot/sc) + np.searchsorted
  插值 + 全物体批量一次 → 单物体 ~2-5µs; 与 C 差距收敛. 结论: Case 2.

■ A7 阴影包围盒角点组装循环 —— 判决 Case 2
------------------------------------------------------------------------
  C 等价: 8N 次写 ~ns×N; 50 模型 ~0.5µs.
  现状: N×8 次 Python 行赋值 ~8-15µs. 逻辑空间: np.tile/广播一次成形 → µs 级.
  结论: 算法层极小改.

■ A9 HUD 文字每帧重建 —— 判决 Case 2 (低优先)
------------------------------------------------------------------------
  现状: 每新文本 pygame.freetype+surfarray+转置+建纹理 ~0.3-1ms (仅裸 pygame
  模式/未覆写 _draw_hud 时生效). 逻辑空间: FPS 取整缓存/内容键缓存 → 命中后
  近零. 结论: 算法层小改, 可选.

■ 子系统判决 (接第二节)
------------------------------------------------------------------------
  B1 物理+碰撞: 算法层剩余空间 (broadphase/连续碰撞/求解器/摩擦滚动) 与库

■ 全网判决结论 (2026-08-29)

七、动态强制型全库筛查 (2026-08-30, 用户新判据: "本可静态却动态")
====================================================================

【新判据 (用户 2026-08-30 写入《库性能优化方向指导.txt》追加内容, 逐点定性用)】
  Nuitka 优化的是"运行 Python 的方式": 能编译成静态语句的, 它能救;
  救不了"Python 动态基因强制本来可以静态执行的代码走动态执行"的地方。
  筛查目标 = 动态强制型: 逻辑在 C/静态环境天然可用固定类型+直接寻址+寄存器
  执行, Python 却必须走对象协议/动态分派 → 用库 (numpy/Cython/Numba/C扩展)
  解决, 这是本轮"最应该做的优化"。
  特征签名 (命中任一即候选):
    S1 逐元素/逐对象 Python for/while 遍历本可 numpy/C 数组化的数据
    S2 每帧逐对象属性链读取 (m.scale[0]/m.color ~150-300ns/个)
    S3 热路径字符串/序列化操作 (json.dumps/hex 解析/f-string 每帧)
    S4 每帧 Python 对象/数组分配-释放循环 (np.zeros+tobytes/GL 建毁/VBO)
    S5 GIL 内纯 Python 数值循环 (物理子步/包围盒组装/深度链) — C 库释放 GIL
