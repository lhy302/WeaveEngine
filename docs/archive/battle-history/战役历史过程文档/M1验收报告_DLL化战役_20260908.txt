四、本棒发现并修复的真实缺陷 (全部在 module_registry.py)
--------------------------------------------------------------------
F1 官方条目 sha256 未比对 (校0 官方分支缺失)
   sha 非空的官方条目被 _sha_gate 直接放行 → 官方坏 DLL 可进进程, 违反
   「官方坏 = AssemblyError 绝不静默降级」。修: 官方 sha 非空即强制比对。
   实证: module_registry_check B3。
F2 sha 前置闸弹出未记账
   条目尚未进在役集合时 _handle_failure 的 _pop 找不到它 → report 漏 'popped'
   动作 (回退链不可审计)。修: _pop 返 bool, 未记账时补记。
   实证: module_registry_check B2。
F3 校6 冲突排序方向反了 (致命误判)
   holders.sort(key=(bool(official), id)) 升序把**非官方**排首位 → holders[1:]
   含官方 → 合法「保官方弃歧义」被误判为「双官方 = AssemblyError」。
   修: key=(not bool(official), id)。实证: module_registry_check D2。
F4 provides_map 悬空/误删
   _install 让后安装者覆盖 map 键, 弹出它时会把仍存活的官方接口一并删掉
   (实测弹出 ambiguous 后 ckernels.aabbs 消失)。修: 新增 _reindex(), 弹出后
   按在役集合重算 map。实证: module_registry_check D2 (provides_map 3 项完整)。

附带发现 (探针侧, 已修):
  · module_fuzz_check.py GBK 崩溃: detail 按字节截断落在多字节 UTF-8 中间 →
    UnicodeEncodeError。修: _safe() 编码兜底 + 子进程 PYTHONIOENCODING=utf-8
    + 按行取尾部。
  · 子进程 stdout 编码不匹配导致中文判定标记丢失 (GBK 输出按 UTF-8 解码)。
  · pipeline_prep_check.py part_b 误对 module_ref 取 loom_aabbs_minmax
    (该符号只属 ckernels) — 子代理自查时已修; 主线程复核确认。

新增靶件说明: ambiguous.c (module_id="ambiguous", provides=["ckernels.aabbs"])
  为验证校6「歧义注入」而建 — 现有 DLL 中唯一 module_id≠provides 前缀的是
  ckernels, 无法构造不同槽位同接口场景。与 badvector 同款「绝不发行」标注。
