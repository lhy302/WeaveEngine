1. 问题定性: 为什么哈希不能当投放判据
================================================================================
审计事实 (本次复测逐字节确认, 与本脚本输出一致):

  文件                                大小      SHA256    差异字节  差异偏移
  pipeline.dll                        20480 B   不同      6         248-250, 14708-14710
  module_ref.dll                      10240 B   不同      6         256-258, 5956-5958
  loom_kernels.dll                    16896 B   不同      6         256-258, 11188-11190
  registry.json / module_loader.py /
  module_registry.py / pipeline_glue.py  --      相同      0         -

  差异全在 PE 头部: COFF 头 TimeDateStamp (偏移 248-258 区) + OptionalHeader
  CheckSum (靠后的 6 字节块)。源侧 20:47:26-34 重编 → 时间戳必然变 → SHA256
  必然不同。这不是缺陷, 是 PE 的固有属性。

  结论: 「投放 SHA256 5/5 一致」是一条**不可复现的声明**, 必须废弃。
        改用「导出符号集合 + 关键字符串 + 大小」作硬判据, SHA256 降为软信息。

2. 设计说明
================================================================================
2.1 PE 导出表解析 (标准库自研, 不引入 pefile)
  路径: DOS header (e_lfanew @0x3C)
        -> NT headers (签名 "PE\0\0")
        -> COFF header (Machine / NumberOfSections / TimeDateStamp /
                        SizeOfOptionalHeader)
        -> OptionalHeader (Magic 0x10B=PE32 / 0x20B=PE32+)
        -> DataDirectory[0] (Export Table: VirtualAddress + Size)
        -> 节表 RVA->文件偏移映射
        -> IMAGE_EXPORT_DIRECTORY (NumberOfNames / AddressOfNames / AddressOfNameOrdinals)
        -> 逐名读 ASCII 字符串 -> 排序去重 -> 导出符号集合

  实现要点
    - DataDirectory 起点按 Magic 分支: PE32 = OptionalHeader+96, PE32+ = +112
    - RVA->偏移用节表 (VirtualAddress, max(VirtualSize,SizeOfRawData), PointerToRawData)
    - 无导出表 (DataDirectory[0] 全 0) 返回空集合, 由调用方判 FAIL, 不抛异常
    - 越界/签名缺失一律抛 PEFormatError, 被采集层捕获成 FAIL 说明, 不崩脚本
    - 同时取出 TimeDateStamp 与导出符号个数, 供报告与快照引用

2.2 校验对象 (7 项, 源侧 vs 编译版逐项对比)
  #  相对路径                                   类型   module_id 字面量
  1  core_components/pipeline/pipeline.dll       DLL    pipeline
  2  core_components/module_ref.dll              DLL    module_ref
  3  ckernels/loom_kernels.dll                   DLL    ckernels
  4  core_components/registry.json               TEXT   -
  5  core_components/module_loader.py            TEXT   -
  6  core_components/module_registry.py          TEXT   -
  7  pipeline_glue.py                            TEXT   -

  默认根
    源侧  : D:\my-project\Loom(py源代码-工作区)\Loom
    编译版: D:\my-project\Loom(编译版)\Loom
  --src / --dst 可覆盖 (负例测试即靠它构造)。

2.3 关键字符串检查
  对 3 个 DLL 在二进制中查找其 module_id 字面量 (来自 registry.json 的
  module_id 字段: pipeline / module_ref / ckernels)。命中位置同时打印, 便于
  人工确认命中的不是巧合字节。未命中 → FAIL, 并提示「可能被编译器优化/改名,
  需人工确认」。该判据防的是「导出符号对但装错模块/符号被改名」这类功能性错配。

2.4 输出与退出码
  逐项输出: 存在性 / 大小 / 导出符号 / 关键字符串 / SHA256(软) / PE 时间戳(软)
            / 字节差异(软) / 判定
  末尾输出四列汇总表 (存在性 / 大小 / SHA256 / 导出符号) + 计数行:
      === 汇总: N 项 PASS / M 项 FAIL ===
  退出码: 0 = 全 PASS, 1 = 存在 FAIL (编译版缺失同样计 FAIL)。
  编译版缺失时额外打印:  SKIP: 编译版不存在 <绝对路径>
  编码: 交互式控制台沿用本机编码 (中文 Windows = cp936), 重定向/管道时强制
        UTF-8, 便于审计日志采集不出现乱码。

3. 判据表
================================================================================
3.1 硬/软判据总表
  项目类型 | 存在性 | 大小 | 导出符号集合 | module_id 字符串 | SHA256
  ---------|--------|------|--------------|------------------|--------
  DLL      | 硬     | 硬   | 硬           | 硬               | 软(INFO)
  TEXT     | 硬     | 硬   | -            | -                | 硬

  硬判据任一不满足 -> 该项 FAIL (退出码 1)。
  软判据仅作 INFO 打印, 永不导致 FAIL。

3.2 DLL 判定规则
  条件                                          结果
  源侧/编译版任一不存在                          FAIL
  大小不一致                                     FAIL
  PE 解析失败 / 源侧无导出表                     FAIL
  导出符号集合不一致 (打印仅源侧/仅编译版差集)   FAIL
  module_id 字面量任一未命中                     FAIL
  SHA256 不一致                                   INFO 「PE 时间戳差异（预期）」
  以上硬判据全满足                               PASS

3.3 文本文件判定规则
  条件                                          结果
  源侧/编译版任一不存在                          FAIL
  大小不一致                                     FAIL
  SHA256 不一致 (文本应逐字节相同)               FAIL
  全一致                                         PASS

3.4 软信息 (仅打印, 不影响判定)
  - SHA256 两侧值
  - PE TimeDateStamp (UTC) 两侧值
  - 字节差异总数 + 偏移示例 (直接复现审计的「各差 6 字节」)

6. 「SHA256 快照」vs「硬判据」用法说明
================================================================================
  两个东西用途不同, 不要混用:

  硬判据 (大小 + 导出符号集合 + module_id 字符串; 文本另加 SHA256)
      用途: 判定「投放副本与源侧是否功能等价」——即发布门禁 (gate)。
      特性: 对 PE 时间戳/校验和这类元数据差异免疫, 可复现。
      用法: 直接看退出码。0 = 可发布; 1 = 禁止发布, 必须查明细。

  SHA256 快照 (--snapshot 产出的 release_snapshot_<YYYYMMDD>.json)
      用途: 事后追溯与文档引用 —— 回答「当时投的到底是哪一版」。
      特性: 记录两侧 path/size/sha256/exports/mtime 的**时刻值**, 是历史证据,
            不是判据。
      用法:
        - 文档写「投放时刻快照见 release_snapshot_20260908.json」;
        - 事后排查「这份副本来自哪次组装」时, 比对 mtime + sha256;
        - 想复现某次投放, 用快照里的 sha256 去源侧/构建产物里找同一文件。
      注意:
        - DLL 的 sha256 在快照里两侧通常不同 (PE 时间戳), 这**不是异常**,
          快照同时给出 sha256_equal 字段并已在 _doc 里写明预期;
        - 不要用快照的 sha256 反向作为「投放一致性」的判据, 那正是 R-5/P9
          指出的错误做法;
        - 文本文件的 sha256 两侧相同, 快照里可直接当「未漂移」的证据。

  一句话: 硬判据管「能不能发」, 快照管「发的是哪一版」。
