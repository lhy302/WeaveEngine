〇、问题模型定量化: 双峰从哪来 (先算账, 再开药)
--------------------------------------------------------------------
0.1 现状机制链 (engine.py / core_clock.py 实读):
  - 渲染帧入口: engine.render(delta_time) (:4645) 先 clk.advance(dt)
    (:4682-4683, 排 0~N 逻辑帧) 再渲染段; dt 实测于 run() 主循环
    (:4939-4941, time.time() 差值)。
  - advance 把 dt 计入 accumulator, 攒够 fixed_dt(30Hz=33.3ms) 跑逻辑
    帧, alpha=acc/fdt (core_clock.py:103-128)。
  - 渲染位姿 = prev/curr 快照 lerp (interp_state.py:106-156)。

0.2 双峰的量化 (模拟 600 渲染帧, 逻辑帧墙钟 28ms / 纯渲染 6ms):
  - 落点帧 (该帧内跑了 1 个逻辑帧): 墙钟 = 28+6 = 34ms, 占比 ~99%
    (因为 34ms > 33.3ms = fixed_dt, 几乎每帧都攒够 1 步 → 实测
    TPS=29.9 贴着 30 上限跑, 渲染帧率被钉在 1/34ms≈29FPS)。
  - 若逻辑帧 15ms (轻场景): 帧序 = 21ms(落点) 与 6ms(快帧) 交替,
    alpha 序列 0→0.29→0.57→0.86→落点, 双峰比 3.5:1。
  - 结论: 双峰幅度 = 逻辑帧墙钟 ÷ 渲染帧墙钟。28ms 逻辑 + 6ms 渲染
    时, 无上限模式退化成"逻辑成本每帧都发生" → 渲染帧率 ≈ TPS,
    无上限的意义 (渲染远快于逻辑) 只在逻辑帧明显更便宜时存在。
  - 机制本质: 单线程下, 逻辑帧成本必然整块落在某个渲染帧内。
    accumulator 只决定"哪一帧落", 不改变"落在帧内就拖长该帧"。

0.3 附带发现: "无上限"在 Qt 路径不是真无上限
  - guiloader.py:48 FPS_LIMITS['unlimited']=1 → ui/loom_gui.py:1149-1150
    QTimer 周期 1ms (PreciseTimer, :459-461)。Windows 上 QTimer 1ms
    实际到达时刻抖动很大 (系统定时器粒度 + 事件循环阻塞), 与用户
    实测"渲染帧率 10-150FPS 飘"吻合。pygame 路径 editor.py:1885/1896
    tick(0) 才是真无上限; 播放器 engine.py:4945 硬编码 tick(120)。
  - 含义: 治双峰之前, Qt 路径先有一个更便宜的病: 限帧器本身不准。
    Panda3D 的 wait_until 混合等待 (见§一) 是对症参考。

一、Panda3D 时钟模型考据 (问题 B, 源码行号)
--------------------------------------------------------------------
1.1 先纠偏: Panda3D 没有叫 "smooth clock" 的类。前报告§二所称
  "平滑时钟"实为两件东西: ① ClockObject 的限频/整形模式 (wait_until
  睡眠机制); ② direct/src/deadrec/SmoothMover (网络远端角色的运动
  平滑器 — 它才是"前瞻"的老师, 见§二)。渲染帧怎么定步长, 答案在
  ClockObject::tick 的 8 种模式 + TaskManager 的任务排序。

1.2 ClockObject (panda/src/putil/clockObject.cxx, 652 行):
  - 8 种模式 (clockObject.h:61-70; set_mode 注释 :94-131):
      M_normal        纯实时, dt=墙钟差 (:363-367)
      M_non_real_time 忽略墙钟, 每帧恒 +1/user_frame_rate (:369-374)
      M_limited       跑不快于目标率: wait_until(old+1/rate) (:376-383)
      M_integer       ★帧率整形: 实际帧率被约束到 user_frame_rate 的
                      整数倍或整数约数 (:386-403)。快于目标 →
                      target_dt=target/floor(target/dt) (如目标 60、
                      实测 144 → floor(2.4)=2 → 拉到 120FPS); 慢于
                      目标 → target×ceil(dt/target) (拉到下一个约数,
                      如 20→拉到 30 的 1/2=15? 实为 30×1=30 档)。
      M_integer_limited 快于目标就用目标本身, 慢于目标才取约数 (:406-424)
      M_forced        无论快慢都按恒定 1/rate 报时 (:426-433)
      M_degrade       按 degrade_factor 均匀降速 (:435-452)
      M_slave         外部喂时间 (:454)
  - wait_until (:491-534) — 混合等待, 全文最可移植的 40 行:
      wait_interval = (want-now) - sleep_precision;  先 Thread::sleep
      睡掉大段, 再忙等 (while get_real_time()<want) 补尾段;
      sleep_precision 默认 0.01s (config_putil.cxx:130-135, 可配);
      过睡有 debug 日志 ("Overslept by N us ... consider raising
      sleep-precision")。= "睡眠省 CPU + 忙等保精度"的标准配方。
  - 帧率统计三件 (:280-337): get_average_frame_rate (滑窗
    _ticks, 平均帧率区间默认 1.0s)、get_max_frame_duration (窗内
    最长帧)、calc_frame_rate_deviation (帧长标准差 = "chugginess"
    直接量化 — 正是 Loom 双峰该上的指标)。
  - get_dt 受 max_dt 封顶 (clockObject.I:109-116; Loom 的
    maximum_logic_delta 同款, Unity maximumDeltaTime 亦同款)。
  - tick() 在帧首打点, get_frame_time() 报"本帧开始时刻" — 动画
    全帧统一时间戳 (clockObject.I:30-41 注释: all animation for a
    given frame remains in sync)。Loom 的 alpha 语义与其
    get_frame_time 一致 (帧内常量时间轴)。

1.3 TaskManager 帧节奏 (direct/src/task/Task.py + ShowBase.py):
  - TaskManager.step (Task.py:561-592): mgr.poll() 跑完本帧全部任务
    → doYield(startFrameTime, nextTaskTime) 挂点 (:847-848, 默认
    no-op, 注释掉的示例 :850-859 就是"睡到下一帧"实现)。
    = Panda3D 把"帧尾空闲怎么睡"开放为可覆写挂点。
  - 渲染是 sort=50 的普通任务 igLoop (ShowBase.py:2363, :2254-2291),
    与逻辑任务同链排序执行; 帧同步靠时钟模式, 不靠插值
    (Panda3D 全引擎没有 render-state interpolation — 它选择
    "时钟整形"而非"状态插值"路线, 与 Unity/MC 相反)。
  - ShowBase.py:603-612 client-sleep / multi-sleep 配置: 渲染后
    附加睡眠 (多客户端同机让 CPU); :2267-2268 igLoop 渲染后
    time.sleep(0) 让出时间片。
  - averageFrameRate 用途实证: Task.py:820-829 _getRandomTask 用
    1/avgFrameRate 估算下一帧到期时刻 (任务剖析采样用), 非调度用。

1.4 对 Loom 可移植的三件 (按价值排序):
  a. wait_until 混合等待语义 → Loom 自制限帧器: sleep(剩余-4ms)

  c. M_integer 档位语义 → 可选设置 "帧率档位约束" (渲染上限自动

二、渲染前瞻 (lookahead) 与各家调度对照 (问题 4 / ③ / C)
--------------------------------------------------------------------
2.1 Panda3D SmoothMover — 真正的"前瞻"参考 (direct/src/deadrec/):
  - 定位: 网络远端角色平滑 (sampled motion over time), 三模式
    (smoothMover.h:33-40): off / 仅平滑 / 全预测 (prediction)。
  - 核心机制 (smoothMover.cxx): 渲染时间先回退固定 delay (:243-245,
    timestamp -= _delay, 默认 0.2s :53), 在两个历史采样点之间线性
    插值 (:427); 数据不够新时才允许前瞻 — 用前两个点连线外推到
    现在 (:318-336 "extending into the future"), 且封顶
    _max_position_age 防外推跑飞 (:332-335)。
  - 语义 = "插值永远领先于数据到达"的反向操作: 先落后 (delay),
    再用速度外推补齐 → 观感零延迟, 且渲染时间轴对采样到达时刻
    不敏感 (网络抖动被 delay 吸收)。速度由相邻采样差分计算
    (compute_velocity :648+)。
  - 对 Loom 的映射: 这就是"渲染帧前瞻一帧"的成熟形态 — 渲染时刻
    对准 curr + alpha×fdt 的"未来位置" (外推), 而不是 curr 之前
    (插值)。差别只在数据来源: SmoothMover 外推靠差分速度, Loom
    快照天然有 prev/curr, 外推 = lerp 系数取 alpha' = 1 + acc/fdt。
    (即把 render_pose 的 a 从 [0,1) 放宽到 [1,2), 方向相反。)

2.2 其余引擎调度对照 (补前报告§二遗漏的时钟细节):
  - ursina (ursina/main.py:163, :179-183): 薄封装 Panda3D, 无独立
    时钟模型 — time.dt = globalClock.getDt() 直取, 逻辑=渲染同帧。
    window.fps_counter 只是显示 (:175-183), vsync 唯一限速

  - arcade (application.py:45, :86-91, :140-150): 逻辑 on_update 用

    补跑 (前报告已判不适用于物理, 结论不变)。vsync 特判
    (:88-90: darwin/linux 强关 vsync 防 1/30 锁死)。
  - pyglet (clock.py + app/base.py): 主循环 idle() (:206-235) =
    派发到期回调 + get_sleep_time 返回下次到期, 事件循环据此
    sleep; interval=0 时 schedule(_redraw_windows) 无限速渲染
    (:143-146)。interval 回调的相位整形: _get_soft_next_ts

  - kivy (clock.py): 唯一做帧睡眠精修的 Python 引擎 — ClockBase
    Behavior.idle (:679-697): maxfps>0 时循环 usleep 直到
    _check_ready (:725-727, 剩余 < min_sleep 的 4/5 就忙等收尾);
    MIN_SLEEP=5ms / SLEEP_UNDERSHOOT=4ms (:605-609) — 与 Panda3D
    wait_until 同构 (欠睡 4ms 后忙等), 是 Python 侧"睡眠+忙等"
    的现成参数样本。tick_draw (:782) 分离事件/绘制计数, 无固定步长。
  - wasabi2d (loop.py:531-561): asyncio 协作式, 每循环固定派发
    update+draw 两事件 (draw 带 updated 脏标志), dt=await next_tick()

  - cocos/moderngl-window: 复用 pyglet/wg 时钟, 无固定步长 (前

2.3 渲染前瞻/预测在各引擎的存在形式 (问题 4 答案):
  - 做状态外推 (前瞻) 的: Panda3D SmoothMover PM_on (网络域,
    §2.1); Unity Rigidbody.interpolation=Extrapolate (官方文档:
    按最新速度外推, 抖但零延迟 — 官方明确标注 trade-off);
    FPS 网络游戏客户端预测 (源客户端本地即时+服务端校正, 属
    输入预测不属时钟)。
  - 做"渲染帧前瞻一帧流水线" (预渲染下一帧) 的: 主机/PC 引擎
    的 frame pipeline / Vulkan swapchain FIFO+ Mailbox 本质是
    GPU 侧 1-2 帧前瞻; CPU 侧如前报告 P-C 提到 "渲染前段与上一
    渲染帧 GPU 绘制重叠"。**没有发现任何引擎在 CPU 逻辑层做
    "提前把下一逻辑帧算好放缓冲供渲染插值"** — 原因见§四: 
    单线程墙钟里提前算=移动成本不消除; 多线程下=游戏状态
    单写者纪律被打破。这是行业缺席而非疏漏。
  - MC (Minecraft) 对照: TPS=20 tick 与 FPS 解耦, 渲染用
    partialTicks 在上一 tick 与当前 tick 间插值 — 与 Loom 现状
    同构 (无前瞻, 接受插值落后 fdt×(1-alpha)), 前瞻不做。

三、追加问题: TPS 档位 × 经典 FPS 档位倍数绑定, 144Hz 怎么办
--------------------------------------------------------------------
3.1 ①accumulator+alpha 是否天然解决非整数倍 — **是, 定论**:
  - accumulator 对 (TPS, FPS) 完全无约束: 渲染帧落点在逻辑时间轴
    上均匀随机 (30TPS@144FPS = 每逻辑帧 4.8 渲染帧, 帧序 4/5 帧交
    替), 但每帧 alpha = acc/fdt 连续递增, 插值输出位置在时间轴上
    连续采样 — 观感是平滑直线, 无需整数倍关系。
  - 数学: 任意渲染时刻 t 的渲染位置 = pos(prev) + (pos(curr)-
    pos(prev))×(t - t_prev_logic)/fdt, t 连续 → 位置连续。整数倍
    只是让落点模式变成确定性的整齐重复 (每逻辑帧恰好 K 渲染帧),
    消除的是"落点节律不齐", 不是"不平滑" — 而 alpha 插值本身已
    把节律不齐变成不可见的采样密度差。
  - 真正的例外只有一个: 逻辑帧成本整块落在落点帧 (0.2 的双峰),
    与倍数无关, 解法在§五。
  - 2D 像素游戏 (Celeste/Dead Cells 类) 会刻意要求整数倍以保像素
    落位整齐 — Loom 是 3D 连续渲染, 无此需求。

3.2 ②有没有引擎做帧率档位约束 (只允许倍数档) — 有, Panda3D:
  - ClockObject::M_integer / M_integer_limited 模式 (§1.2) 就是
    官方档位约束: 实际帧率被 wait_until 整形到 user_frame_rate
    的整数倍/约数 (clockObject.cxx:386-424)。实现代价 = 每帧
    睡眠, 且快帧被拖慢到下一档 (144→120)。
  - 其余引擎: 未见等价物。pyglet 的 _get_soft_next_ts 是"错峰"
    不是"倍数约束"; Unity targetFrameRate/-vSync 只限上限不做
    倍数整形; 主机引擎靠 vsync 隐式绑定 (60Hz 屏 = 渲染 60/30),
    但逻辑帧仍用 accumulator 不要求整数倍。
  - 结论: 档位约束是"可选锦上添花" (Panda3D 提供但极少有人用),
    不是必需设计。Loom 若做, 代价极低 (在限帧器上加一步取整),
    建议做成设置项而非默认。

3.3 ③Panda3D/ursina/arcade 实际做法小结 (一句话版):
  - Panda3D: 默认 M_normal 纯实时不约束; 需要整齐节律时用户显式
    开 M_integer (时钟整形); 逻辑=渲染同帧跑 (任务链排序), 无
    TPS/FPS 分离概念, "平滑"交给时钟模式而非插值。
  - ursina: 无任何处理 — 直接吃 Panda3D 默认 (实时, vsync)。
  - arcade: pyglet schedule_interval 独立调度逻辑回调, 与渲染
    帧率解耦但不补步 — 相位由调度器软整形 (错峰), 属"宽松
    定步长", 无 alpha 插值层。

四、渲染前瞻在 Loom 的可行性判断 (问题 C, 结论: 主线程前瞻无益,
后台线程前瞻不可行/不划算)
--------------------------------------------------------------------
4.1 先澄清"前瞻"在 Loom 语境的两个不同含义:
  a. 插值外推 (extrapolation): 渲染时刻取 curr 之后 (alpha'>1),
     用 prev/curr 差分速度外推 — 零架构改动 (见§五方案C), 不需要
     提前算逻辑帧。
  b. 提前计算 (pre-computation): 在渲染帧 N 期间就把逻辑帧 N+1
     算好放缓冲, 渲染帧 N+1 直接消费 — "逻辑结果双缓冲预取"。
     问题 C 指的是这个。判断如下。

4.2 单线程前瞻 (渲染帧开头先跑下一逻辑帧) — 无益, 排除:
  - 单线程下总墙钟不变: 逻辑 28ms 该算还是要算, 提前算只是把
    成本从"落点帧"搬到"落点帧前一帧" — 双峰平移不消除。
  - 唯一收益: 渲染帧 N+1 的 advance() 不再跑逻辑 → 该帧变轻
    (6ms)。但逻辑成本只是每 4-5 帧发生一次换每帧发生一次的
    均摊, 总 FPS 反而更平稳 — 等价于把落点帧拆细? 不 — 28ms
    是原子块 (一次 advance 内部 while 循环), 拆不开除非改逻辑
    帧内部分段 (帧内流水线, 批6 已在做 P-A 物理线程化)。

4.3 后台线程前瞻 (逻辑线程领先渲染线程一帧) — GIL 下不可行:
  - Loom 逻辑帧 28ms 的构成 (前报告§三实测: physics 23ms 其中
    pre_step 15.71ms 纯 Python + Jolt C 层 0.31ms 释放 GIL +
    脚本/动画/音频纯 Python): **纯 Python 段占大头, GIL 下与
    渲染线程串行**。逻辑线程跑 Python 时渲染线程拿不到 GIL →
    渲染帧率被逻辑墙钟拖住, 与主线程直跑无差。
  - 能释放 GIL 的只有 Jolt step (0.31ms) 和 numpy 大内核 —
    预取线程的可用并行窗口 <2ms/28ms, 收益上限 7%, 换来的:
    ①游戏状态双写者 (逻辑线程写 models, 渲染线程读) → 现有
    "主线程单写者+同步点"纪律 (前报告 5.1 用户定调) 全线作废;
    ②快照/桶/GL 状态跨线程同步成本; ③脚本语义破约 (用户脚本
    update(dt) 契约同步执行, 前报告 5.4 明确不引入异步语义)。
  - 对照行业: 无引擎这么做 (§2.3), 原因相同 — 状态一致性成本
    > 平滑收益。前瞻问题的正解是 4.2a 的外推 + 帧内流水线
    (批6 在做), 不是后台逻辑线程。

4.4 结论: 渲染前瞻作为"提前算逻辑帧"在 Python/GIL 现实下
  判定不可行 (收益<7% 且破坏架构纪律); 作为"渲染时刻外推"
  可行且极便宜 (§五方案C)。重场景根治 = 缩逻辑帧墙钟本身
  (批6 流水线 P-A 物理线程化: pre_step 15.71ms 若随 Jolt
  线程化可重叠, 28ms → 目标 ≤20ms), 属另一条已立项战线。

--------------------------------------------------------------------
五、无上限模式双峰缓解方案清单 (问题 A, 按落地成本排序)
--------------------------------------------------------------------
按成本从低到高, 前 3 项为推荐 (§六), 后 4 项记录不推荐理由。

  ① 限帧器校准 (最低成本, Qt 路径必做)
    改: ui/loom_gui.py _render_timer 的 QTimer 1ms → 自校准混合
    等待 (Panda3D wait_until 语义: QThread.msleep(剩余-4ms) +
    忙等收尾; 参数抄 kivy MIN_SLEEP=5ms/UNDERSHOOT=4ms)。
   pygame 路径 tick(0) 本身已可, 可选换 SDL_Delay 校准版。
    收益: Qt 渲染帧率从 "QTimer 抖动 10-150" 收敛到稳定节律,
    消除限帧器自生的那一半抖动。风险: 低 (改一行定时器驱动,
    逃生门=旧 QTimer 路径保留)。

  ② 帧长方差观测 (零风险, 诊断面)
    改: engine._update_fps 旁加滑窗帧长 std + max (Panda3D
    calc_frame_rate_deviation 同款, 平均区间 1s), HUD/日志输出。
    收益: 双峰从体感变数字, 后续每项优化的验收基线。风险: 零。

  ③ 外推渲染模式 (extrapolate, 小成本, 可选开关)
    改: interp_state.render_pose 支持模式枚举 ('interpolate'/
    'extrapolate'); 外推时 a' = 1.0 + acc/fdt (渲染时刻在 curr
    逻辑帧之后), 旋转外推沿用 angdiff 同式; 需按 prev→curr
    速度差分 (平面已含两帧, 零新增数据)。默认关闭 (设置键
    'interp_mode'), 与 Unity Rigidbody.interpolation 枚举对齐。
    收益: 渲染显示提前量从 [-fdt,0] 变 [0,+fdt], 输入→画面
    延迟降低约半帧; 双峰幅度不变 (方案治平滑不治成本)。
    风险: 外推过冲 (物体急停/反弹时画面超前现实) — SmoothMover
    用 _max_position_age 封顶 (§2.1), Loom 用 alpha'≤1.5 封顶
    + 碰撞事件帧自动回退插值 (物理落点帧不准外推)。

  ④ 双峰"摊平" (逻辑帧内部分段交错) — 不推荐现在做
    思路: 28ms 逻辑帧拆成 K 段分摊到 K 个渲染帧 (Unity 没这么
    做; 行业无先例, 破坏"逻辑帧=原子同步点"语义, 脚本/物理
    一致性全破)。正解 = 批6 帧内流水线缩短 28ms 本身。

  ⑤ 后台逻辑线程预取 — 不可行 (§四判定, GIL)。

  ⑥ 渲染帧率硬上限档位约束 (M_integer 式整形) — 可选不做
    见§3.2: 锦上添花, 快帧被拖慢, 与"无上限"诉求相逆。
    如用户在意"节律整齐"可作为设置项 (§六方案B 附带)。

  ⑦ vsync 依赖 — 记录: 显示器 vsync 开启时双峰被自然平滑
    (落点帧变 2-3 个 vsync 周期), 但 Loom 现状 swapInterval=0
    (qt-view-host-pitfalls 记忆), 不依赖此路。

--------------------------------------------------------------------
六、推荐落地 (问题 D, 按 ROI 排序)
--------------------------------------------------------------------
【方案一 (ROI 最高, 建议先做): 限帧器校准 + 帧长方差观测】
  改动文件:
    - ui/loom_gui.py: _render_timer 驱动改自校准混合等待
      (新增 _wait_until(target, busy_tail_ms=4) 帮助函数,
      QTimer 仅作唤醒源, 实际睡醒在循环内校准; 或改用
      QTimer.stop + 精确循环 — 二选一, 前者 diff 最小);
    - engine.py: _update_fps 增 _frame_dt 滑窗 (deque 120) →
      std/max 暴露 HUD 第三行;
    - guiloader.py: FPS_LIMITS['unlimited'] 语义注释更新
      (1ms 周期仅作下限, 实际节律由校准器保证)。
  预期收益: Qt 无上限态渲染帧间隔从双尾长尾 (QTimer 1ms 抖动
    + 逻辑落点 34ms 叠加) 收敛为单峰主源 (仅逻辑落点); 帧长
    std 可量化下降 ≥40% (QTimer 分量归零)。
  风险: 低。QTimer 路径保留为逃生门 (设置键 'precise_limit':
    false); pygame 路径不动 (tick 内部已是 SDL 校准)。
  成本: ~1 天含验收。

【方案二 (小成本, 第二批): 外推渲染模式 'extrapolate'】
  改动文件:
    - interp_state.py: render_pose 加 mode 参数 (模块级常量
      INTERP_LERP=0/EXTRAP=1), 外推 a'=1+alpha 且 a'≤1.5 封顶;
      angdiff 外推同式; static_frame 判定不变 (prev==curr 时
      外推=恒等, 零开销);
    - engine.py: 设置键透传 ('interp_mode'), advance 后按模式
      调 render_pose; 物理落点帧 (steps>0) 帧自动回退 'interpolate'
      (防碰撞时刻画面超前);
    - scene_driver.py: 同参透传 (vk 路径)。
  预期收益: 渲染画面时间轴从"落后半帧"变"领先半帧内", 输入
    延迟体感改善; 逻辑落点帧的 34ms 长帧不再叠加"画面滞后"
    感 (外推把滞后预算花在刀刃上)。
  风险: 中低。外推过冲仅出现在急变速物体 (落体弹跳顶点);
    默认关闭 + 落点帧回退, 可 A/B。对照: Unity Extrapolate
    官方标注 "good for... but can be visibly incorrect" —
    同款 trade-off, 交给用户开关。
  成本: ~0.5-1 天。

【方案三 (中期, 与批6 合流): 缩逻辑帧墙钟 = 治本】
  双峰的根 = 28ms 原子逻辑块。方案一/二只治"观感"不治"成本"。
  批6 P-A (物理线程化, pre_step 15.71ms Python 段随 Jolt 线程
  重叠) 已立项, 是唯一能把 34ms 落点帧压到 ~20ms 的路; P-B
  (动画/事件重叠) 再收 3-5ms。落地后无上限态: 落点帧 20+6=
  26ms vs 快帧 6ms, 双峰比从 5.7:1 → 4.3:1; 若再配逻辑帧内
  预算分帧 (max_steps=1 已是), 渲染帧率地板从 29 → 33FPS。
  本调研不展开 (归批6), 仅声明依赖关系: 方案一先行无冲突。

【明确不做】后台逻辑线程预取 (§四 GIL 判定) / 逻辑帧内部分
  段摊平 (破坏原子同步点语义) / M_integer 默认化 (与无上限
  诉求相逆, 可选设置不做默认)。
