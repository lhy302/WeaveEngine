〇、方向定调 (用户原话精神, 恢复会话必读)
--------------------------------------------------------------------
现代引擎逻辑帧与渲染帧分离 (MC 的 TPS/FPS; TPS 20-30 游戏机制即正常,
渲染帧无上限)。Loom 现状 = 两者绑死: 渲染帧跑多快逻辑就跑多快 (无上限
模式每渲染帧全量跑一遍逻辑), CPU 单核跑断腿 (500球逻辑 ~28ms vs 渲染
~10ms), GPU 25-50% idle 等待 —— 这是全部历史观测 (单核吃满/GPU 25%/
架构地板 100-130FPS) 的真正根因。

用户拍板:
1. 逻辑帧固定频率, 默认 30Hz, 引擎里开发者可自行调整;
2. 渲染帧位置 = 两个已算好的逻辑帧快照间按 alpha 线性插值 (帧间运动
   视为线性);
3. 帧内流水线 (第二阶段): 逻辑帧内各系统由主线程发同步指令, 其他线程
   互不依赖、等主线程同步信息再算, 负载分摊到所有核心。

一、Unity 官方设计 (老师答案, 命名对齐用)
--------------------------------------------------------------------
Player Loop 执行顺序 (每渲染帧):
  输入采集 → [循环] FixedUpdate ×N (Time.maximumDeltaTime 内) → Update
  (每渲染帧一次) → 动画 → LateUpdate (相机跟随) → 渲染 → yield

关键机制:
- FixedUpdate: 固定步长 (Time.fixedDeltaTime 默认 0.02s=50Hz), accumulator
  驱动, 每渲染帧可跑 0~N 次; 物理引擎 (PhysX) 只在 FixedUpdate 里步进。
- Time.maximumDeltaTime: 逻辑追不上 (卡顿帧) 时单帧逻辑时间上限, 超出
  部分直接丢弃 —— 防死亡螺旋 (逻辑超时→更多逻辑帧→更超时)。
- Time.maximumFixedTimestep (2018.3+): 每渲染帧最多跑的 FixedUpdate 次数
  上限 (默认 0.1s / fixedDeltaTime), 同为死亡螺旋保险。
- Time.deltaTime (Update 用, 可变) vs Time.fixedDeltaTime (FixedUpdate 用,
  恒定) —— 两套 dt 明确分离。
- Rigidbody.interpolation = None / Interpolate / Extrapolate: 物理体在
  物理步之间的渲染插值 —— 渲染帧显示 prev/curr 两个物理步的插值位置,
  或按速度外推。**这就是 Loom 快照插值的直接老师**。
- Time.timeScale: 暂停/慢放 = 逻辑时钟缩放, 渲染循环照跑 (UI/相机仍活)。
- 相机跟随放 LateUpdate (保证在所有逻辑+动画之后), 跟随目标用插值后的
  物理位置 (否则相机抖动)。
- Application.targetFrameRate / vSync 只影响渲染频率, 与逻辑步频无关。

对齐建议: Loom API 命名照抄 Unity 习惯 — fixed_dt / logic_fps (场景
设置) / interp 模式枚举 ('none','interpolate','extrapolate') /
maximum_logic_delta (死亡螺旋保险) / time_scale (暂停/慢放)。

【Panda3D — 任务链模型 (帧内流水线的最佳参考)】
  direct/src/task/Task.py:244 setupTaskChain(chainName, numThreads,
  frameBudget, frameSync, ...):
  - 每条任务链可分配独立线程 (numThreads), 链间并行; 同链内按 sort
    值排序执行;
  - frameBudget = 该链每帧时间预算 (秒), -1 无限制;
  - frameSync=True = 链跑完等时钟进入下一帧才继续 (同步点语义!),
    False = 跑完立即从头再跑 (异步追赶)。
  - TaskManager.step (Task.py:561) = 驱动一帧, mgr.poll() 执行所有任务。
  启示: Loom 帧内流水线 = "系统任务链 + frameSync 同步点 + frameBudget"
  三件套的直接映射。Panda3D 自己的渲染 (C++) 与逻辑分离也靠链排序
  (early/late/last 三档 sort), 不是每帧插值——它选择了平滑时钟
  (smooth clock) 而非状态插值。

【Ursina networking/club_bear.py — 完整 accumulator+插值参考实现 (Python!)】
  samples/networking/club_bear.py:

      while tick_timer >= tick_rate: tick(tick_rate); tick_timer -= tick_rate
  - :94-95 prev_state/new_state 双快照; :117-118 渲染帧 lerp 插值:

【arcade — 双调度分离 (简化版参考)】
  arcade/application.py:45 update_rate=1/60 默认; :140-150 set_update_rate
  用 pyglet.clock.schedule_interval 把 on_update (逻辑) 独立调度;

【cocos/pyglet/moderngl(-window) — 无固定步长】: pyglet app.base:115

  (不含 ursina 示例) 普遍没做这件事 = 对 Loom 是差异化能力。

四、推荐架构: 分离 + 插值 (第一阶段, 本阶段落地)

4.1 核心时钟 (新文件 core_clock.py, 独立可测):

  class FixedStepClock:
      logic_fps        = 30.0          # 开发者可调 (设置.json 'logic_fps')
      maximum_logic_delta = 0.25       # 死亡螺旋保险 (Unity maximumDeltaTime 对齐)
      time_scale       = 1.0           # 暂停=0 / 慢放=0.5 (Unity timeScale 对齐)
      alpha            = 0.0           # 渲染帧插值系数 [0,1)
      # 对齐 Unity 命名: fixed_dt = 1/logic_fps

      def advance(self, render_dt):    # 每渲染帧调
          dt = min(render_dt, self.maximum_logic_delta) * self.time_scale
          self._acc += dt
          steps = 0
          while self._acc >= self.fixed_dt and steps < self.max_steps_per_frame:
              self._on_logic_step(self.fixed_dt)      # 逻辑帧回调
              self._acc -= self.fixed_dt
              steps += 1
          if steps == self.max_steps_per_frame and self._acc >= self.fixed_dt:
              self._acc = 0.0        # 丢弃积压 (死亡螺旋保险, Unity maximumFixedTimestep 精神)
          self.alpha = self._acc / self.fixed_dt
          return steps

4.2 状态双快照 (新文件 interp_state.py):
  - 每逻辑帧开始时把 curr 快照滚成 prev, 逻辑帧结束后再抓 curr:
      _snap_prev = _snap_curr; _snap_curr = _grab()
  - _grab() = numpy 平面 (N,3)×3 (position/rotation/scale), 模式照抄
    _transform_snapshot (id 钉住三件对象防 id 复用, R6);
  - 渲染帧插值 (全 numpy 向量化, 500 物体 <0.5ms):
      pos_r = pos_prev + (pos_curr - pos_prev) * alpha        # lerp
      rot_r = rot_prev + angdiff(rot_curr, rot_prev) * alpha  # 小角度欧拉
      scl_r = 同 pos
      欧拉小角度差: d = rot_curr - rot_prev; d = (d + π) mod 2π - π (防跨±π跳变)
  - 应用方式: **不回写 GameObject** (只读平面直接喂 compute_world_matrices
    的 SoA 入口) —— 写回会二次污染逻辑状态并破 _fw_cache 失效协议;
  - 无逻辑帧的物体 (静止) 插值=原值, 零开销;
  - 暂停/场景加载/toggle_play 边界: curr=prev 强制对齐, alpha 恒 0;
  - 新增物体: prev 缺行 → 用 curr 行填充 (首帧不插值)。

  逻辑帧 (每逻辑步一次, dt=fixed_dt 恒定):

五、帧内流水线 (第二阶段, 逻辑帧内多核分摊)
--------------------------------------------------------------------
5.1 模型 (对齐 Panda3D 任务链 Task.py:244 三件套):
  逻辑帧 = 一串"系统段", 段间是同步点 (frameSync=True 语义):
      [段A 输入/脚本] →sync→ [段B 物理] →sync→ [段C 动画+事件] →sync→ 快照
  每段可声明: 跑主线程 / 派线程池 / 与相邻段重叠 (流水线)。
  段间数据传递只走"主线程发指令+共享只读平面" (用户定调:
  主线程发同步指令, 其他线程互不依赖等同步信息)。

5.2 GIL 现实约束 (组3/组6 教训, 不可回避):
  - 能真并行的: Jolt step (C 层释放 GIL, physics_bridge.py:932)、
    numba njit nogil 内核 (fastpath.py)、numpy 大数组运算 (BLAS);
  - 不能真并行的: 纯 Python 脚本 update (GIL 串行)、Python 层逐体
    循环 (pre_step/post_step)。
  ⇒ 流水线收益来自**重叠**而非加速单段: 前段 C 层物理 step 释放 GIL
  期间, 后段纯 Python 工作 (动画采样/事件预处理) 已在跑 —— 墙钟缩短。
  spin 空烧教训 (组6): 小工作量高频调用严禁 prange, 流水线只用
  常驻线程/既有池, 不开新线程池。

5.3 落地形态 (渐进三步):
  P-A 物理线程化 (收益最大, 风险最小):
    Jolt step (释放 GIL 的 0.31ms C 段 + pre/post Python 段) 移入
    常驻物理线程, 逻辑帧主线程: post 指令 → 不等 → 跑脚本/动画 →
    等待+回读 (同步点)。501 体场景 physics 23ms 里的可并行部分
    (pre_step 15.71ms 若随 Jolt 线程化可重叠) 显著缩墙钟。
    ★R1 红线: 睡眠/唤醒语义一行不动, 只是搬线程; 桥内部状态访问
    全部经队列指令 (生产者-消费者), 无锁共享。
  P-B 脚本/动画与物理重叠:
    脚本 (改位形指令) 与物理 step 现有先后依赖按 Unity 语义保持
    (脚本改 velocity 本逻辑帧生效), 但动画采样 (只读 clip, 写
    position) 与物理无依赖可重叠; 事件派发 (现 _parallel_shadow_
    and_collision 已做池上并行) 并入同框架。
  P-C 渲染前段并入流水线 (编辑器态收益):
    shadow_prep/buckets 与上一渲染帧的 GPU 绘制重叠 (帧流水线,
    前瞻一帧), 需双缓冲桶实例数据 (B1 staging 已 grow-only, 扩
    双份即可)。风险高 (GL 状态跨帧), 最后做或不做。

5.4 不做清单: 逐物体线程 (GIL 下纯开销) / 新通用线程池 (parallel.py
  既有池复用) / 破坏段间顺序的投机执行 / 给脚本 API 引入异步语义
  (用户脚本契约 = 同步 update(dt) 不变)。

七、风险清单 (每坑必答)
--------------------------------------------------------------------
1. 物理穿透: 30Hz 单步 33ms 步长 Jolt 会穿透/弹跳失真 → 物理独立
   accumulator 固定 60Hz (Unity 默认 50Hz 精神), FixedStepClock 支持
   双 accumulator (逻辑 30Hz 内部跑 2 步物理 60Hz); 逻辑帧其它系统
   仍 30Hz。配置: 'logic_fps': 30, 'physics_fps': 60 (都开放可调)。
2. 脚本转速减半: 已核实不成立 (scripts.py 全 dt 驱动); 用户自定义
   脚本若按帧计数才受影响 → 使用指南加一节"逻辑帧分离说明"
   (update(dt) 语义: dt 恒定 = fixed_dt, 调用频率 = logic_fps)。
3. 相机抖动: 本地相机不插值 (渲染帧实时); 物理体跟随的第三人称
   相机 → engine.interp_position 读插值位姿 (4.5)。
4. 暂停/加载/toggle_play 边界: curr=prev 强制对齐, alpha=0;
   gc_play_enter/exit 包裹边界已有, 快照滚动手动对齐插在 toggle_play
   进/出 (editor.py:1611/1695)。
5. 死亡螺旋: maximum_logic_delta 0.25s 上限 + max_steps_per_frame
   保险 + 积压丢弃 (4.1), Unity maximumDeltaTime 同款。
6. GC 批兼容: 快照/时钟长寿命对象 grow-only (R8), 进 freeze 冻结;
   LOOM_GC_PROBE 对账探针复跑确认 GC 事件仍 0。
7. 逐位一致 (R3): 插值只发生在"喂渲染矩阵"处, 逻辑状态 (物理/
   脚本) 数值路径零改动 → 现有对拍网 (aabb/sap/spin_gate/bridge_)
   全部照跑即绿; 新增插值对拍 (分批2)。
8. Vk/GL 双端漂移: 插值层在 scene_driver/engine 各自实现 → 抽
   interp_state.py 单实现两端调用 (同 fastpath 模式), 拒绝双份。
9. 回放/联机未来: 固定步长逻辑帧 = 确定性基础 (ursina :429 注释
   "Networked games require a fixed timestep"), 本方案天然向前兼容。
10. 逃生门总纲: LOOM_NO_SPLIT=1 或 'logic_fps'<=0 = 完整回退旧
   绑死模式 (A/B 基线用, 验收必测一次回退后行为逐位=旧)。
