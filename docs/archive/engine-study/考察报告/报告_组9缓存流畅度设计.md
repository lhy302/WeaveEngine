## 三、GC 方案（接入点 + 参数 + 生态风险 + 探针设计）

### 3.1 现状
全项目 **零 gc 调控**：唯一 `gc.` 出现在 `tests/_tmp/soa_bench.py:61`（bench 里 collect 一次）。运行期完全使用默认阈值 (700, 10, 10)。

### 3.2 对象规模普查（500 球）
- 受 GC 跟踪的“长寿”对象：501 GameObject × ~10 个跟踪对象（组件/Material/ScriptComponent…）+ **501 个独立 Mesh**（`spec_to_mesh` 每球新建，sceneio.py:151/mesh.py:118-132）各带 3 个大 list（vertices 2035 项 / faces 3888 项 / face_colors 3888 项）。
- 关键量级：顶点/面 tuple 本身是“纯标量 tuple"会被 CPython 解除跟踪，但**容纳它们的 list 每次全收集要逐槽访问**——501 × 9811 槽 ≈ **490 万槽/次 gen2 遍历**，估算单次 gen2 停顿 **20-150ms**（nt 機/nvme 无关，纯标记遍历）。
- 每帧跟踪对象 churn ≈ **12-15K 个/帧**（二节 #6/#7/#8 + dispatch/签名 tuple），按默认阈值 gen0 每帧触发 ~18-20 次（单次 ~0.1ms，尚可），**gen2 大约每 5-8 帧就有资格触发一次**——这就是“越流畅 1% low 越尖”的机制：**FPS 越高 → 每秒 churn 与代数晋升越快 → gen2 停顿更频繁**，且流畅画面让尖刺在体感上更刺眼。

### 3.3 设计
**(a) gc.freeze() 接入点**（3.12 可用；把加载期产生的 ~490 万槽场景图整体移出收集集）：
1. `runtime.py:37-52`（PlayerApp：`scene_from_dict` 之后、`set_mouse_locked(True)` 前后）——发布玩家路径。
2. `tests/_tmp/stress_probe.py:113` 之后（探针与玩家同构；更严谨是在预热 40 帧后 :128-129 之后再 freeze，把 GL 惰性建资源也一起冻进去）。
3. `editor.py:1621`（`toggle_play` 进入分支：`is_playing = True` + `_ensure_phys_bridge()` 之后）——编辑器播放态；退出播放 `editor.py:1634` 分支 `gc.unfreeze()` + `gc.collect()`（退出要回收播放期垃圾）。
4. 注意：freeze 只冻结“当时存在的对象”，播放期新建的脚本实例/桥条目仍在年轻代——正确行为。

**(b) 播放态阈值策略**（比 disable 安全，见风险）：
- 进入播放（与 freeze 同点）：`gc.set_threshold(50_000, 50, 200)`。gen0 从 ~18 次/帧降到 ~0.3 次/帧；gen2 频率再降 ~100 倍。gen0 单次成本略升但仍是亚毫秒级。
- 不建议播放期 `gc.disable()`：**脚本生态确有循环引用**——每个脚本实例天然成环 `engine.models → m → sc._script → s.engine(=engine)`（engine.py:3797-3799, scripts.py 实例持有 obj/engine），用户脚本更容易造环。disable 后这些环及用户环无限积累（长局游戏内存单调上涨），且 exe 玩家场景没有兜底时机。
- 折衷（若阈值方案实测 gen2 仍可见）：播放期用 `gc.callbacks` 统计，仅在**帧预算有余量**（如本帧 dt < 预算 60%）时手动 `gc.collect(1)`（只收 1 代），gen2 全收集挂到“安全点”——加载场景、退出播放、窗口失焦——绝不在帧内自发触发。
- 退出播放：`gc.unfreeze(); gc.set_threshold(默认); gc.collect()`（editor.py:1634 分支开头）。

**(c) 治本项（比 GC 调参收益更大）**：二节 #1/#2/#6 的 churn 是 gen0/gen1 频繁触发与晋升的根源；501 个重复 Mesh 是 gen2 遍历 490 万槽的根源。同 params 球共享同一 Mesh 实例（渲染侧已解耦：颜色走实例属性，mesh.face_colors 只在桶几何构建时用一次）可把 gen2 遍历槽位砍 ~99%。此为行为级改动（物体级换 mesh 需置脏桶键），需用户拍板，故只列不展。

### 3.4 探针设计（加进 stress_probe.py）
```python
import gc
_gc_log = []                      # (gen, ms, frame_idx)
_gc_t = [0.0, 0]                  # start, cur_frame
def _gc_cb(phase, info):
    if phase == 'start':
        _gc_t[0] = time.perf_counter()
    else:
        _gc_log.append((info['generation'],
                        (time.perf_counter() - _gc_t[0]) * 1000.0,
                        _gc_t[1]))
gc.callbacks.append(_gc_cb)
# 主循环里: _gc_t[1] = frames; 并同步记录每帧 wall dt 到 frame_dt[]（已有 t0/wall, 需改成逐帧 perf_counter）
```
测量窗口结束后输出：
- 按代分桶：count / 总 ms / max / p99（`collections.Counter` + 排序直方图，10 桶 0-0.1/0.1-0.5/…/>50ms）；
- 帧尖刺对账：`frame_dt` 中 >2×中位数的帧号 vs `_gc_log` 里落在该帧的 (gen,ms)——直接证明“尖刺=GC”或排除；
- 辅助：窗口前后 `gc.get_stats()`（各代 collection 次数差）、`gc.get_count()`、`len(gc.get_objects())` 采样一次（仅诊断，开探针时才跑）；
- 建议加环境开关 `LOOM_GC_PROBE=1`，默认关（callbacks 本身每次 GC 两次 Python 调用，~µs 级，但仍按项目惯例做成开关）。

## 四、数据布局问题清单

1. **【最大】AABB staging 每帧 32.6MB 冗余回填**（engine.py:2183-2185）：`vhN[r] = lst[r][1]` 拷的是**网格齐次顶点（常量，`_bb_cache` 已保证不变）**，与帧无关。同一模型只要不换 mesh，该行内容逐帧相同。当前按 `(gi,n,V)` 键缓存缓冲**容器**，却每帧重拷**内容**。改法：给每行记 `(id(mesh), mesh.vertices 身份)` 脏标记，只回填脏行；500 球静止网格下从 32.6MB/帧 → 首帧后 ~0。这是 steady-state 带宽与三级缓存污染的第一来源（附带：numba 读 vhN 的访存局部性也因此每帧重建）。
2. **`_fw32` 花式索引双拷贝**（engine.py:3907, :3925, :3937）：桶内下标顺序在静态场景逐帧不变，`self._fw32[idxs]`（(k,4,4)f4）可用持久 `np.empty` + `np.take(..., out=)` 复用，或把 `_fw32` 直接按桶序写入 staging 一次（sha 写复用同一份切片视图），消 384KB/帧×3 次分配。
3. **SoA 快照粒度过粗**（engine.py:2504-2522）：keys 是全场景 501×3 对象 id 的大 tuple，100 个 rotate 脚本每帧重建 Point3D → 恒失效 → 每帧全量重建 3 平面 + ~2500 元组。改法：keys 改存 numpy (n,3) int64（id 的低 32/64 位）+ 与缓存平面对比（C 级比较，不建 Python 元组）；或失效改“每对象代数计数”（transform setter 递增对象内 gen）。
4. **AABB 输出对象化**（engine.py:2190-2192）：纯 Python namedtuple 出口（1002 Point3D/帧）。阴影/碰撞两端最终都只读 x/y/z 再拼回 numpy（:2203-2209, :3311-3322）。可让 `_aabbs_batched` 直接输出/复用 (n,6) f64 平面（mn3+mx3），两消费端切片读取——消掉整个 namedtuple churn 层。注意 `get_collisions`/脚本 API 仍需 Point3D 的调用点保留转换（仅在碰撞事件帧）。
5. **碰撞候选对全对生成**（engine.py:3366-3376）：501 collider → 125,250 对全生成再过滤。numpy 侧 6.3MB/帧临时 + related 向量化计算。中期应按 collider 半径做网格/空间哈希候选剪枝（属组4/组5 范畴），短期可先把 `triu_indices` 的 2×int64 改用 `np.triu_indices` 的替代（自算 i,j 递增序列写入持久缓冲）+ `ai/bj` 花式索引改持久 out。
6. **f64→f32 边界唯一且干净**：`_prepare_bucket_frame` 是唯一 f32 化点（:3907），`st[:k]`/`inst['main'].write(st[:k],0)` 走 buffer 协议零拷贝（:3936），`inst['sha'].write(self._fw32[idxs],0)` 除外（见 #2）。无多余转换拷贝，这块组1 做得是对的。
7. **残留逐帧属性链**（可接受但备案）：`_prepare_bucket_frame` 每物体 `models[i].renderer.material` 两跳 + 2 读（:3930-3935，500 次/帧）；`update_audio`/`update_animations` 全模型 `m.audio_source`/`m.animator` 直属性读（:3398, :3412，各 501 次/帧，廉价）；`_entry_signature` 每模型 ~10 个 getattr（physics_bridge.py:647-657，501 次/帧）——与 #7 的 O(n²) 扫描同属桥 ensure_models，一次重构可全消。
8. `_upload_lights` 8 次 `ascontiguousarray().tobytes()`（:2041-2048）：缓冲区都是 8 行小数组，可预建一个持久 bytes 视图/直接 `write(memoryview)` 省去 tobytes 临时——量小（~1.5KB），优先级最低。

| **1** | **GC 代际停顿**：490 万槽场景图（501 独立 Mesh 的三大 list）+ 12-15K 对象/帧 churn，默认阈值下 gen2 高频触发 | GC 停顿 | 全项目无任何 gc 调控（唯一 gc. 在 soa_bench）；churn 集中在二节 #6/#7/#8；“越流畅 1% low 越高”与“FPS 越高→每秒 GC 代数轮转越快”机制吻合；帧时间尖刺量级（几十 ms）只有 gen2 能给出 |
| **2** | **AABB staging 32.6MB/帧冗余 memcpy**（engine.py:2183-2185） | 带宽/缓存逐出 | 缓冲复用但内容每帧全量重拷，拷的是逐帧不变的网格常量；单帧 32MB 写+读足以把 numba 工作集与矩阵平面全部逐出 LLC，放大下一阶段（GL 上传/绘制取数）的访存延迟——整体帧时间与偶发页错误共用此根因 |
| **3** | **碰撞候选对 6.3MB/帧 numpy 临时**（engine.py:3366-3392） | 逐帧大分配 | 501 collider 恒走全对 triu 路径；大块临时 → 页错误/堆增长 → 喂 GC（与 #1 复合）；np 分配走 malloc 大块，Windows 前端堆偶发慢路径即尖刺 |
| **4** | **compute_world_matrices ~2.3MB/帧 9 组临时**（engine.py:2545-2594） | 逐帧分配 | 每帧固定发生；S/T/Rx/Ry/Rz 形状恒定可持久化复用（写入端已全是赋值语句，改造成本低） |
| **5** | **Python 对象 churn 三件套**：SoA keys/cur（~2500 obj）、AABB namedtuple 出口（~3500 obj）、桥签名 tuple（~6000 obj） | GC gen0 压力 | 单项字节不大，但合计 >1 万跟踪对象/帧，是 gen0 每 ~50ms 触发数十次的直接原因；与 #1 是同一枚硬币的两面 |
| **6** | **桥 ensure_models O(n²) 扫描 + 每帧 keep/signature 重建**（physics_bridge.py:771/:784/:789） | CPU（平稳非尖刺） | 即已知"physics 22.8ms"的主嫌疑（501×~250 次 next 身份比较）；它是平均帧时间大头而非 1% low 元凶，但压着“更流畅"的天花板（组5/V02 待办） |
| **7** | `_fw32` + 双花式索引 384KB/帧（engine.py:3907/:3925/:3937） | 逐帧分配 | 量级小于上列，改造廉价，顺手做 |
| **8** | `_scene_light_bounds_par` 256KB/帧 + 4008 tuple（engine.py:2202-2210） | 逐帧分配 | 单光源场景固定发生；可与 #5 的 AABB 平面化一起消 |
| **9** | `_upload_lights`/VP tobytes 零星 ~3KB/帧、池 future/chunk 对象 | 小额 | 每帧固定但可忽略，不单独立项 |

**结论**：1% low 的最可能组合是 **#1（GC gen2）为尖刺本体、#2/#3 为放大器**（带宽逐出+大块分配让停顿帧更贵）。最低风险落地顺序：① gc.freeze+阈值（接入点已给，半小时级）② vhN 脏行回填（局部改动，收益 32MB/帧）③ AABB 平面化+SoA keys numpy 化（消 churn）④ 桥 ensure_models 索引化（配合组5）。

## 六、未决问题

1. **culverin 批量读是否零拷贝**：`post_step` 的 `np.asarray(w.positions)`（physics_bridge.py:945-948）取决于 culverin 暴露的是 buffer 视图还是每次新建 C 数组——影响二节 #9 的量级，需在实机加一行 `id()`/`flags` 探测确认。
2. **Mesh 共享与逐球换色的边界**：face_colors 只在桶几何 flatten 用一次、颜色已走实例属性，理论可安全共享；但 mesh 身份变化会影响 `_bb_cache`/`_homogeneous_vertices`/Vk `_bb_local` 的键数量与序列化（spec_to_mesh 每 object 独立建）——是否做 501→1 去重属行为级决策，需用户拍板（收益：GC gen2 遍历 -99%）。
3. **用户实测 40FPS 的宿主形态**：是编辑器播放（Qt 嵌入、EditorApp.render 另有 view.draw 面板成本）还是 PlayerApp/打包玩家？GC 接入点两处都给了，但探针对账（帧号↔GC 事件）要在用户实测的同一宿主里跑才闭环。
4. **组4 视锥剔除的排期交互**：若先做剔除，`_aabbs_batched` 的全量 501 组会缩到可见子集，二节 #2/#3/#8 的量级同比例下降——优先级排序可能因此互换（当前按“不做剔除”估算）。
5. **`_physics_bounds`/帧内 dict 的 legacy 路径**：桥异常回退 legacy 时 500 球会退化到每子步全网格变换（A3 注释已自知）——本轮不处理，但桥异常日志若在实测中出现，帧尖刺解释要换轨到 legacy 路径。
