# 开发要求：功能解耦与模块化（一个功能一个文件）

> **人类原话（2026-11-18，强制要求）**：
> 「功能解耦化、模块化也都是 beta7 要做的工作，最好做到**一个功能一个文件单独做，不把多个功能混合在同一个文件中**，
> 功能模块与功能模块之间**通过标准方式互相调用和关联**；
> 如果两个功能同时**大量依赖同一段前置**，那应该采取**将两个功能的前置独立成一个单独库来调用**以节省代码长度，
> **不应该选择将两个功能写在同一个文件里**。**全部解耦化对于开发有利。**」

**这是强制要求。** 新增功能、搬动功能、或修改现有文件结构时都必须遵守。

---

## 1 六条硬规则

### 规则 1：一个功能一个文件

一个 `.py` 文件只承载**一个功能域**。判断标准（可审计）：

> **能不能用一句话说清这个文件负责什么，且这句话里不出现「和」「以及」「同时」？**

不能 → 说明它混了多个功能，应当拆分。

**允许的例外**（必须写明理由）：
- **门面/装配文件**（如 `engine_core.py`）：只做 `class X(A, B, C)` 装配 + 跨域公共入口，不含具体实现；
- **契约/常量单点**（如 `loom_scene_contract.py`）：只放版本号、错误类型、纯函数契约；
- **测试文件**：一个测试文件对应一个被测功能域（可以多组断言）。

### 规则 2：模块之间只通过标准方式互调

| 允许 | 禁止 |
|---|---|
| 调用对方**公开 API**（不带下划线的方法/函数） | 直接读写对方 `self._private` 字段 |
| 通过**钩子**（`_backend_*` / `_xxx_impl`）由宿主注入差异 | 在 A 模块里 `if 后端 == 'vk'` 分支 |
| 通过**契约类型**（如 `LightState` / `CameraState` / `TargetDecl`）传递数据 | 传递裸 dict 且各自解释字段 |
| 通过**事件总线**（`self.events`）解耦 | 模块 A 直接 import 模块 B 的内部函数 |
| 通过**服务注册表**（B7-27 目标态）声明 `provides` / `requires` | 隐式依赖「B 一定已经初始化」 |

**判据**：把 A 模块单独拿掉，B 模块应当**在导入期不炸**（运行期缺能力要显式报错，不许静默）。

### 规则 3：共享前置抽成独立库，**不要**因此合并两个功能

这是最容易做错的一条。当两个功能都大量依赖同一段前置时：

`@
❌ 错：把 A 和 B 写进同一个文件（因为都要用 P）
     feature_ab.py  →  P + A + B

✅ 对：把 P 抽成独立库，A、B 各自 import 它
     lib_p.py       →  P（唯一实现）
     feature_a.py   →  import lib_p; A
     feature_b.py   →  import lib_p; B
`@

**为什么**：合并后 A 和 B 的改动会互相干扰（改 A 的测试会跑 B、A 的私有状态可能被 B 误用），
而且「P 有 bug」会变成「A 和 B 都有 bug」，定位成本翻倍。

**本工程已有正例**（照这个做）：
- `loom_collision.py`：GL 与 VK 都要碰撞配对/派发 → 抽成共享库，两端 import（**没有**把两端合并）；
- `loom_scene_query.py`：11 个纯数据查询 → 抽成共享 mixin，两端继承；
- `loom_model_data.py`：模型/材质数据面 → 抽成共享 mixin，GPU 上传留给后端钩子；
- `loom_pass.py`：FramePlan 描述层 → GL/VK 共用同一份「纯数据、无后端依赖」的描述。

### 规则 4：解耦优先于「少写几行」

当「合并能少写 30 行」与「拆开各自清晰」冲突时，**选拆开**。
人类原话：「全部解耦化对于开发有利。」

### 规则 5：新功能优先新开模块，但**先分清「扩展」还是「新增」**

> **人类原话（2026-11-18）**：
> 「所有新功能**优先考虑新开一个模块**，但要**分清对当前一个功能的扩展**和**新加一个新功能**两种情况，
> **不要将两种情况全部混起来**；如果拿不准应该是对已有的功能扩展还是新加一个功能，**就问人类决策**。」

**动手前必须先回答这个问题**：

| | **A · 扩展已有功能** | **B · 新增功能** |
|---|---|---|
| 定义 | 在**已有能力边界内**加深/补全（同一份契约、同一批用户场景、同一类数据） | 引入了**新的能力边界**（新的用户场景 / 新的数据种类 / 新的对外接口） |
| 例子 | 给 @@load_scene@@ 补一个失败语义；给碰撞派发补 trigger 分流；给已有 API 补 VK 侧实现 | 加一个 Sequencer；加 .pak 打包；加骨骼蒙皮；加一个新的后端 |
| 放哪 | **在已有模块内扩展**（必要时把该模块内部再拆子模块） | **新开一个模块文件**（+ 在需要时抽共享前置库） |
| 禁止 | 顺手把「新功能」也塞进这个文件 | 把「扩展」硬拆成新模块导致同一能力两处实现 |

**判断辅助（三条，任一命中就按 B 处理）**：

1. **需要新的公开 API 名**（脚本要学新东西） → B
2. **需要新的数据结构 / 文件格式 / 配置键** → B
3. **现有模块的 docstring 里那句话要加「和/以及」才能覆盖它** → B

**三条都不命中** → A（在已有模块内扩展）。

**拿不准 → 停下来问人类**，不要自己拍。**不许**用「先塞进去以后再拆」当折中 —— 那就是规则 3 的反模式。

### 规则 6：一次提交只做一件事（扩展 或 新增，不许混）

同一次提交里**不许**同时包含：
- 「扩展已有功能」的改动 + 「新增功能」的改动；
- 「纯搬家/拆分」+ 「改语义」；
- 「修缺陷」+ 「重构」。

理由：混在一起就无法用「行为零变化 + 全绿」来验证搬家，也无法单独回退。
（本工程真犯过：修全屏时顺手改 GL 置顶/还原 → 两端不一致且无法单独回退。）

## 3 拆分时的强制纪律（不许「拆出 bug」）

拆分是**纯搬家**，不是重构语义。必须：

1. **行为零变化**：拆完 `run_all` 全绿、`smoke` 绿、A/B 像素门绿（若涉及渲染）；
2. **一次只拆一个域**，拆完立刻跑全套回归；
3. **不许顺手改逻辑**（发现缺陷就单独立项，写进待裁决清单）；
4. **公开符号不许改名**（除非同步全仓调用点 + 门）；
5. **拆出来的模块要有 docstring 说明「我负责什么 / 我不负责什么」**；
6. **拆完更新本文件 §2.2 的状态**。

---

## 4 怎么判断「这个文件该拆了」

三条任一成立就应当拆：

| 判据 | 阈值（经验值） |
|---|---|
| **顶层功能区块数**（`# ---- 区块标题 ----`） | > 5 个 |
| **行数** | > 1200 行 |
| **一句话说不清职责** | 需要「和/以及」才能描述 |

**例外**：装配文件（mixin 汇总）、纯数据表、生成代码。

---

## 5 与 B7-27（模块化 + 服务注册表）的关系

本文是**文件级**解耦要求；B7-27 是**运行期**模块化（`plugin.json` 声明 `provides` / `requires` / `api_version`、装配按依赖拓扑排序、模块间只经 API）。

两者关系：**文件级解耦是运行期模块化的前提** —— 一个文件里混了 5 个功能，就没法把它声明成一个可替换模块。

所以顺序是：**先按本文拆文件 → 再按 B7-27 做成可声明模块**。

---

## 6 反模式（都是本工程真出现过的）

| # | 反模式 | 后果 |
|---|---|---|
| 1 | 因为「都要用 P」就把两个功能合进一个文件 | A 的改动干扰 B；P 有 bug 时定位成本翻倍 |
| 2 | 拆文件时顺手改逻辑 | 拆出 bug 且无人能定位（「搬家」和「改语义」混在一次提交里） |
| 3 | 拆完不更新门/文档 | 下一个人按旧路径找代码 |
| 4 | 在 A 模块里 `if 后端 == 'vk'` | 后端差异渗回公共层（见 `开发要求_后端API一致_JVM模型.md` 反模式 2） |
| 5 | 把「共享前置」写成 A 的私有函数、B 去 import A 的下划线函数 | 隐式耦合，A 一改 B 就炸 |
| 6 | **把「新功能」塞进「扩展」的提交里** | 无法单独回退；无法用「行为零变化」验证扩展部分 |
| 7 | **拿不准扩展还是新增，自己拍板** | 拍错方向后要么同一能力两处实现，要么模块越滚越大 |

## 7 一页速查

`@
□ **这是「扩展已有功能」还是「新增功能」？**（拿不准 → 问人类）
□ 扩展 → 在已有模块内加深；新增 → 新开一个模块文件
□ 这次提交只做一件事？（扩展 / 新增 / 搬家 / 修缺陷，不混）
□ 这个文件能用一句话说清职责吗？（不出现「和/以及」）
□ 顶层功能区块 > 5 或行数 > 1200？→ 该拆
□ 两个功能都要用 P？→ 抽 P 成独立库，不是合并 A+B
□ 模块间只调公开 API / 钩子 / 契约类型 / 事件总线？
□ 拆分是纯搬家（行为零变化 + run_all 全绿）？
□ 拆出来的模块写了「我负责什么 / 不负责什么」？
□ 更新了本文 §2.2 的状态？
`@
