## 0 一句话总结

> **白盒定标准，黑盒写实现，灰盒做验证，自审走流水线，第三方独立复核，架构写成可读的图，结论落成可跑的门，路线由人类拍板。**

三条不可让渡的原则（贯穿全文）：

| # | 原则 | 含义 |
|---|---|---|
| 1 | **AI 可以替人类写实现，不能替人类选路线** | 架构分叉、接口语义、错误策略、资源与安全边界、演进方向 —— 这些是工程判断，必须人类显式选定 |
| 2 | **AI 可以审自己的实现，但审查过程必须是人类可复现的实验** | 没有可执行动作的结论不算结论；拿不准时必须交人类 |
| 3 | **AI 审核 AI 时，审核结论本身也要被复核** | 第三方审核降低盲区，但会引入新错误（方向错、漏上下文、过度推断），主责 AI 必须逐条核证据 |

# 第一部分 问题起点：三种典型失败

## 1.1 失败一：只对齐了样例，没对齐设计标准

传统 Vibe Coding：人类自然语言描述 → AI 写代码 → 人类「感觉对了」就接受 → 测试围绕少数固定用例。结果是 AI 过拟合当前对话、当前示例、当前测试：快乐路径能跑，边界/非法输入/接口缝隙/并发状态全崩，而人类以为对齐了「设计标准」，实际只对齐了「局部样例」。

## 1.2 失败二：路线被 AI 悄悄选完

更隐蔽的前提问题：很多使用者**没有能力**写出完整架构白盒图纸、定义清晰接口契约、在分叉口判断该走哪条路。于是流程退化成：

```
用户说不清 → AI 自己猜 → AI 自己选路线 → 用户看不懂 → 表面能跑 → 埋下架构债
```

## 1.3 失败三：自审时的自我合理化

AI 审自己的代码，激励方向是反的（第三方审查者天然有「找茬」激励，AI 没有）：

| 风险 | 表现 | 后果 |
|---|---|---|
| 自我合理化 | 「这里我这样写是合理的，因为……」（推理链只走到「合理」就停） | 漏报 |
| 证真偏向 | 只写「为什么我相信它对」，不写「为什么它不可能错」 | 漏报 |
| 证据不闭合 | 给结论不给「读者能照着跑一遍」的步骤 | 外部无法审计 |
| 粒度失真 | 把明显正确的代码列成「疑似」（假阳性爆炸），或把高风险代码略过（假阴性） | 信噪比崩 |
| 探针缺失 | 拿不准就猜「应该没事」或直接改，不写实验 | 用假信息做决策 |
| 过度自信的证伪 | 「我检查了这条路径，没问题」—— 实际有 5 条路径 | 漏报 |

**三种失败对应本文的四层防线**：第一种（只对齐样例）→ 第二部分（契约 + 验证 + 隐藏 oracle）；第二种（路线被 AI 选）→ 第二部分 2.7（人类掌舵）+ 第七部分（版本与节奏纪律）；第三种（自审合理化）→ 第三部分（自审流水线）+ 第四部分（独立第三方复核）。

# 第二部分 第一层：白盒契约、黑盒实现、灰盒验证

## 2.1 为什么不是「纯黑盒对齐」

只定义接口签名 + 黑盒测输入输出，不能保证整体正确：接口签名太弱无法表达语义；黑盒只能证伪不能证明全称；局部通过不代表组合正确；并发/资源/副作用难覆盖；AI 可能过拟合测试、硬编码、特判、绕过验证。

## 2.2 分层体系（六层）

| 层 | 谁负责 | 内容 |
|---|---|---|
| **白盒层** | 人类（AI 辅助，人类确认） | 架构边界、组件职责、接口协议、前后条件与不变量、错误模型、时序/超时/重试/幂等、资源预算、安全与权限、可观测性要求、组合规则（谁能调谁） |
| **黑盒层** | AI | 算法、数据结构、内部拆分、性能优化、错误处理实现、资源管理实现 |
| **灰盒层** | 工具 | 静态分析、覆盖率、运行时监控、性能剖析、日志追踪、沙箱与权限限制、资源审计 |
| **验证层** | 工具 + 独立进程 | 单元/属性/模糊/差分/边界/契约测试、模型检查、符号执行、定理证明 |
| **运行时层** | 产品 | 断言、熔断、限流、回滚、隔离、最小权限、审计日志、异常监控 |
| **决策层** | **人类，不可让渡** | 路线选择、架构取舍、接口语义、错误策略、资源与安全边界、演进方向、技术债接受与否 |

## 2.3 契约的六元组

```
S = (Pre, Post, Inv, Protocol, Resource, Error)
AI 的实现 I 必须满足： ∀x, Pre(x) ⇒ Post(I(x))
```

黑盒测试只检查有限样本，形式验证才能覆盖全称。**这条差别决定了「测试通过」永远不等于「实现正确」。**

## 2.4 合法域 / 非法域 / 边界带 / 接口缝

| 域 | 怎么测 | 目的 |
|---|---|---|
| 合法域 L | 按规则生成大量**合法但不同**的输入（属性/模糊/差分/契约测试） | 逼 AI 找通解，而不是硬编码固定用例 |
| 非法域 I | 先由人类定义「每类非法输入对应哪种策略」（拒绝/钳制/默认值/降级/静默/上抛/重试/隔离审计） | 没有策略定义，就只能观察行为，不能判定对齐 |
| 边界带 B（距 ∂L 小于 ε 的邻域） | 在 B∩I、B∩L、以及 ∂L 精确点上采样 | off-by-one、浮点、溢出、Unicode、时区、空/单元素/满容量、并发临界 |
| 接口缝 | 把上游可能产生但下游未声明的值灌进下游 | A 的后置条件弱于 B 的前置条件、单位/精度/编码不一致、错误语义不统一、部分失败的半成品状态 |

## 2.5 oracle 从哪来（最难的一环）

随机输入好生成，判断输出对不对才是瓶颈。可用 oracle：后置条件、不变量、参考模型、元属性（排序后有序、解析再序列化等价、幂等、交换律）、形式规范、独立实现做差分。

> **警告**：如果 oracle 只是从初始样例泛化出来的规则，那规则本身仍是人类规范。规范有漏洞，AI 就可能「合法地」钻空子。

## 2.6 防过拟合验证系统

如果 AI 能看到测试，它可能：对特定边界值硬编码、只处理被测试的几类非法输入、伪造错误反馈但不真正恢复状态、测试环境正确生产绕过、过拟合生成器分布、只满足检查项不满足真实意图。

工程对策：**种子数据给 AI 看，验证生成器与 oracle 隐藏**（独立进程或服务），只返回通过/失败与最小反例；多套独立生成器、多分布、随机种子；用变异测试评估测试强度；用独立 AI 专门生成对抗输入；所有历史反例进回归集。

## 2.7 人类掌舵：把路线选择强行摆到台面上

1. AI 先追问：核心目标？规模？延迟/一致性要求？团队几人？多久上线？
2. AI 列 2~4 条候选路线，各自说明适用场景、代价、风险、演进路径；
3. AI 明确标注每条路线牺牲了什么、换来了什么；
4. 人类**显式选择**一条，或给出自己的新路线；
5. AI 只能在路线选定后才进入实现填充。

AI 在这里的角色是：苏格拉底式追问者、方案生成器、优缺点分析器、一致性检查器、图纸辅助绘制者、契约辅助定义者。**不是**：架构决策者、路线拍板者、产品取舍决定者、风险承担者。

## 2.8 能保证什么、不能保证什么

| 能提高保证 | 不能自动保证 |
|---|---|
| 快速迭代；采样分布上对齐；防固定用例硬编码；提高健壮性；暴露接口组合问题；发现边界与非法输入漏洞；形成反例回归资产；保留人类对路线的控制权 | 数学意义上的全称正确；规范本身正确；并发全交错；资源耗尽下所有行为；安全关键系统的绝对安全；生产与测试环境完全一致；AI 能替人类做工程判断 |

# 第三部分 第二层：AI 自审的流水线（粗筛 → 双向推演 → 实操）

## 3.1 三阶段总览

```
┌─────────────────────────────────────────────────────────────┐
│ 阶段一 粗筛（广度优先，宁可疑不可漏，但明确排除「绝对对」） │
│   输入：待审代码 / 白盒契约 / 文档                          │
│   输出：疑似项清单（每项带类型标签）+ 跳过登记表            │
└─────────────────────────────────────────────────────────────┘
                        ↓ 每个疑似项
┌─────────────────────────────────────────────────────────────┐
│ 阶段二 双向逻辑推演                                         │
│   反手（证伪）：努力证明「这里没有 bug」→ 成功 = DISPROVED  │
│   正手（证真）：努力证明「这里有 bug」  → 成功 = PROVED     │
│   两边都失败 = UNKNOWN；两边都成功 = CONTRADICTION（重做）  │
│   硬约束：每条结论附 8 段式可审计逻辑链                     │
└─────────────────────────────────────────────────────────────┘
                        ↓ 按判定分流
┌─────────────────────────────────────────────────────────────┐
│ 阶段三 实操                                                 │
│   PROVED       → 写修复 + 跑验证 + 反例入回归集             │
│   UNKNOWN      → 写探针取更多信息 → 回填阶段二重跑          │
│   DISPROVED    → 关闭并留证（避免下次重复粗筛）             │
│   CONTRADICTION→ 暂停，先审查推理链本身                     │
└─────────────────────────────────────────────────────────────┘
```

三阶段的核心张力：

- **阶段一宁可宽**：粗筛是筛子不是判决，多报一点让阶段二有活干；但把 `def f(): pass` 也列进来就是噪音。
- **阶段二必须严**：进入阶段二的每一项都要走完反手和正手并留下逻辑链。**不许跳过反手直接做正手** —— 这是对自我合理化的第一道对冲。
- **阶段三必须实**：所有结论都要落到「跑一次看得见」的行动上。**没有可执行动作的结论不算结论。**

## 3.2 阶段一：粗筛

唯一目的：在合理成本内把高嫌疑点全找出来、把低嫌疑点明确排除、并给每个疑似项标注「可能是什么类型的 bug」。
约束：广度优先（模块→函数→分支→语句，不深入单点）、宁可疑不可漏（成本不对称：漏一个真 bug 就永久错过）、不瞎质疑、必须打标签。

### 3.2.1 「绝对对」的四类可审计跳过理由

| 理由 | 例子 | 为什么可以跳 |
|---|---|---|
| 语言规范保证 | `dict.get(k, default)` 不抛 `KeyError` | 标准库文档是唯一判据，不依赖项目 |
| 白盒契约明确声明 | 契约写「输入 x 已保证 x>0」，则不必审 x<=0 分支 | 契约本身是审查基准 |
| 已有回归测试覆盖 | 有 `test_xxx` 覆盖该路径且全绿 | 用测试证据作跳过依据 |
| 工具/框架自身声明 | 工具文档写「print 属于上报」 | 判定基准是工具自身文档 |

**不允许的跳过理由**（自我合理化的常见入口）：看起来简单 / 我写的我记得 / 上次跑过没报错 / 经验上安全 / 语义我懂不用细看。
共同问题：依赖 AI 的内部状态，外部不可审计 —— 只要跳过理由不可审计，跳过就作废。

### 3.2.2 疑似类型表（给阶段二指方向，不是判决）

| 组 | 标签 | 含义 |
|---|---|---|
| A 语义 | `SEM-MISMATCH` / `SEM-OVERFIT` / `SEM-SILENT` / `SEM-DEFAULT` | 与契约不一致 / 只覆盖示例 / 静默失败 / 失败返回静默默认值 |
| B 边界 | `BND-OFFBYONE` / `BND-EMPTY` / `BND-OVERFLOW` / `BND-UNICODE` / `BND-TIME` / `BND-CONCURRENCY` / `BND-RESOURCE` | 边界点、空/满、溢出、多字节、时区、并发交错、资源耗尽 |
| C 接口 | `IFACE-PRECOND` / `IFACE-UNIT` / `IFACE-ERROR` / `IFACE-PARTIAL` / `IFACE-VERSION` | 后置弱于前置、单位/精度/编码、错误语义不统一、半成品状态、版本错配 |
| D 过拟合 | `OVERFIT-HARDCODE` / `OVERFIT-TESTENV` / `OVERFIT-GEN` / `OVERFIT-ORACLE` | 硬编码测试值、只在测试环境对、只覆盖生成器分布、只满足检查项 |
| E 可审计 | `AUDIT-NOCHAIN` / `AUDIT-DEADCODE` / `AUDIT-ASYMMETRY` / `AUDIT-DOCIMPL` | 注释声称已处理但行为不符、白名单死条目、相似情况不同对待、文档与实现冲突 |
| F 工具自身 | `TOOL-WHITELIST` / `TOOL-HEURISTIC` / `TOOL-CLI` / `TOOL-SCOPE` | 白名单过宽过窄、启发式过糙、CLI 与文档不符、扫描范围与宣称不符 |

### 3.2.3 输出格式（六元组，缺一不可）

```
ID:        P-<编号>            # 全程唯一，后续阶段引用
位置:      <file>:<line> 或 <函数名>
标签:      <从类型表选 1-2 个>
初步方向:  <一行说明，指向可能的 bug 机制>
跳过理由:  <若决定跳过，必须写明四类理由中的哪一类>
粗筛证据:  <引用的代码行 / 文档句>
```

> **跳过要留痕**：跳过的项不进入阶段二，但跳过本身要被审计。后续发现某个「跳过」是错的，说明粗筛判据有漏洞，要补规则。

## 3.3 阶段二：双向逻辑推演

### 3.3.1 为什么必须双向独立

| 只做证真 | 找到一个「看起来像 bug」的点，写段「为什么是 bug」就结案 → 可能只是实现的合理选择，误报 |
|---|---|
| 只做证伪 | 努力证明「这里没问题」，成功就结案 → 证伪可能有漏洞（只查了 3 条路径中的 1 条），漏报 |

双向独立的价值在于**矛盾检测**：两条链互相制约，能抓出 AI 自己没意识到的推理漏洞。

### 3.3.2 四象限

| 证伪 | 证真 | 判定 | 后续 |
|---|---|---|---|
| 成功 | 失败 | `DISPROVED` 确认无 bug | 关闭，留证 |
| 失败 | 成功 | `PROVED` 确认有 bug | 进入阶段三修复 |
| 成功 | 成功 | `CONTRADICTION` 推理链有错 | 重做，不许选一边信 |
| 失败 | 失败 | `UNKNOWN` 判据不明 | 探针；三次探针后升级人类 |

### 3.3.3 反手（证伪）的四条判据

1. **路径全覆盖**：列出所有可能被执行的路径（控制流图或等价枚举），并证明覆盖了全部。
2. **每条路径有证据**：每条路径都引可核对的行号/文档句，证明该路径不产生疑似行为。
3. **没有「未检查路径」**：存在无法枚举的路径（动态调用/反射/多线程）必须显式标记「无法证伪」。
4. **不依赖内部状态**：不出现「我认为 / 经验上 / 看起来」。

> 证伪成功 **不是**「我没找到反例」。没找到 ≠ 没有。

### 3.3.4 正手（证真）的五条判据

1. **最小复现**：可复制粘贴的最小输入，隔离其他变量。
2. **预期（文档依据）**：引用**工具自身的白盒契约**说明应该是什么行为。不能引用外部标准（外部标准只用于判断契约本身对不对）。
3. **实际（代码推理）**：从代码逐步推出实际行为，每步可被源码验证。
4. **差异明确**：预期与实际不一致，方向明确（多做了什么/少做了什么/返回了不该返回的）。
5. **可执行验证**：给出能跑的命令，任何人跑一遍都能对照。

### 3.3.5 逻辑链的 8 段式模板（缺一段即无效）

```
【P-xx · <证伪/证真> · <结论>】
1. 判定基准   引用白盒契约的哪一条（禁止引用外部标准）
2. 代码证据   原样引用源码片段（不是转述），标函数名/常量名/行号
3. 推理链     从代码到行为的逐步推导，每步可被源码验证；
              证伪必须附「路径枚举表」，证真必须附「最小复现输入」
4. 预期       （仅证真）按判定基准，应该输出什么
5. 实际       （仅证真）按推理链，实际输出什么
6. 差异分析   （仅证真）预期与实际的差异，方向明确
7. 可复现验证 一段能直接跑的命令，输出可对照
8. 判定       DISPROVED / PROVED / UNKNOWN / CONTRADICTION + 一句话理由
```

**第 3 段是重灾区**。写成「我检查了 if 和 else，都没问题」= 不完整。合格写法必须列出每条路径的进入条件、每条路径的返回值/异常、以及「路径枚举完备」的理由（无动态分派、无闭包捕获、无 `**kwargs` 转发）。
区别在于：前者只说「检查了」，后者让外部审计者能照着源码逐条核对，并发现「漏了一条路径」。

## 3.4 阶段三：实操

| 判定 | 动作 | 硬要求 |
|---|---|---|
| `PROVED` | 写修复 → 跑验证 → 反例入回归集 | 修复只改被证真的那一点（审 A 改 B 会让推理链失效）；改完必须跑验证，不能直接说「已修复」 |
| `UNKNOWN` | 写探针取更多信息 → 回填阶段二重跑 | 探针必须有目标（「跑一下看看」信息增益为零）；探针不许写进生产代码；三次探针仍 UNKNOWN 必须升级人类 |
| `DISPROVED` | 关闭 + 留证 | 留证是为了下次粗筛不重复劳动 |
| `CONTRADICTION` | 暂停，先审查推理链本身 | 不许选一边信 |

**交人类的格式**：给具体问题 + 已知选项 + 各自代价，不给开放式提问（「你觉得怎么办」人类无法回答）。

## 3.5 推广：从「实现审查」到「设计审查」

同一套三阶段可以审白盒契约本身，对象从代码变成架构文档/接口定义/错误模型/资源边界/职责描述。

| 标签 | 含义 |
|---|---|
| `DESIGN-CONFLICT` | 两条契约互相冲突（如 A 声明「永不失序」、B 声明「允许乱序」） |
| `DESIGN-GAP` | 契约没覆盖某类情形（如错误模型没定义「部分成功」） |
| `DESIGN-AMBIG` | 措辞有歧义（「尽量快」没有量化） |
| `DESIGN-OVERLAP` | 职责重叠（A 和 B 都声称负责数据校验） |
| `DESIGN-DEAD` | 永不触发的条款 |
| `DESIGN-DRIFT` | 契约与实现渐行渐远 |

**关键区别**：设计层证真成功后，**AI 不直接改设计** —— 「改哪一条、怎么改」是工程路线选择。AI 的产出是「冲突证据包」，人类裁决。
因此设计审查里人类裁决项比例高是**正常**的；如果 AI 很少交人类裁决，更可能是它在自我合理化。

## 3.6 失败模式清单（外部审计时优先查这些）

| 阶段 | 失败 | 表现 |
|---|---|---|
| 粗筛 | 瞎质疑 / 跳过头 / 标签缺失 / 跳过不留痕 / 广度过低 | 把 `def f(): pass` 列成疑似；用「经验上没问题」跳过关键路径；只列位置不列类型 |
| 推演 | 跳反手 / 证伪走过场 / 路径不枚举 / 证真不过硬 / 矛盾无视 / 基准混用 | 「检查了应该没问题」；没给最小复现；引用外部标准判实现 |
| 实操 | 修复顺手改别的 / 不跑验证 / 探针没目标 / 探针改生产代码 / 不回填 / 无限探针 / 问题太开放 | 改完不验证；探针跑完不重走阶段二 |

### AI 自我合理化的七个信号（专查）

1. 证伪链里出现「这个实现是合理的，因为……」—— 那是合理化措辞，不是证伪。
2. 正手链里「我认为用户不会这样用」—— 假设未验证。
3. `UNKNOWN` 被悄悄改成 `DISPROVED` —— 判定篡改。
4. 修复后没重跑验证命令，直接说「已修复」—— 验证缺失。
5. 跳过的项集中在大段代码 —— 跳过头。
6. 所有疑似项最终都是 `DISPROVED` —— 要么粗筛太严，要么证伪有系统性漏洞。
7. 所有疑似项最终都是 `PROVED` —— 反方向异常，证伪走过场。

> **最强信号**：如果报告里 **`UNKNOWN` 数量为 0**，几乎可以断定阶段二有系统性放水。真实项目一定有判据不明确的项。

# 第四部分 第三层：独立第三方审核（多代理）

## 4.1 为什么必须有这一层

第二部分的流水线解决「AI 自审不瞎说」，但它有一个天花板：**同一个模型、同一份上下文、同一套盲区**。
自审再严格，也只是把「我不知道」变成「我检查过的不知道」。

第三方审核带来三样自审给不了的东西：

| 收益 | 说明 |
|---|---|
| **搜索面** | 它没有你的先验，会把「你以为不用看」的地方重新看一遍 |
| **激励方向** | 它的任务就是找问题，没有「证明自己写对了」的动机 |
| **交叉验证** | 两条独立路径得出同一结论，比一条路径自证可信得多 |

> 但它**不是**替代复核。第三方审核会引入新的错误类型（见 4.4），主责 AI 必须逐条核证据。
>
> **一条容易搞错的前提**：多代理协作本身是可并发的（一个组件一个代理，互不干扰）。
> 你在某个环境里遇到「并发派发全挂」，那是**该环境的 API 并发配额**问题，不是协作模型的限制 ——
> 遇到时退化为串行即可，但不要把它写进方法论当成「只能单代理」。

## 4.2 派单规范（经验：这些细节决定成败）

| 规范 | 做法 | 原因 |
|---|---|---|
| **一个组件一个子代理** | 按「组件/切片」切分派单：一个组件（或一个独立语义面）= 一个代理，各自独立审；**多个组件可以并发** | 一个代理审多个组件会串味、证据变泛；按组件切分才能给出 file:line 级证据 |
| **并发是环境能力，不是协作模型** | 环境配额允许就并发派（每个组件一个）；受限时退化为串行，**切片不变** | 实测：某环境并发派 4 个会集体失败、单发成功 —— 那是 API 并发配额问题，**不能推导出「只能单代理」**。协作模型本身支持高并发多代理（据 DSH 侧信息，高并发多代理交互配合正在研发中） |
| **并发时要交叉复核** | 同一结论被两个代理独立指出 → 可信度升高；两个代理结论矛盾 → 主责 AI 自己核，核不了交人类 | 并发带来的真正增量不是速度，是**独立路径的交叉验证** |
| **只读** | 明确写「不要修改任何文件」 | 审核方一旦动手，就不再是独立视角 |
| **单一切片** | 一个代理只审一个维度（如「双后端重复实现」），不审全项目 | 切片越窄，证据越具体；宽任务会退化成泛泛而谈 |
| **给核对清单** | 列出具体要核的点（常量、默认值、失败路径、容量上限…） | 否则它只会给你「看起来不错」 |
| **要求 file:line** | 每条结论必须能指到文件行号；读不到就写「未读」 | 没有行号的结论无法复核，等于没有 |
| **要求列出未核实项** | 明确要求 D 段「你没能核实的」 | 防止它用推断填充空白 |
| **给它独立环境** | 同一工作目录但独立上下文 | 它会重新读代码，而不是继承你的结论 |

## 4.3 审核产出格式（建议固定成四段）

```
A. 规模统计     各标记/各维度的命中数（按文件分组的 Top10）
B. 对照表       | # | 语义 | A 侧位置 | B 侧位置 | 是否一致 | 证据（一句话+行号） |
C. 风险排序     判断「必须收敛成单一实现」的项，按风险排序，每项一句理由
D. 未核实项     明确列出（不许猜）
```

## 4.4 主责 AI 必须逐条复核（三类真实错误）

拿到审核报告后，**不能直接抄进结论**。复核方法：每条结论 → 自己找证据 → 标 `确认 / 推翻 / 未核`。
实测中第三方审核最常犯三类错误：

| 类型 | 表现 | 案例（抽象） | 复核要点 |
|---|---|---|---|
| **① 方向对、机制推断错** | 定位正确，但「后果」是按另一条分支的语义推的 | 审核方说「某后端会因此整盏灯变黑」，依据是它读到的另一分支的除法宏；实际两个后端分支的宏不同，它读反了分支 —— 我一度准备推翻这个**正确**的结论，读全文件的分支条件后才确认它成立 | 复核后果推断时**必须读全所有分支**，不能只看片段；分支宏/条件往往在文件开头 |
| **② 漏上下文** | 把「有意为之」当缺陷 | 审核方把某常量与另一处的数值不一致列为缺陷；实际源码里有 8 行论证 + A/B 实测记录说明该差异不影响结果 | 看到「两处数值不同」先找**论证注释与实测记录**，再判缺陷 |
| **③ 口径混入** | 统计里混进与主题无关的项 | 审核方把与主题无关的 36 处标记计入「重复实现规模」，拉高了结论强度 | 复核统计口径：分子分母是否同一口径 |

复核后的写法（示例）：

```
| 它报的 | 我的复核 | 判定 |
| X 后端灯变黑 | 结构属实；机制我逐层验到 shader 宏分支 → 确认 | 确认（静态，未做渲染实测） |
| 某常量三份定义 | 三份属实，但第 4 处使用点仍用自己那份 | 确认 |
| 某处不一致是缺陷 | 源码有 8 行论证 + A/B 记录 | 推翻（有意为之） |
| 材质回查行为不同 | 未读对照代码 | 未核 |
```

> **「未核」必须真的写「未核」**。把没查的写成「查不到」，是这类工作里最常见的失信方式。

## 4.5 审核失败的处置

| 情况 | 处置 |
|---|---|
| 代理启动即失败（API 挂/配额） | 不重试第三次；记「本轮无独立审核」，主结论降级标注 |
| 代理超时/无返回 | 同上，但保留已下发的核对清单，下一轮复用 |
| 代理结论大面积不可用 | 只采纳可复核的条目，其余进「未覆盖」 |

## 4.6 什么时候必须派第三方

1. **跨文件的「同一语义多处实现」**（这类问题人眼和自审都容易漏）。
2. **大范围数字统计**（静默异常数、API 面差异、重复代码量）—— 数字错会带偏整个结论。
3. **自己写下的关键结论**（尤其是「根因已定位」这种）。
4. **上线前的等价性判断**（产物与源码是否同一份、两端行为是否一致）。

# 第五部分 第四层：架构可读性（把理解成本降下来）

## 5.1 为什么这是一等公民

三个理由：

1. **设计失误大多不是「写错了」，而是「职责放错了位置」**。这类问题在单文件里看不出来，只有把「职责 → 位置」摊开才一眼可见。
2. **AI 的上下文有限**，接手时只能读一部分代码；没有架构图，它只能靠猜，猜错就改错。
3. **人类需要能审计 AI 的设计判断**。让人自己找错很难；给一张「谁依赖谁、哪个功能在哪几个文件」的图，人一眼就能看出「这里不对」。

> 一句话：**缺陷清单是让 AI 找错，架构图是让人自己找错**。后者更可靠。

## 5.2 三层视图（缺一层都不完整）

| 视图 | 回答什么问题 | 形态 |
|---|---|---|
| **① 目录树** | 文件实际怎么组织？哪个目录有多少行？ | 像文件管理器一样缩进，每个文件标行数与一句话职责 |
| **② 功能关系图** | 功能之间谁依赖谁？功能实现在哪几个文件？ | 节点=功能簇/文件，边=关系（带文字标注），分簇上色 |
| **③ 职责归属表** | 每个职责落在哪个模块？该模块的本职是什么？ | 表格：职责 / 落在哪 / 该模块本职 / 判断 |

## 5.3 图的工程规范（实测有效）

| # | 规范 | 原因 |
|---|---|---|
| 1 | **一张图 ≤ 15 个节点** | 超过就必然连线缠绕；46 节点 76 边的图是不可读的（实测教训） |
| 2 | **拆成多张小图**，一张只讲一件事 | 全景/装配/主链路/时序/清单，各一张 |
| 3 | **节点颜色 = 角色**（入口/门面/实现/契约/文件/产物） | 同一颜色在所有图里含义一致，扫一眼就知道层级 |
| 4 | **线型 = 关系种类**（实线=直接依赖，虚线=弱/运行时，粗线=继承/拼装） | 光有箭头分不清「调用」和「只是共享一个格式」 |
| 5 | **线上写字**（调用 / 实现于 / import / 共享契约 / 拼装） | 「谁因为什么依赖谁」必须写在线上，读者不用猜 |
| 6 | **功能 → 文件用「实现于」连线** | 这正是「这个功能分布在哪几个文件」的答案 |
| 7 | **流程用时序图，不用流程图** | 「谁先调谁」用流程图一定乱；时序图天然有序 |
| 8 | **画不下的进表格** | 图上只放主干，全量文件清单用表格（文件/行数/职责） |
| 9 | **同一张图里不要混「直接调用」和「隔层调用」** | 混画会让读者误判入口与层级（这是画图时最容易犯的错） |
| 10 | **判断与事实分开标** | 「这里职责放错了」是判断，要标注；否则读者会把判断当事实 |

## 5.4 职责归属表（最有价值的一页）

格式：

```
| 职责 | 落在哪（file:line） | 该模块的本职 | 我的判断 |
|------|--------------------|--------------|----------|
```

它为什么有用：把「职责」和「模块本职」并排放，**错位会自己跳出来**。典型错位形态（可直接套用当检查表）：

| 错位形态 | 例子（抽象） |
|---|---|
| 纯数据变换被绑在带副作用的流程里 | 版本迁移函数被放进「把数据装配进对象」的函数内部 → 不走装配的路径拿不到迁移 |
| 同一判定在多处重复 | 同一个校验在 3 个入口各调一次，其中一处漏了 |
| 渲染层回头改数据 | 容量超限时渲染层直接改写场景对象，保存后固化 |
| 序列化函数兼职事务 | 用一个参数当模式开关，控制「是否真的写盘」 |
| 全局隐式状态 | 模块级变量记住「上次谁加载过什么」，供后续解析兜底 |
| 进程级设施住在门面文件里 | GC 策略、活实例注册表挂在引擎类同文件 |
| 一个模块横跨全部子系统 | 4000 行的命令面覆盖所有子系统，等于第二套 API |

## 5.5 写作纪律

1. **所有结论带 `file:line`**；读不到就写「未读」，不推断。
2. **事实与判断分开**（「它这么写」vs「我认为这不对」）。
3. **量化优先**：写「283 处静默 except / 60 个文件」，不写「很多静默失败」。
4. **未覆盖必须列明**：审了 93 个文件就写清哪些没逐行读。
5. **自我更正要留痕**：发现自己写错，改正文并在注里保留错误原文（不删）。
6. **图要能被 diff**：用纯文本（Markdown/Mermaid），不要截图。

## 5.6 产出清单（一次完整架构梳理应交付什么）

| 产出 | 内容 |
|---|---|
| 目录树 | 仓库根 + 主目录（每个文件行数/职责）+ 非源码目录 |
| 全景图 | 分层 8~13 个节点 |
| 装配图 | 「一个类由 N 个文件拼成」这类结构 |
| 主链路图 ×3 | 打开/加载、一帧、构建发布 |
| 时序图 ×2 | 两条关键流程的逐步调用 |
| 节点表 | 功能 → 文件（行数）→ 出入边数（由图的边自动统计） |
| 文件清单表 | 按功能簇归组，97 个文件逐个标行数 |
| 职责归属表 | 职责 / 位置 / 本职 / 判断 |
| 有意不统一清单 | 哪些差异是取舍而非缺陷（附代码里的论证） |

> 维护纪律：代码变了图要跟着变；**图的价值在「职责表」和「未核实清单」，不在结论**。

# 第六部分 第五层：可执行的门（把「我觉得对齐了」变成「跑一次就知道」）

## 6.1 四层验证，各管一段

| 层 | 目的 | 特点 |
|---|---|---|
| **冒烟** | 产物能不能起来 | 快、粗、每次必跑；不通过就不谈别的 |
| **回归** | 已有行为有没有被改坏 | 全量、可重复、必须全绿；数量本身就是资产 |
| **测量** | 性能/像素/体积等数值指标 | 有阈值、有基线；基线不许在修 bug 时漂移 |
| **一次性探针** | 回答某个具体问题（不改生产代码） | 用完即弃；结论要写回账本，否则下次重做 |

## 6.2 门的四种形态

| 形态 | 做法 | 适用 |
|---|---|---|
| **对拍（差分）** | 两个来源/两条路径的结果必须逐项相等 | 「包=代码」、两个后端、两套实现、迁移前后 |
| **有牙（能红）** | 人为把被修的东西改回坏状态，门必须失败 | 每条新测试/新门都要做一次「修前必红」 |
| **矩阵** | 维度相乘（后端 × 场景 × 设置 × 路径），逐格填结果 | 任何「两端/多路径应当一致」的要求 |
| **快照** | 哈希/像素/序列化文本逐值比对 | 输出稳定性、格式兼容、二进制卫生 |

## 6.3 三条硬纪律

1. **修前必红**：新增的测试/门，先在「未修复」状态跑一次，确认它真的会失败，再跑「已修复」确认转绿。
   不做这一步，「新测试通过」可能只是因为它什么都没测。
2. **修缺陷不许移动基线**：改的是状态机/渲染路径时，最容易顺手把像素/性能基线改了。基线不动才算「只修了缺陷」。
3. **数字必须真跑**：不写「约」「大概」；跑不了就写「推算」并注明推算依据；口径变了要写清「旧口径假红 → 新口径真绿」。

## 6.4 留痕清单（这四项最容易被吞掉）

| 要留痕的 | 为什么 |
|---|---|
| **跳过**的项 | 跳过本身要被审计（同 3.2.3） |
| **未验证**的项 | 「未核」必须写成「未核」，不能写成「查不到」 |
| **口径变化** | 过滤器/统计方式改了，前后数字不可比，必须写明 |
| **判断依据** | 为什么判它是缺陷/不是缺陷，证据是什么 |

# 第七部分 第六层：版本与节奏纪律

## 7.1 一个版本只做一类事

| 版本类型 | 内容 | 纪律 |
|---|---|---|
| **扫尾版** | 只修设计失误/缺陷，零新功能 | 不接受「顺手加个小功能」；验收看「差异清零」 |
| **功能版** | 只加功能，不重构地基 | 验收看「功能矩阵」；地基问题登记到下一轮 |

混合版（功能 + 修补同批）的代价不是工作量，是**验收面翻倍**：功能和修补互相干扰，最后分不清「这个变化是功能带来的还是修 bug 带来的」。
实测教训：一次混合版收尾时，修完还要重出包、重指发布标签、重写说明 —— 全部是混合带来的额外成本。

## 7.2 依赖顺序优先于功能排序

排期时先问：「这个功能卡在哪个地基项上？」

| 功能类型 | 通常卡在 |
|---|---|
| 渲染类新功能 | 渲染状态契约、后端门面收敛（否则每个功能写两遍） |
| 数据/格式类功能 | 序列化/契约模块化（否则每条入口各写一遍迁移） |
| 任何新 API | 公共 API 契约（否则新 API 只在一个后端存在） |

**先做功能 = 在会分叉的基础上再分叉一次。**

## 7.3 成本算术

把登记表里每项的估时**直接相加**，判断一个周期装不装得下。
装不下时，不是「加班」，而是**二选一**；选哪个由人类定，AI 只负责把算术和依赖摆出来。

## 7.4 登记制度

1. **只存在于对话里的计划视为未登记** —— 必须落盘。
2. **取消也留痕**：写「已取消 + 理由」，不删行。
3. **人类裁决原文留痕**：引原话，不改写；后续若被推翻，保留原文并注明「已作废」。
4. **行内原文不篡改**：口径变了，在标题/注里说明，不回去改历史行。

# 第八部分 一页速查

## 8.1 开工前

- [ ] 路线由人类显式选定（不是 AI 默认）
- [ ] 白盒契约已确认：接口/前后条件/不变量/错误模型/资源边界
- [ ] 验收门已定义（对拍？有牙？矩阵？快照？）
- [ ] 本版本定位单一（扫尾 or 功能）

## 8.2 写实现时

- [ ] 只依赖契约，不碰别人的内部字段
- [ ] 失败必须可见（不静默）
- [ ] 边界/非法输入按人类定义好的策略处理

## 8.3 自审时（按第三部分）

- [ ] 粗筛有清单 + 跳过登记
- [ ] 每项走完反手 + 正手，8 段式齐全
- [ ] 有 `UNKNOWN`（没有就是放水）
- [ ] 修复后重跑了验证命令

## 8.4 派第三方审核时（按第四部分）

- [ ] **一个组件一个代理**（环境允许则并发）、只读、单一切片、给了核对清单
- [ ] 并发时做了交叉复核（同结论双证 / 矛盾项自己核或交人类）
- [ ] 要求 file:line + 未核实清单
- [ ] 拿到报告后逐条标 `确认/推翻/未核`

## 8.5 交付前

- [ ] 冒烟 + 回归 + 测量 + 对拍 全绿
- [ ] 新门做过「修前必红」
- [ ] 基线未漂移
- [ ] 文档/图与代码同步
- [ ] 未覆盖项、未核实项、跳过项都写清了

## 8.6 交接时

- [ ] 架构三层视图（目录树/关系图/职责表）
- [ ] 当前状态与下一步（可执行，不含「待定」）
- [ ] 裁决原文与作废项

# 第九部分 能保证什么、不能保证什么（含「AI 审 AI」的边界）

| 层次 | 能提高 | 不能保证 |
|---|---|---|
| 契约层 | 语义可判定、边界有策略 | 规范本身正确 |
| 验证层 | 采样分布上对齐、防硬编码、暴露接口组合问题 | 全称正确、并发全交错、资源耗尽全行为 |
| 自审层 | 结论可复现、自我合理化被流程对冲 | 同一模型盲区仍在 |
| 第三方审核 | 扩大搜索面、交叉验证 | 审核结论本身正确（必须复核） |
| 架构文档 | 降低理解成本、让职责错位可见 | 不产生正确设计，只暴露设计 |
| 运行时 | 最后防线、可观测可回滚 | 不能替代测试与形式化 |
| 人类决策 | 路线、取舍、风险承担 | 不能替代实现工作量 |

# 第十部分 成熟度分级（合并两套，并补两个维度）

## 10.1 验证成熟度（原 L0–L7）

| 等级 | 内容 |
|---|---|
| L0 | 固定用例测试 |
| L1 | 隐藏随机合法输入验证 |
| L2 | 隐藏非法与边界输入验证 |
| L3 | 接口契约与组合验证 |
| L4 | 对抗搜索与反例回归 |
| L5 | 关键路径形式化 |
| L6 | 运行时监控与自动回滚闭环 |
| L7 | 人类路线决策权被显式保留，AI 仅辅助不替代 |

## 10.2 自审成熟度（原 A0–A7）

| 等级 | 行为 |
|---|---|
| A0 | 直接给结论，无过程 |
| A1 | 有粗筛清单，无阶段二 |
| A2 | 有证真链，无证伪链 |
| A3 | 双向链但链不完整（缺路径枚举/最小复现/可审计措辞） |
| A4 | 完整双向链 + 矛盾检测 |
| A5 | A4 + 探针机制 + 三次升级人类 |
| A6 | A5 + 白盒层推广 + 人类裁决格式规范 |
| A7 | A6 + 跳过留痕 + 自我合理化清单作为审计项 |

> 多数 AI 自审产物处在 **A0–A2**。升到 A4 的关键是把「证伪」显式化，并把「矛盾检测」跑出来。

## 10.3 本文新增的两个维度

| 维度 | 低 | 高 |
|---|---|---|
| **独立审核（R）** | R0 无第三方；R1 派了但未复核；R2 派了且逐条标确认/推翻/未核；R3 R2 + 审核错误类型被记录成检查表 |
| **架构可读性（D）** | D0 无图；D1 只有目录树；D2 目录树 + 关系图；D3 D2 + 职责归属表 + 有意不统一清单 |

# 结语

这套东西不产生「正确的设计」，它只做三件事：

1. **让 AI 的实现可被判定**（契约 + 验证 + 门）；
2. **让 AI 的结论可被审计**（自审流水线 + 第三方复核）；
3. **让工程本身可被理解**（架构三层视图 + 职责归属表）。

设计对不对，仍然由人类判断。AI 能做的是：把判断所需的证据摆整齐、把该跑的验证跑完、把该留的痕留下、把不确定的项如实标出来。

> 最终口号（合并两文）：
> **合法域随机测正确性，边界带随机测健壮性，接口缝随机测组合性，隐藏 oracle 防过拟合，对抗搜索找反例，关键路径形式化，运行时做最后防线；**
> **自审走粗筛—双向—实操，结论附 8 段链，UNKNOWN 不许为零；第三方独立复核，审核结论也要被复核；架构画成可读的图，职责摊开成表；路线由人类掌舵。**
