# 功能补全 5 档施工路线图（2026-10-17 · 决策落定版）

> 性质：施工指导文件。规定「补哪些功能、按什么顺序补、每步怎么测」。
> 制定依据：用户定案「骨架+血肉并行，对标 Unity，按 80% 中型游戏会用到的功能优先补齐」。
> 分档原则：按实际使用频繁程度分 5 档；档内按依赖树基座优先 + 同层按实现难度由难到易；
> 档内每功能只做崩溃冒烟测试，档末做完整模拟测试（正常/极限/非法/畸形/Unity 对齐）。
> 基线：已完整的功能见附录 A，不重复施工。

---

## 〇、总则

### 0.1 五档定义

| 档位 | 使用频率 | 判定标准 |
|---|---|---|
| 第 1 档 | 极高频 | 几乎所有类型游戏都会用到；缺了做不出像样的游戏 |
| 第 2 档 | 高频 | 大多数游戏会用到；缺了游戏体验明显打折 |
| 第 3 档 | 中频 | 相当一部分游戏会用到（取决于游戏类型）|
| 第 4 档 | 低频 | 特定类型游戏才用（载具、布娃娃、开放世界）|
| 第 5 档 | 极低频 | 可延后，或在脚本层实现即可 |

### 0.2 档内排序规则（用户 D1 决策确定）

**第一优先：依赖树基座优先。** 若功能 A 依赖功能 B，则 B 必须先于 A 施工。被依赖的功能是依赖树节点上较高的基座，优先施工以尽早解锁依赖链。

**第二优先：同一依赖层级内按实现难度由难到易。** 难度判断依据：改动文件数、是否触及热路径、是否需要新 DLL 接口、是否需要新建子系统。

**冲突处理**：若难度排序与依赖关系冲突，**依赖优先**。在文档中显式标注「依赖优先调整」以便追溯。

### 0.3 测试策略（两阶段）

**阶段一：档内冒烟测试（每个功能做完立刻做）**
- 只测一件事：**引擎能正常启动、不崩溃**
- 方式：启动编辑器 → 加载默认场景 → 进出播放 → 退出；无异常即通过
- 不做：功能正确性、边界、性能
- 目的：快速定位「是谁把引擎搞崩了」，避免攒到最后一起排查

**阶段二：档末完整测试（一档全部做完后做）**
- 模拟真实用户操作：按该档功能的典型使用场景，走一遍完整流程
- 极限数值：最大值、最小值、0、负数、超大数、超长字符串
- 非法数值：类型错误、空值、越界索引、不存在引用
- 畸形数值：NaN、Infinity、Unicode 特殊字符、超长嵌套
- Unity 对齐：同一操作在 Loom 与 Unity 2022.3 LTS 中的表现是否一致
- 目的：确认这一档功能真正可用，而非「勉强能跑」

### 0.4 每档施工纪律

1. 开工前 git commit 一次（回退锚点）
2. 每完成一个功能：冒烟测试 → 通过则 commit → 进入下一个功能
3. 档内全部完成：完整测试 → 全部通过则 commit 并更新台账 → 进入下一档
4. 任何一步失败：git checkout 回退到该功能开工前，不硬撑
5. 探针放 tests/_tmp/，永久保留

### 2.2 排序说明（依赖优先调整记录）

- **序 1 Layer/Tag 排最前**：它是 LayerMask（序 14）、Raycast（序 16）、Trigger（序 17）的共同基座。按用户 D1 决策「依赖优先」，提前到所有依赖者之前。虽然其难度中等，但基座优先原则覆盖同层难度排序。
- **序 2 AudioListener 排第二**：它是 3D 距离衰减（序 15）的基座。同理优先。
- **序 3~13 无依赖功能按难度由难到易**：Canvas/UI 最难（新建子系统）→ 协程 → 事件系统 → SendMessage → 生命周期 → 对象查找 → 聚光灯 → FixedUpdate → LateUpdate → 执行顺序 → 天空盒最简单。
- **序 14~15 一级依赖层**：LayerMask 依赖 Layer/Tag；3D 距离衰减依赖 AudioListener。
- **序 16~17 二级依赖层**：Raycast/Trigger 依赖 LayerMask。

### 2.3 特别标注

**序 16 Raycast 涉及 physics.dll 接口扩展**：需先检查 ABI 契约（loom_module.h）是否支持新增导出，若需扩 ABI 主版本会破坏兼容性。**施工前先做 ABI 兼容性检查，若需破坏性变更，停下来交用户决策。**

**序 3 Canvas/UI 参考对象**（D4 决策）：设计时参考 Unity UGUI（Canvas + RectTransform + LayoutGroup）、Godot Control 节点、React Flexbox 布局算法。不重复造轮子，只做「适配 Loom 的最小实现」。

### 2.4 档末完整测试场景

- **模拟场景**：第一人称迷宫小游戏——玩家移动、捡金币（Trigger）、开门（Raycast 点击 + 动画）、HUD 显示金币数（Canvas/UI）、背景天空盒、脚步声（3D 衰减）、手电筒（聚光灯）、金币用事件系统通知 UI、开门用协程做渐变动画

### 3.2 间隙任务：后-B7b-1 绑死模式开发后门（D7 决策）

**定位**：独立小任务，穿插在第 2 档间隙（建议在序 5 之后、序 6 之前做），不占正式功能序号。

**设计（用户 D7 决策细化）**：

1. **新增模块常量**：在 core_clock.py 顶部定义
   - 「_DEV_ENABLE_LEGACY_BINDING = False」——默认 False，锁定绑死模式
2. **用户层/制作人层屏蔽**：
   - 设置.json 中 logic_fps<=0 时，若常量为 False → **启动报错**「logic_fps 必须 > 0」，并回退默认 30
   - GUI 设置面板、EAI 命令、MCP 工具均**无法设置 logic_fps<=0**（校验拦截）
3. **开发者后门**：
   - 只有手动把源码中「_DEV_ENABLE_LEGACY_BINDING」改为 True 并重新编译/运行，才能触发绑死模式
   - 绑死模式代码路径（loom_render 的 else 分支、scene_driver 的 else 分支）**保留不删**，作为测试对照基线
4. **防作弊语义**：
   - 玩家改配置文件无法开启绑死模式（常量锁定）
   - 联网游戏中不存在「改配置导致机制大变」的作弊后门
   - 测试人员要对照绑死模式时，改代码常量即可

**验收**：
- 常量=False 时：配置 logic_fps=0 → 启动报错；GUI/EAI/MCP 设置 logic_fps=0 → 被拦截
- 常量=True 时：配置 logic_fps=0 → 进入绑死模式（测试基线可用）
- 探针：tests/_tmp/verify_legacy_binding_locked.py（断言常量 False 时配置路径被拒）

**风险**：修改 core_clock.py 的 split_enabled / clock_from_settings 两处判定逻辑，需确保常量=True 时行为与现在完全一致（逐位对拍）。

## 七、跨档注意事项

### 7.1 第 1 档序 16 Raycast 的 ABI 检查（D3=A 衍生）

Raycast 走 physics.dll C 化路线，需在 physics.dll 新增「射线-三角形求交」导出函数。施工前必须检查：
- loom_module.h 的 ABI 版本规则（主版本破坏性、次版本兼容）
- 新增导出是否影响现有 6 个必需导出
- 是否需要扩 LOOM_TENSOR 结构或新增结构体

**若需 ABI 主版本变更，停下交用户决策。**

### 7.2 第 3 档骨骼动画的 pipeline 接口调研（D8）

骨骼动画需要：
- 骨骼矩阵上传通道（GPU buffer 或 uniform 数组）
- 蒙皮着色器槽位
