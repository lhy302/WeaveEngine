# 设计：场景版本判定与升级的模块分离（beta7 P0）

> 触发：人类提问「场景版本检测/升级是不是被高耦合进引擎了？会不会让这个功能在以后版本里混乱？」
> 结论：**是，而且已经出问题了**——不是「将来会乱」，是**现在就有两条路径漏迁移**（实测见 §3）。
> 因此建议 beta7 把「场景契约（版本判定 + 迁移）」独立成模块，并把**所有打开场景的入口**收口到它。

---

## 1 现状：版本知识散落在 6 个地方

| 位置 | 职责 | 行数 |
|---|---|---|
| `Loom/sceneio.py:66` | `SCENE_VERSION = 12`（单一事实源） | — |
| `Loom/sceneio.py:160-198` | `check_engine_version()` 引擎版本闸门 | 39 |
| `Loom/sceneio.py:2116-2193` | `migrate()` 版本迁移（v1→v12 各段） | 78 |
| `Loom/sceneio.py:2026-2033` | `scene_from_dict()` 里**唯一**调用 `migrate()` 的位置 | — |
| `Loom/editor.py:1241-1246` | `_load_scene()` **自己又调一遍** `check_engine_version` | 6 |
| `Loom/scene_driver.py:623-628` | VK 播放器 `load_from_data()` **再调一遍**闸门，但**不调 migrate** | 6 |
| `LoomHub/hub_config.py:786-796` | Hub 新建场景时 `import sceneio` 取 `SCENE_VERSION` | 11 |
| `Loom/run_player.py:269-300`、`loom_player_window.py:52-81`、`build_entry.py:439-444`、`agent_commands.py:547-549` | 版本错误的**呈现**（弹窗/退出/日志）散在 4 处 | — |

`sceneio.py` 总长 **2378 行**，除版本/迁移外还装着：资产身份层（guid/资产库）、材质、相机、UI、天空盒、Prefab、对象图校验、明文/混淆读写。版本逻辑被这堆东西包着。

已有一个「半分离」先例：`tools/migrate_scene_assets_v11.py`（v11 资产 guid 的一次性迁移脚本，在引擎之外）。它证明「迁移可以离开引擎单独跑」，但它**只覆盖资产段**，且不是所有打开路径都会经过它。

## 2 结构性问题（不是审美问题）

1. **闸门重复三处，迁移只有一处** —— 三处各自实现，行为已经分叉（见 §3）。
2. **迁移藏在 GPU 侧的加载函数里**：`migrate()` 由 `scene_from_dict()` 调用，而 `scene_from_dict()` 是「把 dict 灌进 Engine 实例」的函数。任何不走 Engine 的消费者（VK 数据层、打包器、Hub）都拿不到迁移。
3. **`migrate()` 是纯函数**（只吃 dict、吐 dict、不改外部状态）—— 这恰好说明它**本来就不该待在** `scene_from_dict` 里：纯数据变换被绑在了有副作用的对象装配流程中间。

## 3 实测：两条路径漏迁移（本轮新增缺陷 B15）

同一份 v8 场景（v8 的相机 `yaw/pitch` 是**弧度**，v9 起改**度**）：

```python
data = {'version': 8, 'objects': [], 'active_camera': 'c1',
        'cameras': [{'id':'c1','name':'Cam','yaw': math.pi/2, 'pitch': 0.0, 'fov': 60.0}],
        'lights': []}
```

实测输出（`py -3.13`，`LOOM_NO_DIALOG=1`）：

```
migrate(v8):        version=12   camera_yaw=90.0            <- 度制，正确
SceneDriver(v8):    version=8    camera_yaw=1.5707963       <- 仍是弧度，未迁移
```

即：**同一份老场景，GL 路径相机朝向 90°，VK 路径朝向 1.57°**（差 88.4°）。

可达性（不是理论）：

| 路径 | 是否迁移 | 证据 |
|---|---|---|
| 编辑器打开场景 | ✅（`scene_from_dict`） | `editor.py:1265` |
| GL 播放器 / GL 打包游戏 | ✅ | `runtime.py:148` → `scene_from_dict` |
| **VK 播放器**（`--backend vulkan`） | ❌ | `vk_player.py:321-328` → `scene_driver.load_from_data` |
| **VK 打包游戏**（默认后端就是 vulkan） | ❌ | `game_player.py:159` 默认 vulkan；`build_game.py:394` 原样入包不迁移 |
| Hub 新建项目 | 只写当前版本，无老数据 | `hub_commands.py:406` |

而且 VK 路径 `data['version']` 加载后**仍是 8**（不会抬到 12），任何后续按版本判断的分支都会走错。

## 4 建议形态：`loom_scene_contract.py`（纯数据，零 GPU 依赖）

```
CURRENT_VERSION = 12
class SceneVersionError(ValueError)         # 从 sceneio 迁出（保留 re-export 兼容）
def gate(data, engine_version=None) -> True  # 引擎版本闸门（现 check_engine_version）
def migrate(data) -> (data, steps)           # 纯函数；返回实际执行了哪几步（可观测）
def prepare(path_or_dict, engine_version=None) -> (data, report)
    # 唯一入口：读盘(明文/LOOMSC) -> gate -> migrate -> 打标 data['_normalized']=CURRENT_VERSION
    # report = {from, to, steps:[...], rejected:reason|None}
```

约束：

- 只允许依赖 `json/os/math`（**不许** import mesh/numpy/引擎任何东西）—— 这条本身就是「能单独跑」的证明；
- 每步迁移拆成独立小函数（`_v3_lights`、`_v4_scripts`、`_v8_to_v9_camera_deg` …），可单独测；
- `sceneio` 保留 `SCENE_VERSION = contract.CURRENT_VERSION` 的 re-export，`migrate`/`check_engine_version` 变成薄包装（不破坏现有调用点与测试）。

## 5 收口：所有「打开场景」的入口都必须先 `prepare()`

| 入口 | 现状 | 改造后 |
|---|---|---|
| 编辑器打开 | 自调闸门 + `scene_from_dict` 内迁移 | `prepare(path)` → `scene_from_dict(data)` |
| 编辑器新建 | 写当前版本 | 不变（但走 `contract.CURRENT_VERSION`） |
| 编辑器播放（切场景） | 内存 dict | `prepare(dict)`（幂等，标记已规范化则直通） |
| GL 播放器 / GL 打包 | `load_scene_data` → `scene_from_dict` | `prepare(path)` → `scene_from_dict` |
| **VK 播放器** | **无迁移** | `prepare(path)` → `load_from_data` |
| **VK 打包游戏** | **无迁移** | `prepare(pack_dict)` → `load_from_data` |
| `build_game` 打包 | 原样入包 | `prepare()` 后入包（老项目打成新包 = 已规范化） |
| Hub 新建项目 | import sceneio 取版本号 | import `loom_scene_contract` 取版本号（不拖引擎） |

## 6 强制手段（不靠自觉，靠门）

1. **入口断言**：`scene_from_dict()` 与 `SceneDriver.load_from_data()` 开头断言 `data.get('_normalized') == CURRENT_VERSION`，否则 `raise`（测试/开发构建）或「告警 + 就地补做」并打点（发布构建）。这样任何新增旁路会**立刻红**，而不是静默错。
2. **路径覆盖测试**：枚举「打开场景」的入口（编辑器/GL/VK/打包/游戏包/Hub 各一条），每条喂同一份 v1/v8/v11 老场景，断言最终 `data['version'] == CURRENT_VERSION` 且关键字段已转换（相机度制、lights 默认值、scripts 数组化）。
3. **迁移链全量测试**：v1..v11 每档一个夹具 → 断言 `steps` 与结果；同一夹具跑两次结果相同（幂等）。
4. **禁止旁路**：加一条静态检查（沿用 `tools/` 现有 lint 风格）——`sceneio.load_scene_data` / `json.load` 出现在场景打开路径上而没经过 `prepare` 即报错。

## 7 收益（回答「为什么值得拆」）

| 收益 | 具体 |
|---|---|
| 修 bug 只动 1 个文件 | 以后发现「某档老场景转换错」，只改 `loom_scene_contract.py`，不碰渲染/资产/UI 代码 —— 正是人类担心的「更新一大片本不需要改的编译产物」 |
| 迁移可被独立验证 | 现在只能靠 `scene_from_dict` 间接测；拆出后可对纯 dict 做 v1→v12 全链路断言 |
| 漏路径自动暴露 | 入口断言 + 覆盖测试 = 新加的打开方式必须过契约，不能忘 |
| Hub 可单独用 | Hub 新建场景/校验老场景不必 import 引擎 |
| 与「打包=已规范化」一致 | 老项目打成新包时在打包期就规范化，玩家端不再依赖运行期迁移 |

## 8 对「不分离也能凑合」这类意见的逐条回应

> 口径澄清（人类 2026-11-16）：提问的本意是**「分离是否合理」**，不是要求论证「保持现状」。
> 所以本节不是替某个「保持现状」的方案辩护，而是把「不分离」可能被提出的理由逐条摆出来、逐条给证据 —— 结论仍是分离。

| 「不分离」的常见理由 | 为什么不成立 |
|---|---|
| 「`migrate()` 已经是纯函数，够干净」 | 纯函数放对了，**位置**没对：唯一调用点在 `scene_from_dict` 里，于是 VK/打包两条路拿不到（§3 实测） |
| 「闸门只有一处也行，多调几次无害」 | 已经三处，且三处行为已分叉（VK 只闸不迁） |
| 「拆分会让版本常量有两个来源」 | 相反：拆分后 `sceneio.SCENE_VERSION` 变成 re-export，来源**只剩一个**；现在是 Hub 通过 `import sceneio` 绕一大圈拿同一个数 |
| 「beta7 排期紧」 | 本次拆分是**搬家**（代码量不增），估 4-6 人天；不做的话 §3 的缺陷要么留在 VK 路径，要么在 beta7 各处再打补丁 |

## 9 验收门

| 门 | 判据 |
|---|---|
| S1 一致 | 同一份 v1/v8/v11 夹具，编辑器 / GL / VK / 打包游戏 四条路径加载后 `data['version'] == CURRENT_VERSION` 且相机 yaw 全为度制、值相等 |
| S2 有牙 | 把 §3 的 VK 迁移修复回退 → S1 必须红（证明门不是摆设） |
| S3 无旁路 | 入口断言开启后，全量测试 139+ 个文件 0 失败（说明没有别的地方偷偷传未规范化数据） |
| S4 幂等 | 同一夹具 `prepare()` 两次，第二次 `steps == []` 且数据不变 |
| S5 零依赖 | `loom_scene_contract.py` 的 import 图里不含 numpy/引擎/渲染模块（用 `python -X importtime` 或 AST 断言） |

## 10 未验证 / 风险

1. `build_game` 打包期规范化会**改写**老项目进包的数据（版本抬到 12）。语义上正确，但需要确认「打包不改源场景文件」（只改内存副本）——现有代码是 `load_scene_data` 读入内存，改的是内存对象，落盘只在 `pack()` 里，风险低但需一条测试钉死。
2. `_normalized` 标记是新增字段：写盘时必须**剔除**（否则污染场景文件），且要兼容「第三方手写的场景带了这个键」→ 需要 `_strip_internal_keys()` 并在读入时覆盖。
3. VK 数据层是否有自己的字段级兼容逻辑（绕过 `migrate` 的隐性等价物）——本轮只验证了相机 yaw 一处，其余字段（lights 默认值、scripts 数组化、parent_id）在 VK 路径是否同样缺失**未逐一验证**；拆分时按 S1 全字段比对补齐。
