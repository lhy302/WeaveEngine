--------------------------------------------------------------------
〇、写在最前 — 为什么做 DLL 化 (一句话)
--------------------------------------------------------------------
Python 本身不适合高性能场景 —— 这是两个月性能战役反复证实的底层事实:
- 播放态 (混合500, TPS20) 主线程独占 65% 单核算力, 其余 60 线程全 <3%,
  全机 2.3 核当量 / 18 核 (87% 算力闲置), GPU 从编辑态 97% 跌到播放态 54%
- 根因 = GIL: 逻辑帧与渲染帧同线程串行 (advance_logic 在 paintGL 帧内调),
  帧内流水线 (physics_pipe v2) 已经做了能做的
- 期1 NgilPool (gather 池, world_matrices 段外包) 验收全绿但相对 DLL 化是
  "GIL 墙内腾挪" — 收益上限=主线程计算 730ms/s → ~250ms/s, CPU>GPU 转变
  做不到
⇒ DLL 化 = 拆墙: 热路径核心组件用 C ABI DLL 实现, Python 只做基座
(调度/编辑/场景/脚本层), 原生产物无 GIL, 天然吃满多核。
战略定性 [v1.1, 补漏报告合流]: 本战役第一目标 = 工业级稳定性 (崩溃物理
隔离在 DLL 边界: 访问违例崩掉当前帧 DLL 调用, 基座捕获后回退软备胎,
引擎进程不退出) + 消灭 Python 胶水层的不可预测崩溃/GIL 卡死/调试困难;
性能提升是顺带红利。引擎无正式版/无社区/无存量兼容包袱 → 不是"迁移"
而是"趁地基未盖楼直接换承重墙"的终局手术, 最大的敌人不是"怎么拆",
而是"拆的时候别把自己困死" — 故 M1 即建自愈/模糊测试/崩溃落盘三闸。

一、用户构想完整版 (九点, 语言错误已修正, 精神原样)
--------------------------------------------------------------------
1. 【基座=Python, 只写挂载+调度】:
   引擎只写一个基座, 挂载所有核心组件。渲染、游戏内逻辑等等本质上都是
   一个个功能、一个个函数, 它们耦合的地方只有函数的接口。只需要定义
   接口长什么样、应该出来的数据长什么样、函数间怎么互相传递数据、函数
   从哪里获取数据 —— 这些东西的内部实现没人在意。
2. 【DLL 即最好的模块化】:
   将这些函数全部拆分、打碎成一个个 DLL (操作系统本来就给软件提供 DLL
   及其对应 API 接口作为运行环境基石), 互相依赖、互相传输数据, 接收
   数据完成下一步计算再继续传递数据。为何模块化要限于一个个 .py 文件?
   DLL 本身就是最好的模块化: 接收数据、处理、吐出数据, 为下一个 DLL
   提供数据和依赖。
3. 【接口契约=换模块的代价】:
   接口和数据传输协议定义后, 哪个模块写的不好想重写, 只用替换那个 DLL
   即可。没人关心 DLL 内部用什么语言写的 —— 可以是 C、可以是 C++、可以
   是任何语言, 只要符合接口数据要求都能接入。
4. 【核心组件=积木】:
   核心组件不能只替换, 也能像搭积木一样增加几块 (新功能块), 只要明确
   写明了调用了哪些其他 DLL 和基座的接口、并且提供了哪些接口就行。
   调用系统的接口不用写出来。
5. 【核心组件注册表 (替换机制)】:
   专门放一个核心组件文件夹, 建立核心组件注册表。引擎能检测到文件夹内
   的插件, 但都不替换、不启用; 只有在引擎内明确启用 (顶替了注册表里
   原来那个核心组件的位置; 顶替默认所有接口保持一致, 也可以写出有没有
   多增加接口) 才启用。如果替换组件导致引擎崩溃, 崩溃后基座自动把坏
   DLL 从注册表里删掉, 替换回官方 DLL。
6. 【插件注册表 (同类机制)】:
   普通插件也是类似的逻辑, 一样采用注册表机制, 必须写明调用了哪些 DLL
   的接口。注册表机制是方便自由组装整个引擎的, 全部注册表化可以方便基座
   组装修改后的引擎: 按照先核心、后插件的步骤组装。核心插件坏了自动还原
   成官方版本; 插件加载失败自动从引擎中弹出。注册表写明了有哪些接口,
   也方便基座判断各个接口是否合法和正确, 让整个引擎更稳定 —— 如果调用
   了失败的接口, 可以自动去掉插件提示"此插件加载失败", 保住整个引擎
   不崩, 而不是在组装引擎阶段崩溃后后置修复。
7. 【三层分权 (核心组件/普通插件/游戏脚本)】:
   核心组件只使用 DLL (基座调度接口 + 直接与系统交互); 普通插件只能以
   脚本形式接入核心组件 DLL 为其提供的接口 (能用什么接口取决于 DLL 提供
   了什么); 游戏脚本跟专门的脚本 DLL。普通插件和脚本都属于脚本类, 但
   插件跟随其对应的 DLL, 脚本跟随专门的脚本 DLL (引擎内物体运动类脚本
   接口)。这样普通插件权力是否越界的问题, 就变成 DLL 内部如何执行脚本
   和防护的问题 —— 威胁不会一层层传递。
8. 【封装游戏 = DLL 拆装】:
   封装游戏变得容易: 封装时只要拆掉所有编辑器 DLL, 保留播放器 DLL 即可。
   无编辑器 DLL = 自动游戏模式 (模式判定=装配问题, 不是代码分支)。
9. 【GUI = 独立 DLL + 双向注入】:
   GUI 也单独一个 DLL, 留下编辑器 DLL 注入接口: 注入了编辑器 DLL 就按照
   编辑器模式运行, 没注入就按照播放器自动变成游戏模式。GUI 按钮、
   边缘按钮都由 DLL 注入 (和之前那个插件可定义按钮一样)。编辑器 DLL 能
   注入按钮和自行编辑编辑栏 GUI 的能力, 编辑器 DLL 预留播放器 DLL 注入
   功能按钮传给 GUI 的接口 —— 做到所有按钮都能自定义。

三、目标架构
--------------------------------------------------------------------
┌─ 基座 Python (Loom) ────────────────────────────────────────┐
│ Qt 编辑器/GUI · EAI · 场景IO · 插件加载器 · 注册表组装器 · 编排 │
│ 用户脚本层 (Python 生产力层, 方括号内=调 DLL 接口)              │
└──────────────┬──────────────────────────────────────┬──────┘
        C ABI 契约 (唯一耦合点)                (系统交互直连: GPU/文件/音频)
               │                                        │
┌──────────────┴──────────────────┬─────────────────────┴──────┐
│ pipeline.dll 帧循环               │ physics.dll (Jolt 封装)      │
│   (物理子步调度/碰撞/逻辑prep)      │ audio.dll (miniaudio 封装)   │
│ render_prep.dll 渲染侧预计算       │ ckernels.dll (AABB/对偶, 已有)│
│   (interp 矩阵/桶组装/阴影VP)      │ gui.dll (Qt GUI 壳)          │
│ script.dll 脚本执行+防护边界       │ editor.dll (注入区)          │
└──────────────────────────────────┴─────────────────────────┘
     ↑ 核心组件池 (core_components\), 注册表组装, 可替换/积木式扩展
     ↑ 普通插件 (只能经核心组件 DLL 的开出的接口, 注册表+加载失败弹出)
     ↑ 游戏脚本 (只能经 script.dll 的物体运动类接口)

3.1 接口契约 = 纯 C ABI (跨语言唯一稳定契约):
  - extern "C" 函数 + POD 结构体 + 裸缓冲区 (禁止 C++ 类/对象跨 DLL 传)
  - 函数签名: 版本号注册函数 + 能力查询 + 帧步进 + 资源挂接
  - 每个 DLL 头部: LOOM_MODULE_INFO {magic, abi_version, module_id,
    provides[], depends[]} — 注册表按此校验
3.2 内存所有权 = 基座独占帧 arena:
  - 所有帧内缓冲区 (位置/矩阵/AABB/桶等) 由基座预分配 (grow-only 铁律
    沿用), DLL 只收 (指针, 形状, dtype 描述) 裸参数
  - DLL 不 malloc 帧内存; 零拷贝接力 (A 产品的输出= B 产品的输入视图)
  - 例外: DLL 内的私有一次性资源 (物理世界/音频设备/GPU 对象) 归 DLL 管,
    生命周期由显式 init/deinit 契约 (基座启动/退出调)
3.3 帧数据流 + 组装顺序 (用户构想: 先核心、后插件):
  基座(编辑器态/播放态判定)  → 按注册表加载 core_components\
  → 校验接口 (ABI 版本/依赖/冲突) → 失败=弹出+回退官方 DLL (不崩)
  → 加载 plugins\ → 校验 plug 接口声明 → 失败=弹出 (不崩)
  → 帧循环: 基座 `prepare(pipeline.dll)` → `step(physics.dll)` →
    `prep(pipeline.dll)` → `render_prep(render_prep.dll)` →
    `submit(gui.dll)` → `consume_input(...)` → 循环
3.4 播放器/编辑器判定 = 装配判定 (用户构想) :
  - editor.dll 注入 → 编辑器模式 (工具栏/层级/检查器/DLL 注入按钮)
  - editor.dll 缺席 → 播放器模式 (自动游戏, 零编辑器壳)
  - gui.dll 按模式注入资源; 编辑器 DLL 留有播放器 DLL 按钮注入接口
    → 所有按钮可自定义 (沿 _EDITOR_BUTTONS 升格为 DLL 接口)

    回退), 崩溃隔离在模块 (分隔地址空间/崩溃恢复由注册表回退器)
5.3 配套:
  - 攻击面复核: 路径读取/文件写入/网络 — 基座放开, 插件/脚本仅经白名单
  - 信任闸: 新 DLL 首次启用=弹窗确认 (沿用 plugin_loader 的 SHA256 信任

十、开发方向指针 — AI 时代的工具观 (2026-09-08 用户追加)
--------------------------------------------------------------------
定位: 北极星, 高于性能目标 (性能是手段, 方向是目的)。与第一章用户
  构想九点同源 — 注册表/积木式扩展/按钮注入本就是模组化基因, 本章
  把它提升为整个战役的方向判据。

10.1 用户原话 (修正明显语言错误, 精神原样):
  "AI 时代, 创意的落地是一件很容易的事情, 未来的工具本身允许用户
  自行创造新功能、自行搭建自己的创意才是主流方向。在可以看见的未来
  里, 未来的所有工具都有可能会像 MC (Minecraft) 那样模组化、可自定
  义化, 每个人自由地创造自己专属的工具。所以整个引擎'基座'的开发
  方向应该是: 如何更稳定地承接用户注入的创意, 和方便 Agent 工具的
  操作 — 这可能将成为人人都能造自己专属工具的一个开端。"

10.2 工程解读 — DLL 化架构恰好是这个方向的载体 (不是巧合):
  - 模组化 = 注册表机制本体: MC mod 生态的本质 = 明确接口契约 + 依赖
    声明 + 加载器 + 坏 mod 弹出不拖死游戏; 本战役 core_components/
    plugins 两层注册表 + "先核心后插件"组装序就是它的工程化 — 引擎
    做成"造工具的工具" (平台), 不做单体软件
  - 承接创意的注入梯度 = 三层分权: 普通玩家写 Lua 脚本 (M4 极简运动
    接口) → 进阶用户写插件 (经核心 DLL 开出的接口) → 深度用户替换/
    新增核心组件 DLL (注册表顶替/积木扩展); 门槛逐层抬高, 权力逐层
    放大, 威胁不层递
  - "更稳定地承接" = 自愈三闸的战略重估: M1 模糊测试/Minidump/回退
    软备胎不只保开发期, 是未来每个注入者 (人或 Agent) 失误时的引擎
    保命机制 — 注入从危险操作变成零恐惧常规操作 (MC 装 mod 坏了就
    禁用, 没人心疼), 这才是模组化的精神
  - "方便 Agent 操作" = DLL 化对 AI 工具链的三重红利:
    ① 注册表 = Agent 可机读的能力清单 (provides/depends 显式声明,
      读表即知引擎有什么/缺什么)
    ② C ABI 契约 = Agent 可验证的调用协议 (签名+POD+错误码, 不用猜
      Python 对象图内部 API)
    ③ 自愈回退 = Agent 犯错的安全网 (写坏 DLL/脚本 → 弹出回退, 引擎
      不死, Agent 可以试错)
    EAI 测试体系 (52+16 命令) 已是 Agent 操作引擎的前哨, 沿此加深;
    接口文档/注册表一律"人+AI 双读" (机器可解析+人可读)

10.3 三问校验 (每个架构决策的最终判据):
  ① 这个设计让"注入创意"更容易还是更难?
  ② 这个设计让"Agent 操作"更容易还是更难?
  ③ 这个设计让引擎在"坏注入"下活下来的概率更高还是更低?
  三问不过不放行。与性能目标冲突罕见 (C ABI 显式契约两者兼得); 真
  冲突时方向优先、性能另寻他路, 但 M2/M3 对拍逐位与 FPS 验收不降。

十一、用户原话存档 (保留设计初衷, 防日后忘为什么这么做)
--------------------------------------------------------------------
【原文直录 (修正明显语言错误, 未经润色)】:
"目前引擎遇到的所有问题说白了都是 Python 本身的性能极度拉胯导致的,
Python 本身就不适合高性能场景, 打再多库都是补救而不是解决问题。
我们的引擎应该长什么样? 我的构想是我们只写一个挂载所有核心组件
(渲染、游戏内逻辑等等本质上都是一个个功能、一个个函数, 它们耦合的
地方只有函数的接口), 我们只需要定义这个接口和应该出来的数据是长什么
样、怎么函数间互相传递数据、这个函数从哪里获取数据这些东西就可以了,
这些东西的内部实现没人在意。将这些函数全部拆分、打碎成一个个 DLL
(本质上系统就是给软件提供一个个 DLL 及其对应的 API 接口给软件提供运行
环境基石的), 互相依赖互相传输数据, 并接收数据完成下一步计算再继续
传递数据的。为何模块化要限制于一个个 .py 文件? DLL 本身就是最好的
模块化: 接收数据、处理、吐出数据为下一个 DLL 提供数据和依赖。接口和
数据传输协议定义后哪个模块写的不好想重写只用替换 DLL 就行, 没人关心
DLL 内部使用什么语言写的, 可以是 C、可以是 C++、可以是任何语言, 只要
符合接口数据要求都能接入, 而接入这一切的基座可以使用 Python 编写,
同时这也给如何划分核心组件和普通插件做了很重要的区分。"

【补充论述 (随聊续添, 修正后)】:
"这也很好的区分了核心组件和普通插件的区别: 核心组件只使用 DLL, 而普通
插件只能以脚本形式接入核心组件 DLL 为其提供的接口, 能用什么接口取决于
DLL 提供了什么。DLL 核心组件除了能调用由 Python 写好的底座提供的调度
接口以外还能直接和系统交互, 这样普通插件权力是否越界问题就变成了 DLL
内部如何执行脚本和防护的问题, 威胁不会一层层传递。游戏用的脚本这件事
想了一下: 专门做一个 DLL 提供引擎内物体运动类脚本接口? 或者在操作物体
运动的 DLL 上直接开一个接口? 你完整的梳理一下。目前想到的是普通插件和
脚本都属于脚本类, 但是插件跟随其对应的 DLL, 脚本跟随专门的脚本 DLL。
这样还有一个好处, 封装游戏变得容易, 封装时只要拆掉所有编辑器 DLL
保留播放器 DLL 即可。想了一下 GUI 也单独一个 DLL, 留下编辑器 DLL 注入
接口, 注入了编辑器 DLL 就按照编辑器模式运行, 没注入就按照播放器自动
变成游戏模式, 按钮、边缘按钮都由 DLL 注入 (和之前那个插件可定义按钮
一样)。"

"想了一下核心插件如何替换: 和之前一样专门放一个核心插件文件夹并建立
核心插件注册表, 引擎能检测到文件夹内的插件但都不替换启用, 只有在引擎
内明确启用 (顶替了注册表里原来那个核心插件的位置, 顶替默认所有接口
保持一致, 可以写出有没有多增加接口。当然核心插件不是只能替换, 也能像
搭积木一样再增加几块上去, 只要明确写明了调用了哪些其他 DLL 和基座的
接口并且提供了哪些接口就行, 调用系统的接口不用写出来) 才启用。如果
替换组件导致引擎崩溃, 崩溃后基座自动将坏 DLL 从注册表里删掉替换回
官方 DLL。插件也是类似的逻辑, 一样采用注册表机制, 必须写明调用了哪些
DLL 的接口 (注册表机制是方便自由组装整个引擎的, 全部注册表化可以方便
基座组装修改后的引擎, 按照先核心、后插件的步骤组装; 核心插件坏了自动
还原成官方版本, 插件加载失败自动从引擎中弹出); 注册表机制写明了有哪些
接口也是方便基座判断各个接口是否合法和正确, 让整个引擎更稳定, 如果
调用了失败的接口可以自动去掉插件提示此插件加载失败保住整个引擎不崩,
而不是在组装引擎阶段崩溃后后置修复。"

"GUI 组件保留, 让编辑器 DLL 注入按钮和自行编辑编辑栏 GUI 的能力,
编辑器 DLL 预留播放器 DLL 注入功能按钮传给 GUI 的接口, 做到所有按钮
都能自定义。"

【主要设计后注 (Claude 工程化补充)】:
- 接口契约=纯 C ABI + POD + 裸缓冲; DLL 版本号+依赖声明
- 帧 arena 内存所有权=基座; 零拷贝接力; DLL 私有资源 init/deinit 显式命周期
- 用户脚本层保留 Python (生产力); 脚本/插件只能经 DLL 接口 (威胁不层递)
- 迁移 = 绞杀者模式, 逐里程碑对拍逐位/单堵点/逃生门/稳定区只读
