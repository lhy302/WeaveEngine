## 1 我偏在哪（诚实复盘，带证据）

前面三批（B7-24 契约 + 矩阵门、B7-18/B7-21/B7-26 修复）做的是：
**把两端的差异变得可见、可测，然后逐条追平**。这条路的终点是——

| 我做的 | 终点是什么 |
|---|---|
| B7-24：105 vs 40 的矩阵 + 契约，A 类 40 条「VK 必须补齐」 | **手写 40 个第二实现**，然后永远靠门盯着两边别漂 |
| B7-26：抽 loom_collision 共享派发，但 VK 的配对仍是第二份（朴素 O(n²)） | 语义对齐了，**但仍是两套装配** |
| B7-18/B7-21：VK 侧改一行条件 | 同上 |

**JVM 类比里从来没有「两个 System.out」**。Java 字节码只有一份，JVM 在下面把差别吃掉；用户写
System.out.println 时不关心实现。而我们现在是：**用户看到的是两个类**（GLEngine 105 个方法 /
SceneDriver 40 个方法），脚本写 engine.on_key_event 在 VK 下 AttributeError —— 这就是「受后端影响」。

**具体误判**：我把 on_key_event / on_text_input / on_quit_request 判成了「仅 GL 专属」（契约 §6 C 类），
理由是「VK 由播放器喂」。这恰恰是错的地方：**这三个是宿主/用户的事件入口**，
它不该因为后端不同而存在性不同 —— 应该是「同一个入口，两种喂法，引擎内部屏蔽」。

## 2 目标形状（JVM 模型落到本工程）

```
        ┌──────────────────────────────────────────────┐
        │  脚本 / 内容 / 工具链 / 宿主                     │  ← 只依赖这一层
        │  看到的是**一个**引擎对象，一套事件 API            │
        └───────────────────┬──────────────────────────┘
                            │ IEngineAPI（唯一契约）
        ┌───────────────────▼──────────────────────────┐
        │  引擎内核（唯一实现：场景/脚本/物理/动画/音频/   │
        │  碰撞事件/时钟/输入状态/生命周期）               │
        └───────────────────┬──────────────────────────┘
                            │ RenderBackend（可替换驱动）
              ┌─────────────┴─────────────┐
        ┌─────▼─────┐               ┌─────▼─────┐
        │ GLBackend │               │ VKBackend │   ← 只有这一层知道 OpenGL/Vulkan
        └───────────┘               └───────────┘
```

三条硬要求：

1. **用户可见的成员集合与后端无关** —— 不是「VK 追平 GL」，而是**只有一份**，
   差异在 RenderBackend 之下，用户连 render_api 都不用改代码（只是配置项）。
2. **事件面统一**：宿主入口（键盘/文本/退出/鼠标增量/鼠标锁定）与脚本钩子（on_collision_* /
   on_trigger_* / on_fixed_update / on_late_update / 生命周期）**两端同名同语义**。
   「谁把事件喂进来」是宿主的事（编辑器 GLFW/Qt、播放器、打包游戏），**不是用户 API 的差异**。
3. **差异只允许存在于后端层**：GL 立即模式绘制、VK 的 pass 结构、阴影贴图张数…… 这些归 RenderBackend，
   用户看不见；**不允许**再出现「某个引擎 API 只在某个后端存在」。

## 3 判据要换（这是本次最实质的改动）

| 现在的判据 | 应换成的判据 |
|---|---|
| API 矩阵：两端方法名集合差异 = 0 | **用户视角**：同一份脚本 + 同一份场景 + 同一串输入 → 两端**事件序列与状态序列逐条相等** |
| 像素对拍（test_ab_gl_vk） | 保留（它验的是「同一个后端语义」），但它是**后端层**的验收，不是用户层 |
| 方法存在性 | 方法存在性只是**必要条件**，不是目标；目标是「用户代码零改动」 |

**为什么必须换**：方法名对齐 ≠ 不受后端影响。两端都有 on_key_event，但一个由 GLFW 回调触发、
一个由播放器手动调，用户仍然要写两套宿主代码 —— 那还是受后端影响。

## 5 两个收敛形状（**需要人类裁决**）

### 选项 A：GLEngine 为唯一门面，SceneDriver 降为「数据 + 后端驱动」

- 编辑器 / GL 播放器 / VK 播放器 / 打包游戏 **全部装配同一个 GLEngine**；
- SceneDriver 从「第二个引擎」退化为 GLEngine 内部的一个后端驱动（负责 VK 侧装配与 VkRenderer 调度）；
- 好处：改动面小、编辑器不动、脚本层零改动（脚本本来就按 GL 的 API 写）；
- 代价：GLEngine 变成唯一大对象（它已经是 8 个 mixin 的装配体，继续长）；VK 侧要迁到「被 GLEngine 驱动」的形状。

### 选项 B：抽中立内核 EngineCore，两个宿主都只做「宿主 + 后端」

- EngineCore = 场景/脚本/物理/动画/音频/碰撞/时钟/输入状态（**后端无关**）；
- GLEngine 与 VkEngine 都只是 EngineCore + 宿主循环 + RenderBackend；
- 好处：形状最干净，最接近 JVM；将来第三个后端（D3D/Metal）只是加一个驱动；
- 代价：改动最大（GLEngine 的 8 个 mixin 要拆到 core/backend 两侧，编辑器链路要跟着改），估 12-18 人天，且期间必须保持全绿。

**我的建议：先 A 后 B**（A 是 B 的子集，做完 A 再决定要不要拆 core）。理由：

1. 编辑器只有 GL 一条腿（EditorApp(GLEngine)），A 不需要动编辑器 → 风险可控；
2. A 做完，用户层就已经「不受后端影响」（一个门面 + 一套事件 API），B 只是内部结构更干净；
3. beta7 的定位是扫尾，B 的收益是「将来加后端更容易」，属 beta8 更合适。
