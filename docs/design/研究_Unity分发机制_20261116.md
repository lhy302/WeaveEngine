# 研究：Unity / Unity Hub 的分发与更新机制（2026-11-16）

> 目的：回答「Unity 有没有热更新补丁包机制」「Unity Hub 怎么处理『发布后发现小问题』」。
> 方法：直接查 **Unity Hub 自己用的官方发布 API**（`services.api.unity.com`），取真实字段与真实体积；
> 本轮 `web_search` 通道 401 不可用、`docs.unity.com` 正文页 404，故**不引用文档措辞**，只引用 API 与实测值。
> 凡属记忆/常识、本轮未取证的，正文里显式标【未取证】。

---

## 1 结论（先说）

**Unity 没有、也不提供「同一版本号下换包」的机制。** 编辑器与 Hub 的每一次修复都必须以**新版本号 + 新 changeset** 发布，用户端表现为「有新版本可装」，而不是「同一版本的字节被悄悄换掉」。

Unity 侧真正存在的「增量」只在另外两层：**包（Package Manager）**与**内容（Addressables）**，都不是引擎二进制的增量。

## 2 证据：发布单元 = 版本号 + changeset，字节与版本一一绑定

官方 API（Hub 与官网下载页共用）：

```
GET https://services.api.unity.com/unity/editor/release/v1/releases?limit=2&order=RELEASE_DATE_DESC
-> 200，total = 1601 个 release
```

单条 release 的字段（实测）：

| 字段 | 实测值 | 含义 |
|---|---|---|
| `version` | `6000.6.9f1` | 版本号 |
| `shortRevision` | `8c45277fb9c5` | **changeset 哈希**（下载目录名就是它） |
| `unityHubDeepLink` | `unityhub://6000.6.9f1/8c45277fb9c5` | Hub 安装该版本用的深链（版本+changeset 双要素） |
| `stream` | `SUPPORTED` / `LTS` / `BETA` / `ALPHA` | 通道，Hub 按它过滤 |
| `recommended` | 仅最新 SUPPORTED 为 `true` | 服务端「推荐哪个版本」开关 |
| `downloads[]` | 每平台一条 | 见下 |

`downloads[]` 里单条对象的**全部**键（实测）：`architecture, downloadSize, installedSize, integrity, modules, platform, type, url`。
**没有** `delta` / `patch` / `incremental` / `baseVersion` 之类字段 —— 分发模型里不存在「增量包」这个概念。

## 3 证据：相邻两个补丁版本各是一个完整安装包

同一条 `6000.6` 线上相邻两个 SUPPORTED 版本（Windows ARM64 编辑器安装包，实测）：

| 版本 | changeset | 下载体积 | 安装后体积 |
|---|---|---|---|
| `6000.6.8f1` | `237b6593792b` | **3.56 GB** | 7.55 GB |
| `6000.6.9f1` | `8c45277fb9c5` | **3.54 GB** | 7.48 GB |

下载 URL 形如 `download.unity3d.com/download_unity/<changeset>/WindowsArm64EditorInstaller/...` ——
**changeset 是路径的一部分**。想「悄悄换掉某个版本的字节」在结构上就不成立：换了字节就换了 changeset，就换了 URL，就不是同一个版本了。

其它实测参考点（说明这套模型的规模）：`7000.0.0a16` 3.66 GB / `6000.0.85f2` 3.72 GB / `6000.7.0b9` 3.51 GB。

## 4 Unity Hub 如何「处理发出去才发现的小问题」

| 手段 | 机制 | 对用户的表现 |
|---|---|---|
| **发新版本** | 新 `version` + 新 `shortRevision`，新完整安装包 | Installs 里出现可装的新版本；老版本仍在，不会被替换 |
| **推荐位** | 服务端 `recommended=true` 只给最新 SUPPORTED | Hub/官网把用户往「推荐版本」引 |
| **通道** | `stream` 过滤（LTS / SUPPORTED / BETA / ALPHA / TECH） | 用户自己选稳定度，出问题的 beta 不会污染 LTS 用户 |
| **并存安装** | 安装根下按版本号分目录（`unityhub://<ver>/<changeset>` 决定目录）【机制未本轮取证，但由 deepLink 双要素可推】 | 升级=新装一份，旧版可回退 |
| **项目锁定** | 项目里记录编辑器版本（Unity 的 `ProjectVersion.txt`）【未取证】 | 打开老项目不会被动升引擎 |

> 未取证项：Hub **自身**的更新包是否也是完整安装包（`docs.unity.com` 正文页本轮 404，未拿到官方措辞）。
> 但从结构上看，Hub 更新与编辑器安装共用同一套「版本号→安装包」模型，没有理由例外；如需硬证据，下一轮单独取 Hub 更新日志与安装包体积。

关键点：**没有任何一步是「替换已发布产物」**。要撤回一个坏版本，能做的是「发更新的版本 + 改推荐位」，而不是把旧包换成新包。

## 5 与我们现状的对照

| 维度 | Unity | Loom（beta6 实况） |
|---|---|---|
| 发布单元 | 版本号 + changeset，字节与版本一一绑定 | tag 可重指；beta6 补丁把资产**原地替换**并把 tag 从 `74f8535` 重指到 `f2bba69` |
| 用户能否感知换包 | 能（版本号/changeset 变了） | **不能**（同版本号、同 tag） |
| 修复分发 | 新版本全量 | 新版本全量（138.6 MB） |
| 增量 | 引擎二进制无增量；包/内容层有版本化增量 | 无 |
| 完整性 | API 带 `integrity`（sha384）+ 每平台体积 | 整包 sha256（GitHub asset digest） |

结论：beta6 的「换包」是**分发纪律缺陷**，不是技术限制。修法两件：

1. 纪律：tag/资产不可变，补丁=新版本号（写进发布检查单，工具里加断言）；
2. 技术：文件级增量 + 版本身份可见（见 `设计_Hub增量更新与版本身份_20261116.md`）。

## 6 另一层「增量」（供对照，非本轮结论依据）

Unity 真正的增量在引擎之外：

- **Package Manager**：每个包独立版本号，项目 `manifest.json` 锁版本，升级只换该包【未取证】；
- **Addressables**：内容更新构建只产出变化的 bundle + 新 catalog【未取证】。

这两者的共同点仍是「按版本替换单元」，而不是「按字节补丁」。对我们**不构成**「引擎也应该做二进制增量」的论据。

## 7 人类裁决与本仓影响（2026-11-16）

人类裁决：**不走 Unity 的「不可变」路线，走「可检测」路线**——

> 「引擎校验当前安装版本的引擎和服务器上的引擎（例如同样名字都是 beta6）的哈希或者提交节点是否一样，不一样的话 hub 端提示有新补丁包并推荐拉取。」
> 「发现有补丁包版本的话和 Unity 一样推荐由 Hub 端进行当前同样版本号的老引擎的覆盖安装。」

对本研究的影响：

| 结论 | 是否仍然成立 |
|---|---|
| Unity 没有增量/换包机制（§1-§3） | **成立**，仍是事实依据 |
| 「换包=分发缺陷」的定性 | **部分作废**：我们主动选择保留「同版本号替换」能力，改用**检测 + 提示 + 覆盖安装**兜底 |
| Unity 的 `recommended` 机制 | 保留借鉴：我们也需要一个「服务器说哪个才是当前正版」的单一基准（即 `manifest-<ver>.json`） |
| 「用户不可能不知道」 | **不成立**，我们不能靠版本号本身区分，必须靠对拍（设计 §4.4） |

代价（必须记账）：可检测路线的唯一防线是**检测本身**，所以对拍要有牙（设计 G4/G6/G7），且**替换资产时必须同步更新 manifest**（设计 R1）——否则基准本身就是错的。
