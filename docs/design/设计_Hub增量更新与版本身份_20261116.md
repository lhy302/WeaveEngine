# 设计：Hub 增量更新与版本身份（Hub 0.1.5）

> 立项：2026-11-16，人类提问「基于 GitHub 的更新推送下如何做增量更新」「用户不知道换包了怎么办」。
> 本文只写**已测量**的事实与可验收的方案；未测量的数字不写。
> 相关代码：`LoomHub/hub_update.py`、`LoomHub/hub_github.py`、`LoomHub/hub_install.py`。

---

## 1 现状（代码证据，不是印象）

| 通道 | 现在的行为 | 证据 |
|---|---|---|
| Hub 自更新 | 拉 `releases` → 筛 `hub-v*` → 下载 **整个** `LoomHub-<ver>-Setup.exe` → 校验 size/digest → 写 updater.cmd → 必要时 runas 提权**原地覆盖安装** | `hub_update.py:298-341`、`:538-585` |
| 引擎安装 | 拉 `releases` → 筛 `engine-v*` → 下载 **整个** `Loom-<ver>-compiled.zip`（走镜像 + Range 断点续传）→ 解压到 `<安装根>/<版本号>/` | `hub_github.py:326-389`、`hub_install.py:98-210` |
| 完整性 | 整包级：`size` + `digest`（GitHub release asset 的 sha256）。**没有文件级清单** | `hub_update.py:279-295` |
| 多版本 | 安装根下按版本号分目录，天然并存（与 Unity Hub 同构） | `hub_install.py:119` |

两条通道都是「整包替换」。一次只改 8 个 .py 的补丁，用户要重下 138.6 MB。

## 2 问题（两条，都必须解）

1. **流量/等待**：代码补丁只影响极少数文件，却按整包分发。
2. **身份不可见**：beta6 补丁版是把 release 资产**原地替换**、tag 重指到 `f2bba69`。已装旧构建的用户**无法感知**自己的 beta6 与官方 beta6 不是同一份字节。
   Unity 的解法是**永不换包**（每次修复发新版本号，见 `研究_Unity分发机制_20261116.md` §2-§4）。

   **人类裁决（2026-11-16）不采用 Unity 的不可变路线**，而是：同版本号可以替换，但引擎/Hub 必须**对拍出来并提示「有新补丁包」**，再由 Hub 做**同版本号覆盖安装**。
   → 由此把问题 2 的解法从「禁止换包」改成「换包可检测」（§4.1 / §4.4 / §4.5）。

## 3 测量（2026-11-16 本机实测，可复现）

### 3.1 编译包的文件构成（`C:\loom_build\engine\build_entry.dist`）

| 项 | 值 |
|---|---|
| 文件数 / 总量 | **332 个 / 150.2 MB** |
| 最大的单文件 | `Loom.exe` **37.1 MB**（Nuitka onedir 把所有 Loom Python 代码编进这一个 exe） |
| 其余大头（跨版本稳定） | `numpy.libs` 19.6 / `qt6core` 10.0 / `qt6gui` 9.2 / `qt6widgets` 6.2 / `python313.dll` 5.9 / `libcrypto-3` 5.0 / `PySide6\QtWidgets.pyd` 4.7 |

结论：**任何代码改动都必然重写整个 37.1 MB 的 exe**，而其余 ~113 MB 是跨版本不变的三方件。

### 3.2 单 exe 的差分可行性（关键否定结论）

对比 11-11 构建（beta6 首版）与 11-16 补丁构建的 `Loom.exe`：

| 指标 | 值 |
|---|---|
| 字节数 | 38 821 376 → 38 934 528（+113 152） |
| 4 KB 对齐块差异 | **9506 / 9506 块全部不同（100%）** |
| 64 KB 对齐块差异 | 595 / 595 块全部不同（100%） |
| 新 exe 单独 zlib | 12.92 MB（35%） |

所以：**文件级/块级差分对单体 exe 无效**（Nuitka 单一翻译单元，改动会让后续偏移整体平移）。

> 口径说明：这一对构建相隔 5 天提交，差异比「本次补丁」大，属**上界**；
> 未做「仅一个 .py 差异」的小改动对照实验，故「小改动同样 100% 失配」属**结构推断**（偏移平移），非实测。
想在 exe 内部省流量只能上 bsdiff/xdelta/CDC 一类二进制差分 —— 需要自带补丁器，纯 Python 在 37 MB 上不可接受。**不做**。

### 3.3 但「文件级」增量已经足够划算

| 场景（**推算**，非实测增量包体积） | 全量 | 只下变化文件 | 倍数 |
|---|---|---|---|
| 编译包（只改代码） | 138.6 MB（zip） | `Loom.exe` 压缩后 **12.9 MB** + `build_info.json` 等零头 | **≈ 1/11** |
| 源码包（只改代码） | 342.1 MB（zip） | 十来个 `.py`，**< 0.1 MB** | ≈ 1/3000 |

（源码包：`tools/dist/Loom-0.1.0.beta6-source.zip` = 342.1 MB；编译包 = 138.6 MB / 145 288 824 B。）

推算依据：补丁只改 `.py` → Nuitka 只重写 `Loom.exe`（12.92 MB 压缩值实测）+ `build_info.json`/`解释器.json` 零头；
shaders/ckernels/core_components 等运行期数据目录只在对应源文件变化时才变。**未做「打一个真增量包并称重」的实测**，列为 G3 验收时的第一件事。

### 3.4 GitHub release asset 支持 Range（决定可选方案）

对当前发布资产实测：

```
HEAD  -> 200  Content-Length: 145288824  Accept-Ranges: bytes
GET Range: bytes=0-1023 -> 206  Content-Range: bytes 0-1023/145288824
```

即：单文件按字节区间取可行（`hub_github` 的断点续传已在用 206）。
这条是「方案 C（单 pack + Range 内容寻址）」的前提，但**本版不用**（见 §5）。

## 4 方案（Hub 0.1.5 落地）

### 4.1 发布口径（**2026-11-16 人类裁决**，取代我先前的「永不换包」建议）

人类原话（方案）：

> 「引擎校验当前安装版本的引擎和服务器上的引擎（例如同样名字都是 beta6）的哈希或者提交节点是否一样，不一样的话 hub 端提示有新补丁包并推荐拉取。」

即：**允许同版本号下替换资产，但必须让客户端能检测出来、并主动提示**。由此推出三条硬要求：

| # | 要求 | 为什么 |
|---|---|---|
| R1 | 服务器必须为**每个版本**维护「当前应有的身份」：`manifest-<ver>.json` 里的 `git_head` + `package_id` + 逐文件 sha256 | 没有基准就无从对拍；**替换资产时必须同步更新该 manifest** |
| R2 | 替换必须留痕：`tools/release_notes/发布记录.md` 里记「谁/何时/旧 sha→新 sha/tag 指向变化」 | 事后可审计；也回答「用户装的到底是哪一份」 |
| R3 | 客户端只做「对拍 + 提示 + 推荐拉取」，**不得静默替换** | 否则等于把「用户不知道」换成「用户被强推」，问题没解 |

我先前建议的「tag 永不重指 / 资产永不替换」**降级为可选做法**，不作为硬纪律：人类选的是「可检测」路线，不是「不可变」路线。

代价（记账）：Unity 选不可变、我们选可检测，差别在于**检测能力成为唯一防线** —— 所以 §4.4 的对拍必须「有牙」（验收门 G4）。

### 4.2 发布侧：清单 + 相邻版本增量包（每版 3 个资产）

| 资产 | 内容 | 体积量级 |
|---|---|---|
| `Loom-<ver>-compiled.zip` | 全量包（不变） | 138.6 MB |
| `manifest-<ver>.json` | 逐文件 `path/size/sha256` + `git_head` + `package_id` + `engine_version` + 文件总数/总字节 | 几十 KB |
| `delta-<from>-to-<to>.zip` | 只含新增/变化文件 + `_delta.json`（同 manifest 结构）+ `_delete.txt`（相对路径，一行一个） | 代码补丁 ≈ 13 MB |

生成器 `tools/make_delta.py`（新）：

```
make_delta.py --old <旧版本解压目录|旧 zip> --new <新版本 dist> --out-dir <dir>
  -> manifest-<to>.json
  -> delta-<from>-to-<to>.zip
```

打包门追加断言（写进 `tools/package_engine_compiled.py` 的收尾）：

> 清单里每个文件的 sha256，必须与**全量 zip 解压后**逐文件重算的结果完全一致，且文件集合完全相等。

这条是「增量包 = 全量包」的**唯一**证明手段，不能只靠生成器自己说。

### 4.3 客户端：硬链接拼装 + 逐文件校验（先拼后换，绝不在原目录里逐文件写）

核心决定：**先把完整的新内容拼到 `<ver>.partial/`，校验全过再一次性换名**。
两种落地：**新版本号** → 直接落到新目录（旧版本目录不动）；**同版本号补丁** → 走 §4.5 覆盖安装（拼装同一套，换名时把旧目录挪成 `.rollback`）。

```
1) 选源版本：本地已装版本里，取「有 delta-from 能对上的」最高版本；没有 -> 全量。
2) 新建 <安装根>/<新版本>/（临时名 <新版本>.partial/）
3) 对 manifest 里每个文件：
     · 源版本里存在且 sha256 相同 -> os.link 硬链接（NTFS 同卷，O(1)）；失败则 shutil.copy2
     · 否则从 delta zip 解出（解出后再算 sha256 比对，不符即整次失败）
4) 按 _delete.txt 保证不把已删文件硬链过去（按 manifest 正向拼装，天然不需要删）
5) 全量校验：manifest 每个文件 sha256 逐个比对；多出/缺失都算失败
6) 成功后 <新版本>.partial -> <新版本> 原子改名；登记解释器
7) 任一步失败：删掉 .partial；此时旧版本目录**一个字节都没动**，用户可继续用旧版（同版本号补丁的换名/回滚见 §4.5）
```

为什么不用「原地替换 + updater 脚本」：

- 原地改要处理「文件被占用/正在跑」，就得再写一套 updater + 提权（Hub 自更新那套复杂度，`hub_update.py:466-535`）；
- 拼装式失败即回滚（旧目录没动），不需要回滚逻辑；
- 与现有 `<根>/<版本号>/` 布局天然一致（`hub_install.py:119`），不破坏多版本并存。

磁盘代价：硬链接不占额外空间；跨卷/非 NTFS 退化为复制（此时增量省的是**下载**，不省磁盘 —— 明确告知用户）。

### 4.4 版本身份对拍（**H-01，人类指定方案**）

#### 4.4.1 两端身份从哪来（都是现成的）

| 端 | 来源 | 字段 |
|---|---|---|
| 本地 | `<安装根>/<ver>/Loom/build_info.json` | `git_head`、`git_dirty`（`tools/build_engine.py:108-120` 已写入） |
| 本地 | `<安装根>/<ver>/Loom/解释器.json` | `version` |
| 服务器 | `manifest-<ver>.json` | `git_head`、`package_id`、逐文件 sha256、文件数/总字节 |

#### 4.4.2 判定表（同版本名不同字节 = 人类要解的那一档）

| 本地 `git_head` vs 服务器 manifest | 判定 | Hub 表现 |
|---|---|---|
| 相同 且 `package_id` 相同 | 一致 | 静默（不打扰） |
| **不同（版本名相同，例如都是 `0.1.0.beta6`）** | **有新补丁包** | 黄字提示 + 「拉取补丁」按钮 → 走 §4.5 **覆盖安装**（增量拼装 + 原子换名 + 失败回滚） |
| 本地 `git_dirty=true` 或文件被改（AV 篡改/用户手改） | 安装已损坏 | 红字提示 + 「校验完整性」（§4.4.3） |
| manifest 取不到 / 无网 | 无法判定 | **静默**（与现有 24h 静默口径一致，`hub_update.py:5-6`） |

#### 4.4.3 成本（决定能不能每次启动都做）

- 常规对拍：只读 `build_info.json` + 一个几十 KB 的 manifest → **不需要哈希 150 MB**，毫秒级；
- 全量 sha256 只在用户点「校验安装完整性」时做（复用 §4.3 第 5 步代码），并显示进度；
- 显示：已装列表每行 `版本 / git_head 前 7 位 / package_id 前 12 位 / 安装时间`。

#### 4.4.4 为什么这条排第一

**不依赖**增量更新：即使只做 §4.4、不做 §4.2/4.3，「用户不知道换包了」就已经被解决（用户能看到并主动拉补丁）。
反过来，只做增量而不做对拍，则「同版本名不同字节」依旧不可见 —— 所以 H-01 先于 H-02/H-03。

### 4.5 同版本号覆盖安装（**2026-11-16 人类裁决**）

人类原话：

> 「发现有补丁包版本的话，和 Unity 一样推荐由 Hub 端进行当前同样版本号的老引擎的**覆盖安装**。」

即：补丁不另起一个版本目录，而是**由 Hub 把同版本号的老引擎就地覆盖掉**。对用户来说就是「beta6 还是 beta6，但已经是补丁版」。

> 事实澄清（不影响裁决，只影响措辞）：Unity 侧的补丁通常以**新版本号**发布，所以「同版本号覆盖」在 Unity 身上没有可观察证据；
> 这一条是**我们的扩展**。因此它必须自己补齐「覆盖」带来的三件事，不能指望 Unity 的经验：
> ① 覆盖前有基准（R1 的 manifest）；② 覆盖后能证明覆盖成功（逐文件 sha256）；③ 覆盖失败能回到原样。

#### 4.5.1 用户可见语义 vs 实现语义

| 层 | 语义 |
|---|---|
| 用户可见 | 覆盖安装：同版本号目录被换成补丁版，安装列表仍是一条，不需要用户管两个 beta6 |
| 实现 | **不能真的逐文件覆盖**（中途中断会留下半新半旧的残骸，且 `hub_install.py:125-127` 的清理逻辑正是为「半残目录」写的）。改为 staging + 原子换名 + 失败回滚 |

#### 4.5.2 流程（覆盖安装的安全实现）

```
0) 前置：本地 <ver>/ 身份与服务器 manifest-<ver>.json 不一致（§4.4 判定表第 2 档）
1) 拼装到 <ver>.partial/（§4.3：未变文件从 <ver>/ 硬链接，变化文件从 delta 解出，逐文件 sha256 校验）
2) 校验通过 -> <ver>/ 原子改名为 <ver>.rollback/（旧引擎不删，先留着）
3) <ver>.partial/ 原子改名为 <ver>/
4) 启动新引擎做一次自检（能 import 主模块 / --version 输出正确）
     成功 -> 删 <ver>.rollback/
     失败 -> 删 <ver>/，把 <ver>.rollback/ 改回 <ver>/，提示覆盖失败并保留旧版
5) 中断恢复（下次 Hub 启动时按目录状态机判定）：
     只有 <ver>.partial   -> 上次没拼完，删掉重来（旧 <ver>/ 完好）
     有 <ver>.rollback 无 <ver> -> 换名到一半，把 .rollback 改回 <ver>/
     有 <ver>.rollback 有 <ver> -> 上次在自检/删备份阶段被中断，跑一次自检再决定删或回滚
```

关键点：硬链接让「未变文件」不复制、也让 `.rollback` 与新版共享 inode（换名不影响内容），所以回滚是 O(1) 的改名，不需要重新下载。

#### 4.5.3 与「另起版本目录」方案的取舍（为什么按裁决走覆盖）

| 维度 | 覆盖安装（裁决采用） | 另起目录（我原建议） |
|---|---|---|
| 用户认知 | 一个 beta6，不会被问「为什么有两个 beta6」 | 会出现两个同名版本目录，需额外解释 |
| 回退 | 靠 `.rollback` + 目录状态机（有状态，需测） | 天然可回退（旧目录没动） |
| 磁盘 | 覆盖后只剩一份（+ 拼装期的临时副本） | 两份并存 |
| 失败面 | 需要覆盖流程本身正确（G8/G9 门兜住） | 失败面更小 |

覆盖安装的额外风险由验收门兜：G8（覆盖后身份与全量包逐文件相等）、G9（在自检阶段人为失败 → 必须回到旧引擎且能启动）、G10（各阶段 kill 进程后状态机必须能恢复）。

## 5 明确不做（写清理由，留痕）

| 方案 | 内容 | 为什么不做 |
|---|---|---|
| B | 单 pack + Range 内容寻址（任意跨版本按块取） | §3.2 已证单体 exe 块级差分无效；三方件本来就稳定。只有「频繁小改 + 用户长期落后很多版本」时才值得，现在没有这个需求 |
| C | 用 git 仓库当增量通道（`git fetch` 自带内容寻址增量） | 要求用户机有 git 或内置 dulwich；且编译产物进 git 会撑爆仓库（每版 150 MB） |
| D | exe 级二进制差分（bsdiff/xdelta） | 需自带补丁器；纯 Python 在 37 MB 上时间/内存不可接受 |
| E | 代码签名 | 已知缺口（beta6 登记过「无 CI / 无签名」），需要证书与 CI，单独立项 |

## 6 验收（可执行门，不达标不发）

| 门 | 判据 |
|---|---|
| G1 增量=全量 | 用 beta6 全量包 + beta7 delta 拼出的目录，与 beta7 全量包解压结果**逐文件 sha256 完全相等**（文件集合也相等） |
| G2 中断可恢复 | 拼装中途 `kill` 进程：`.partial` 可识别、重跑能续/重来、旧版本目录 sha256 不变 |
| G3 真实升级 | 在本机 `<安装根>` 上做一次真实 beta6 → beta7 升级，记录下载字节数（应 ≈ 13 MB 量级）与耗时 |
| G4 身份可见 | 人为把本地 `git_head` 改成别的值 → Hub 必须显示不一致提示（有牙自证：改回去必须不显示） |
| G5 无清单不装 | manifest 缺失/解析失败 → 拒绝增量，回落全量并说明（不得静默） |
| G6 同版本名替换可检测 | 造一份「本地 beta6 = 旧构建 / 服务器 beta6 = 新构建」的夹具：Hub 必须提示「有新补丁包」并能一键拉补丁；拉完再对拍必须转为「一致」 |
| G7 判定不误报 | 本地与服务器完全一致时**不得**出现任何提示（防「狼来了」）；`git_dirty=true` 时提示文案必须与「有新补丁包」区分开 |
| G8 覆盖后=全量包 | 覆盖安装完成后，`<ver>/` 与服务器全量包解压结果**逐文件 sha256 完全相等**（证明覆盖没漏文件、没留残骸） |
| G9 覆盖失败可回滚 | 在第 4 步自检处人为让它失败：必须回到旧引擎、旧引擎能正常启动、安装列表仍可用（有牙自证） |
| G10 覆盖中断可恢复 | 在拼装中/换名中/自检中/删备份中四个位置各 kill 一次：下次启动状态机必须恢复到「一个可用的 `<ver>/`」，且不丢旧引擎 |

## 7 工作量与排期（Hub 0.1.5）

| 项 | 内容 | 估 |
|---|---|---|
| H-01 | **版本身份对拍（人类方案）**：两端身份读取 + 判定表（含「同版本名不同字节」档）+ 提示与「拉取补丁」入口 + 完整性校验按钮 | 3-4 人天 |
| H-02 | `tools/make_delta.py` + 清单生成 + 打包门 G1 断言 | 2-3 |
| H-03 | 客户端拼装器 + **同版本号覆盖安装**（硬链接 + 逐文件校验 + `.rollback` 原子换名 + 自检 + 四阶段中断恢复状态机，见 §4.5） | 4-6 |
| H-04 | Hub UI 接增量（选源版本、进度、失败回落全量、覆盖失败提示、磁盘提示） | 2-3 |
| H-05 | **替换留痕**（人类口径 R1/R2）：替换资产时同步更新 `manifest-<ver>.json` + 写 `发布记录.md`；`tools/release_github.py` 加「同名资产已存在 → 必须走替换流程并留痕」的提示 | 1 |

顺序：**H-01（先让「换了包」可被看见）** → H-05（替换有基准、有留痕）→ H-02（发布侧清单/增量包）→ H-03（客户端拼装）→ H-04（UI 接线）。

依赖关系：H-01 的判定要读 `manifest-<ver>.json`，所以 H-02 的「清单生成」必须与 H-01 同批交付（可以先只生成清单、不生成增量包）。

## 8 未验证 / 风险

1. 硬链接在目标机的实际行为：NTFS 同卷可行；**跨卷或用户把安装根放在 exFAT/网络盘上会失败** → 已设计为自动退回复制，但退化的磁盘占用尚未实测。
2. 杀毒软件：beta6 已有「安全软件把 .py 改成全零」的历史（`hub_install.py:65-96`）。增量拼装会产生大量硬链接，是否触发扫描行为未知，需 G3 实测。
3. GitHub release 资产数量：每版本 3 个资产、60 个版本 = 180 个，未验证 Hub 的 `releases?per_page=30` 分页策略是否够用（`hub_github.py:128` 只取 30 条）。
4. 镜像站点（`ghfast.top` 等）对新增 delta 资产的支持未实测（URL 前缀拼接方式相同，理论上一致）。
