# 稳定性与启动自检设计

> **性质**：白盒契约 + 机制设计。落实"操作系统引导"模型 —— 官方件出厂即稳定、
> 启动自检、外部件全兜底、官方件被改则报警。
> **取证来源**：`core_components/module_loader.py`、`module_registry.py`、`registry.json`、
> `crash_reporter.py`、`guiloader.program_dir`（均为当前代码）。

---

## 1. 设计目标

1. 官方出厂组件**未被修改 = 必定稳定不崩溃**
2. 官方件**被修改/损坏 → 报警 + 拒绝加载**（提示修复或重装）
3. 外部第三方 DLL **不可用 → 全部默认回退官方件**
4. 主线程启动后充当"引导程序"，**自检通过后逐步拉起完整引擎**

---

## 2. 核心机制：内嵌出厂基准

### 2.1 问题
当前 `registry.json` 带 SHA256，但它在**磁盘上，可被修改** —— 改了它就能骗过校验。

### 2.2 方案：两个文件，职责分离

| 文件 | 角色 | 可改性 |
|---|---|---|
| `registry.json` | **花名册**：有哪些组件、装哪、启用否 | 允许改（装配灵活性来源） |
| `official_manifest.py` | **出厂基准**：官方件应有的 SHA256 | **编译进 exe，外部改不动** |

### 2.3 official_manifest.py（构建时自动生成）

```python
# 本文件由 build_all.bat 自动生成，请勿手改
# 生成时间: 2026-10-15T...
# 对应 registry 版本: loom-core-registry/1.0
OFFICIAL_MANIFEST = {
    "module_ref": {"path": "core_components/module_ref.dll", "sha256": "3cf5fc9c..."},
    "ckernels":   {"path": "ckernels/loom_kernels.dll",     "sha256": "df810fc5..."},
    "pipeline":   {"path": "core_components/pipeline/pipeline.dll", "sha256": "051b12d6..."},
    "script":     {"path": "core_components/script/script.dll",     "sha256": "d445c97e..."},
    "physics":    {"path": "core_components/physics/physics.dll",   "sha256": "124eba34..."},
}
```

**生成方式**：`build_all.bat` 在 `refresh_registry_sha.py` 之后加一步，从 registry.json 抽出官方件 sha 写成此 .py 文件。

**打进 exe**：Nuitka 编译时 `official_manifest.py` 被 import → 编译成机器码嵌入 exe，**外部看不到、改不了**。

## 3. 启动自检流程

主线程启动 = 引导程序：

```
[引导] 读 official_manifest（内嵌基准）
  ↓
[自检] 对每个官方件:
   1. 文件存在?
   2. 算实际 SHA256
   3. 与内嵌基准比对
  ↓
[分级处理]
   ├─ 全部一致 → 正常装配，拉起引擎
   ├─ 官方件被改 → 【报警】"组件 X 被修改，请修复/重装" + 拒绝加载该件
   └─ 官方件缺失 → 【报警】"组件 X 缺失" + 拒绝启动
  ↓
[装配] 按 registry.json 拓扑顺序 init 各组件
  ↓
[外部件] 用户注入 DLL（official=false）:
   ├─ 校验失败 → 弹出，回退官方
   └─ 运行崩溃 → Minidump 落盘 + 弹出，回退官方
  ↓
[就绪] 提供运行平台
```

---

## 4. 失败分级

| 失败场景 | 处理 | 用户感知 |
|---|---|---|
| 官方件 SHA 不符 | 报警 + 拒绝加载该件 | 明确提示"请重装" |
| 官方件缺失 | 报警 + 拒绝启动 | 明确提示 |
| 官方件 init 失败 | 报警 + 拒绝启动 | AssemblyError |
| 外部件校验失败 | 静默弹出 + 回退官方 | 控制台日志 |
| 外部件运行崩溃 | Minidump + 弹出 + 回退官方 | 进程不崩 |
| 外部件静默算错 | **无法自动检测**，靠出厂前对拍 | —— |

**关键认识**：前两种是"你要的崩"，后三种是"兜底"。**"静默算错"只能靠出厂前对拍网压下去**。

---

## 5. 开发模式 vs 出厂模式

### 5.1 问题
开发时天天重编官方件，SHA 一直在变。若强制校验，开发无法进行。

### 5.2 方案：双模式

| 模式 | 触发 | 官方件 SHA 校验 |
|---|---|---|
| **出厂模式**（默认） | 无环境变量 | 强制校验，不符=报警拒载 |
| **开发模式** | `LOOM_DEV=1` | 跳过校验，记录"非出厂状态" |

**判定**：`_DEV_MODE = os.environ.get('LOOM_DEV') == '1'`。

## 6. 自检阶段落点（代码）

**新增模块** `core_components/boot_check.py`：
```python
def verify_official(registry_path, manifest, dev_mode=False):
    """对官方件逐个算 SHA256 与内嵌基准比对。
    返回 (ok: bool, report: list[dict])。
    report 每项: {module_id, path, expected, actual, status}
    status ∈ {'ok','modified','missing'}"""
```

**接入点**：`module_registry.assemble()` 之前先调 `boot_check.verify_official()`；
出厂模式下有 modified/missing → `AssemblyError`。

**报告输出**：引导阶段打印清晰报告（哪些件 OK / 被改 / 缺失）。

---

## 7. 实施步骤

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1 | 写 `boot_check.py`（自检模块） | 单元探针：篡改某 DLL 字节 → 检出 modified |
| 2 | `build_all.bat` 加生成 `official_manifest.py` | 构建后文件存在且 sha 与 DLL 一致 |
| 3 | `module_registry` 接入自检（出厂模式） | 篡改 DLL → 启动报错 |
| 4 | 加 `LOOM_DEV=1` 开发模式开关 | 设开关后跳过校验 |
| 5 | 引导阶段打印自检报告 | 启动可见报告 |

---

## 8. 与现有机制的衔接

- **保留** `registry.json` 的 sha256 字段（用于外部件信任闸）
- **新增** `official_manifest.py` 只钉**官方件**（外部件不进此表）
- **复用** `module_loader` 的 SHA 计算函数
- **复用** `crash_reporter` 的 Minidump（外部件崩溃兜底）

---

## 9. 边界

- **不阻止**用户改 registry.json 增减外部件（那是扩展自由）
- **阻止**用户偷偷改官方件冒充（内嵌基准是唯一权威）
- **反编译 exe** 理论上能改内嵌基准，但成本极高，不在防御范围
