## 1. beta7：设计失误扫尾（**唯一大纲方向**）

> **人类裁决（2026-11-17，原文留痕）**：「修改 beta7 的开发计划，把所有功能补全的计划全部推迟到 beta8，beta7 里的计划只留『给当前工程的设计失误扫尾』这一个大纲方向。」

因此本节**只有扫尾项，零功能补全**。原 beta7 的功能项已整体顺延到 §2（beta8），编号不删、原文保留（见 §2 开头的口径说明）。
扫尾的验收口径统一走 §6（双后端一致 P0~P5 门）+ §7（版本定位）。

### 1.0 路线纠正（2026-11-17 人类裁决：**不受后端影响 / JVM 模型**）

> 人类原话：「两个VK后端的不一致我的要求是如同JAVA或者Python这样的高级编程语言一样不受到后端的影响，

**这推翻了「逐条补 VK 的 40 条」这个做法**（补完只是维护两份实现）。改为按门面收敛推进：

## 6 专题：双后端「无感切换」（2026-11-17 人类立项，beta7 起跨版本）

人类原话（留痕）：

> 「引擎本身由我们付出不同后端的渲染差异的对齐，也就是尽可能让两个后端的功能与渲染效果没有区别，展示给用户的就是两个后端都是无感切换，
> 用户切换后端不应该有感受差距。大概就是这样：用户做的东西 → 引擎 → 引擎根据用户设置的不同后端来走对应的渲染路径（VK/GL），
> 不同后端之间的差异由我们对齐屏蔽掉。」

一句话目标：**用户只管做内容，后端是引擎的实现细节；切后端只改变帧率数字，不改变看到的东西。**

> **2026-11-17 人类裁决（收窄口径）**：「性能对齐不在考虑范围内，毕竟 VK 本来对性能的调度就优于 GL，门槛也更高。
> 只对齐暴露给用户的 API 接口操作都是一样 —— 一个要求。」
> 即：本专题的**唯一硬要求是「API 同一套、同一操作同一结果」**；性能不在内（见 6.5）。

### 6.0 与 JVM 的类比：保证什么、不保证什么（2026-11-17 人类对齐）

人类给的类比：**像 Java/Python 那样，同一份程序在不同底层架构（x86/ARM）上执行结果一致 —— 后端之于我们，就像 CPU 架构之于 JVM。**

这个类比成立，而且它把重点从「像素」搬到了「API + 语义」：

| JVM 世界 | Loom 对应物 | 现状 |
|---|---|---|
| JVM 规范（JLS/JVMS）定义语义 | 引擎公共 API 契约（**我们还没有**） | GL 侧有效公开 API **105 个**，VK 侧 **38 个**，GL 有而 VK 没有的 **77 个** |
| 同一份字节码在任何 JVM 上行为一致 | 同一份场景/脚本在两后端行为一致 | **不成立**（77 个 API 缺失 + 13 条已知差异） |
| **不保证**：性能、内存占用、GC 时序、线程调度 | **不保证**：帧率、显存、GPU 耗时 | 与 JVM 同口径；**人类已明确排除性能对齐**（见 6.5） |
| 浮点：Java 17 起全 strict（历史上有 strictfp 开关） | 图形输出：没有对应规范 | 只能阈值化（结构性差异 = 0 + MAE ≤ 实测阈值） |
| 一致性测试套件（JCK / TCK） | 我们的 P1~P5 验收门 | 有门，但**缺 API 矩阵**（见 6.4 P0） |

**结论**：要的不是「像素一样」，而是「**同一份用户内容 + 同一套 API → 同样的可观察结果**」。
像素只是其中最外层的一维；真正的大缺口是「两端根本是两套 API」。

### 6.1 唯一要求 + 四个判定面（不是四/五个目标，是同一个要求的四种验法）

**唯一要求：同一份用户内容、调同一个 API、做同一个操作 → 两端结果相同。**

| 面 | 判据 | 为什么归在这条要求下 |
|---|---|---|
| ⓪ **API 面** | 两端公开方法集合**完全一致**（名字/参数/返回/语义）；差异必须为 0 | 现在 GL 有效公开 API 105 个、VK 38 个，**GL 有 VK 无 77 个** |
| ① 功能面 | 同一个 API 调用在两端都能完成同一件事（不出现「一端能加灯、一端加不了」） | 这是 API 缺失的直接后果，不是独立目标 |
| ② 视觉面 | 同一个调用产生的画面：**结构性差异 = 0**；数值差异 MAE ≤ 实测阈值 | 视觉差异是「同一 API 结果不同」的**证据**，不是独立目标 |
| ③ 行为面 | 同一设置/同一操作 → 同一行为：**逻辑帧段序与生命周期回调顺序**（FixedUpdate→Update→动画→物理→音频→prep→碰撞事件→插值）、时钟档位、鼠标锁、UI 派发、相机投影 | 现在 VK 逻辑帧只有 4 段（缺音频/prep/碰撞事件），碰撞事件**从不派发** → 同一份脚本两端行为不同（差距 15） |
| ④ 错误面 | 同一故障两端都**出声**（文案可不同，不许一端静默） | 「同一操作」的失败表现也属于操作结果 |

> 口径说明：**性能不在这张表里**（人类裁决，见 6.5）。
> 视觉/行为/错误之所以还要写，是因为它们是**验证 ⓪ 的手段**——没有它们，「API 一样」就只能靠方法名比对来证明，那是假的。

### 6.4 验收门（怎么证明「无感」）

| 门 | 判据 |
|---|---|
| **P0 API 矩阵** | 把两端公开方法集合导出成表（方法名 / 参数 / 返回 / 语义一行说明）→ 差异必须为 0；有差异即不通过（这是 JVM 类比里「同一套标准库」那条） |
| P1 像素对拍矩阵 | N 个场景 × 固定相机 × 两端 → MAE 表；**结构性差异必须为 0**，数值差异在阈值内；阈值由首批实测确定并写死 |
| P2 功能矩阵 | 每条功能一行 × 两端 = 可用/不可用；出现「一端有、一端无」即不通过 |
| P3 行为矩阵 | 每个设置项一行（logic_fps/physics_fps/鼠标锁/键位/相机投影/UI 滚轮…）× 两端行为 = 必须相同 |
| P4 错误矩阵 | 人为注入故障（缺天空盒/缺贴图/阴影超限/驱动不支持）→ 两端都必须可见 |
| P5 切换回归 | 同一存档切后端再切回：场景/资产/UI/脚本状态不得损坏（VK 路径现在连 migrate 都不过，这条必红） |

> 为什么单独立专题：上面 14 条差距分散在 8 个不同文件、由 6 个不同历史批次引入；逐条修完不等于「一致」，
> 必须有**一张统一的验收矩阵**把「两端应该一样」这件事变成可执行的门，否则修一条漏一条。

### 6.5 明确不做（2026-11-17 人类裁决）

| 不做 | 理由（人类原话） |
|---|---|
| **性能对齐** | 「性能对齐不在考虑范围内，毕竟 VK 本来对性能的调度就优于 GL，门槛也更高。」→ 不设「两端帧率不得低于对方 X%」这类门，也不追求两端 GPU 耗时接近 |
| 逐像素相等 | 两套光栅器不可能逐位相等；只要求结构性差异为 0 + 数值 MAE ≤ 实测阈值 |
| VK 版编辑器 | 要把撤销/Qt 视图/gizmo/拾取/UI 编辑全部重做一遍；档 B（编辑器 UI 留 GL、播放走所选后端）即可满足「编辑器里也能验 VK」 |

> 记法：本专题的验收门**只回答一个问题** —— 「同一个操作，两端结果一样吗」。
> 帧率/显存/GPU 耗时一律不进判据；如果哪天要性能对齐，另开专题（届时判据是「同场景同设置下两端 FPS 比值」，与本文无关）。

### 7.3 依赖关系（决定顺序，不是拍脑袋）

| 功能 | 卡在哪个地基项上 |
|---|---|
| B7-01 骨骼/GPU 蒙皮、B7-06 后处理扩展、B7-07 GPU 粒子 | 都要改渲染 pass → 先要 **B7-15（RasterState 落地）** 与 **B7-20（门面收敛）**，否则每个功能都要在 GL/VK 各写一遍 |

### 7.4 建议 → **已采纳为裁决**（A：beta7 = 纯地基版，零新功能）

理由：

1. 依赖关系决定：功能积压的前提全是地基项（§7.3）；先做功能等于把分叉再乘一遍。
2. 算术决定：地基 46-72 人天已是一个完整周期；功能 93-126 人天装不进去。
3. 历史决定：beta6 就是「功能 + 修补同批」，结果修完还要重出包、重指 tag（见 `beta6_缺陷账本`）。混合版会重演。
4. 一致性专题（§6）本身就是一个大工程：14 条差距 + P0~P5 五道门，它不是「顺手做」的活。
