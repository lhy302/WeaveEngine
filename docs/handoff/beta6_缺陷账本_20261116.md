## 2. 本轮新发现（文档里没有或写得不够）

### 2.1 B13 根因：两处独立崩溃 + GL 也有一处

**复现方式**（探针放 `%TEMP%`，未入仓，避免污染仓库）：用 `test_ab_gl_vk.render_vk / render_gl` 渲染 `ab_scenes/ab_scene.json`（4 物体 / 2 灯）的 4 个变体，逐例捕获异常。

| 变体 | GL | VK |
|---|---|---|
| 全部 `visible=False`（**合法用户状态**：把物体全隐藏） | OK | **CRASH** `ValueError: zero-size array to reduction operation minimum` |
| `objects=[]`（空场景列表） | **CRASH** `RuntimeError: pipeline.dll 调用失败 rc=-2（官方件契约违约）` | **CRASH** 同上 |
| `objects=[] + lights=[]` | OK | **CRASH** `ValueError: Invalid data_offset` |

**根因 1（VK，有平行光时）**：`Loom/vk_renderer.py:1539`
`mn = w[:, :3].min(axis=0)` —— 零可见实例时 `w` 形状为 `(0,4)`，对空数组求 min/max 必然抛 `ValueError`（`_dir_light_vp` 用可见物体包围盒拟合平行光阴影相机，没有处理"没有物体"）。

**根因 2（VK，无灯或无实例时）**：`Loom/vk_renderer.py:1821`
`d.queue.write_buffer(self._inst_buf, 0, _inst_pack.tobytes())` —— `_inst_pack` 为空时 `tobytes()` 是 `b''`，wgpu 拒绝 `write_buffer` 空数据 → `ValueError: Invalid data_offset`。

**根因 3（GL，只有现象、根因未定位）**：`objects=[]` 且**有灯**时 GL 崩在 `pipeline.dll rc=-2`。注意「全部隐藏」GL 是正常的 → 说明 GL 的崩溃点不在渲染遍历，而在**空模型列表**触发的某个 C 内核入参非法（见 §4 第 3 项）。用户可达性：编辑器里删光所有物体、保留默认灯 → 就是该状态；且 `test_ab_gl_vk.render_gl` 走的是 `EditorApp.render()` 生产路径，不是测试专用路径。

**为什么这条必须记账**：把场景物体全部隐藏是正常玩法状态（玩家清场、或分帧加载还没出现），VK 会**必崩**。当前 `ab_ui_only` 用远在 `(1000,1000,1000)` 的哨兵物体绕过 —— 这是**绕，不是修**。

### 2.2 B14 实况：文档写"不深度测试"，代码没关，失败还被吞掉

- `Loom/engine.py:804-831` `draw_screen_lines`：docstring 写「屏幕空间折线描边（UI 层用，**不深度测试**）」，但函数体只做坐标换算 → 调 `draw_lines`，**既没有 `ctx.scope` 也没有 `disable(DEPTH_TEST)`**；
- `Loom/engine.py:833-854` `draw_screen_polygon`：同样问题；
- 两处结尾都是 `except Exception: pass`（`830-831` / `853-854`）—— **线画不出来时没有任何报错**，违反项目硬纪律「失败必须可见」；
- UI Shape 的实际调用点：`Loom/loom_ui.py:888-897`（描边分支）→ `engine.draw_screen_lines`；**它外面还包了一层 `except Exception: pass`（`885-886` 填充 / `896-897` 描边）** → 静默层数是 **3 层**（ui 元素 → engine 包装 → draw_lines 内部），不是 2 层；
- **仓库内已有独立证据**：`Loom/tests/test_ab_gl_vk.py:209-216` 的夹具注释原样写着「GL 的 Shape 描边走 draw_lines，不会像 panel/text 那样在自己的 ctx.scope 里关深度 → 3D 深度非 1 的像素上整条线被深度测试丢掉（实测 480x320 场景条线 0 像素）」——这是夹具作者当时就发现的同一件事，只是被当成「夹具状态对齐」处理，没回改引擎。

→ 后果：3D 深度非 1 的像素上整条描边被深度测试丢掉，而且**静默**。夹具里靠外部 `disable(DEPTH_TEST)` 绕过，所以像素门一直绿。

### 2.3 静默失败面积（第一次量化）

`py -3.13 tools/loom_lint_except.py` 实测（该工具**没有排除参数**，只能整目录扫）：

| 范围 | 文件 | ERROR | 其中 silent-pass | 其中 no-handling | WARN(broad-exception) |
|---|---|---|---|---|---|
| `Loom` 全量 | 300 | **988** | 563 | 425 | 300 |
| `Loom/tests` | 194 | 361 | 258 | 103 | 53 |
| **产品树（减法推导）** | **≈106** | **≈627** | **≈305** | **≈322** | **≈247** |

**口径警告（自审修正）**：这些是**工具报告数，不是缺陷数**。`tools/loom_lint_except.py` 自身已知会误判——例如把 `{'ok': True}` 这类字典键当作「已上报」，因此真实「静默吞错」数量可能**高于也可能低于**表内数字。**只能当趋势指标，不能当结论引用**。

**判断**：里面必然混着大量「可选依赖缺失 → 合法降级」（项目允许环境适配型降级），但**没有任何豁免清单**，所以真缺陷与合法降级无法区分 → 这条 lint **目前当不了门**。
**建议**：beta7 先立「静默失败豁免清单（文件+行+理由）」，再把它接成 CI 硬门；否则 988 条噪声会让人继续忽略它。

### 2.5 本轮自己引入的新约束（也要记账）

`Loom/tests/test_shader_spirv_matrix.py`（2026-11-16 新增）依赖 **glslang + 可用 GPU 适配器**：
- 缺 glslang 或版本/sha256 不符 → **FAIL（不跳过）**；无 GPU 适配器 → **FAIL**，除非显式 `LOOM_ALLOW_NO_GPU=1`；
- 含义：`run_all` 从此在别的机器上也需要同样环境。与既有 `ab` 门（默认 FAIL、显式 `LOOM_AB_ALLOW_NO_VK=1` 才 SKIP）**同口径**，不新增"必须装编译器"之外的限制。

### 2.6 `verify_pkg_vs_head` 的口径问题（发版后必然报红）

判据是「HEAD 在 `Loom/` 下**零 diff**」。发布后任何 `Loom/` 改动都会让它红 —— 2026-11-16 新增一个测试文件后已经如此。
**建议**：改成「HEAD 是某个 tag 的祖先 **且** `Loom/` 下相对该 tag 无 diff」，否则每次发版后工具都在喊狼来了，喊多了就没人看。
