# 期1 微基准结论 — aabbs C 内核碎任务批量化 (2026-09-07)

探针: tests\_tmp\sched_microbench.py (常驻可复跑, 结果落 sched_microbench_result.json)
口径: 混合500 真实 V 分布复刻 (3015x100/2501x90/2035x90/1617x90/1247x90/24x40/4x1),
LOOM_NO_NUMBA=1 (编译版同形态), loom_kernels.dll 直调。

## 实测 (两轮稳态)
| 口径 | 耗时/逻辑帧 | 说明 |
|---|---|---|
| A) 碎任务 (92 次调用, n≤6, 复刻池分块现状) | 6.73-6.87 ms | 501 行全量 |
| B) 组批 (7 次调用, 同 V 组合并) | 4.89-4.93 ms | 内核本体地板 |
| C) ctypes 空调用税 | 15.2-15.9 µs/次 | 纯提交开销 |

- 提交开销占比 = 20.3-21.7% (≥20% 闸门 → batch 入口值得做, 未触发降级出口)
- 批量化潜在收益 (A→B) = 26.8-28.8% (碎任务形态全量 501 行口径)
- 内核本体 = 9.8 µs/行 → 播放态 dirty ~100 行 ≈ **0.98 ms/逻辑帧** (批4A 实锤 0.1ms 级同量级, 本基准含 501 行全量上界)

## 对期1 接入的推论 (诚实账)
1. 提交税本身 ~1.4-1.5 ms/帧 是在 **501 行全量形态**下测的; 播放态真实 dirty 行
   ~100 行, 碎任务形态的绝对开销约 0.3-0.5 ms (92 次调用税 1.4ms 是按 501 行切块数,
   dirty 100 行切块更少 ~20-30 次 → 税 ~0.4ms)。
2. batch 入口 (改 .c + 重编 dll) 可省这笔税 + 让"同 V 组跨块合并"可行, 但收益上限
   <1ms/逻辑帧, 且 DLL 变更要求全对拍网重跑。
3. 结论: **期1 batch 入口按"可选/低优先"处理** — 先接无 DLL 变更的段 (world_matrices
   分块 + aabbs 池批整合), batch 入口仅在池接入后账目显示提交税仍显著时再做。
