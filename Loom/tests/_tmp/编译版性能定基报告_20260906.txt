## 三、★核心归因 (代理 FPS 公式, 三侧全部命中)

播放态 FPS = (1000 − 30 × L) / R, 其中 L = 每逻辑帧耗时 (ms),
R = 每渲染帧非逻辑耗时 (ms)。代入三侧:
- 编译版: L=26.39, R=(1000−30×26.39)/17.6 = 11.7   → 命中 17.6 ✓
- 冻结:   L=24.94, R=(1000−30×24.94)/23.3 = 12.3   → 命中 23.3 ✓
- 原生:   L=21.86, R=(1000−30×21.86)/39.0 = 7.4    → 命中 39.0 ✓

结论 (证据强度: 定量闭环, 非猜测):
1. **播放态瓶颈 = 逻辑帧内容 (L 项), 不是渲染, 也不是 Qt 合成**。
   三侧 R 仅 7-12ms 且几乎不随环境变 (渲染侧 numpy 调用本来就少);
   L 从原生 21.9 → 冻结 24.9 → 编译 26.4ms, 全部花在 aabbs+
   collide_pairs (占 L 的 78-83%)。
2. **"1.38× 结构性差距"推翻**: 逐阶段编译/冻结倍率全部在 0.71-1.14×,
   多数阶段编译版反而更快 (Nuitka C 编译的 numpy 调用层比 CPython 解释
   快)。bench 同口径 1.38× 差距 = bench 路径 logic 段占比不同的口径假象。
3. **3.5× 悬案 (16.4 vs 58.3) 定案 = aabbs 一个点**: 冻结版旧账 aabbs
   全量 26-37ms (行级缓存修复前) vs numba 3.4ms — 逻辑帧每秒 30 次 ×
   差值 ~25ms = 每秒墙钟多吞 750ms = FPS 直接腰斩式下坠。09-06 晚行级
   缓存修复后账目已大幅收窄 (上表 555 vs 487, 仅 1.14×)。
4. **numpy 本身在编译环境不慢** (微基准: 微型 Nuitka exe vs py 直跑,
   matmul/ufunc/any/alloc/reduction 全部 ±10% 内, aabbs_kernel 18.2 vs
   18.5ms 持平) — "Nuitka 编译 numpy 变慢"假设正式排除。

## 五、剩余堵点排序 (C 内核后, 按账面收益)
1. **collide_pairs ~126ms/s** (编译/冻结/原生三方同价 ~0.98×): SAP 已
   numpy 化, 剩 Python 调用层; C 化 pair 过滤可再省 ~4ms/逻辑帧。
2. **pipe_wait ~264ms/s**: 逻辑帧流水线等待 (管线结构固有, 慎动)。
3. **R 项 ~7-12ms/渲染帧**: shadow_prep 族+buckets+interp; 编译版与
   原生同价, 深挖收益 <10FPS, 优先级最低。
4. 编辑态 143 vs 167: 编辑态无 logic_step, 差距主因 = 渲染侧散段
   (各阶段编译版多数更快, 差异在未插桩段/Qt 合成, 收益有限)。
