====================================================================
Loom 开发进度与 Unity 差距对照 (2026-08-11 起稿, 更新至 2026-08-28, 原名 3D引擎)
====================================================================
用途: 一眼看清"这个引擎现在做到哪、离 Unity 还差什么、差多少"。
对照方式: 按"功能模块"一行一行比, 标注 差距等级:
    ✅ = 已有且可用(核心可用, 够用级)   🟡 = 部分/简化/够用但远不如
    ❌ = 没有
先看结论, 再看表。

====================================================================
〇、一句话定位
====================================================================
这是一个 **Python 写的小型 Unity 式引擎编辑器**:
  - 技术栈: Python 3.12.10 + PySide6 编辑器 UI (默认 Qt 原生视图 ui/loom_gui.py)
    + moderngl/OpenGL 渲染 + 控制器命令层 (pygame 自研即时模式 GUI 已弃用仅参考)
  - 规模: 代码全部自研, 一个开发者完全可控、可读
  - 目标: 小游戏 / 玩法原型 / 可视化教育 / 参数化创作
  - 命名 (2026-08-11): 解释器 = **Loom**, 项目管理器 = **LoomHub**
    (LoomHub 是 Unity Hub 角色: 项目管理 + 项目启动 + 解释器多版本选择/安装)
  - 目录分离 (解释器 / 项目管理器 解耦):
      D:\my-project\Loom(py源代码-工作区)\Loom\     ← Loom 解释器 (引擎编辑器全部源码)
      D:\my-project\Loom(py源代码-工作区)\LoomHub\  ← LoomHub 项目管理器
      文档 *.txt 留项目根 (位置不变); 编译版本已删 (2026-08-31, 等指令重打)
  - 现状: **创作闭环 [布置→行为→试玩→打包] 四环齐全, M1~M41 全落地,
          + LoomHub 项目管理器 + 插件系统 L1 分级 (2026-08-27)
          + EAI/HUB-EAI 命令自动化 (52/16 条命令, 测试全绿), 详见第八节**

和 Unity 的关系: 不是"竞争", 是"按 Unity 的模块设计逐项补齐"。
本引擎能做出"能玩、能发布"的东西(见《使用操作指南.txt》), 但它不是要替代
Unity —— 它证明"Unity 的架构哲学用几百 KB 的 Python 也能搭起来"。

一、已实现全景 (模块一览)
====================================================================
  [场景组织]   场景树(Transform 层次, 防环)、单场景 JSON 序列化(v10)、
               Prefab 模板、组件化 GameObject+Component (M25)
  [编辑工具]   层级面板 / 检查器 / 资源浏览器面板 / 播放模式 /
               平移+旋转 gizmo / 轨道相机 / 全量撤销重做(命令模式 100 步) /
               底部命令行坞 (F12/状态栏[命令行], 输入即命令, 同远程 Agent 命令表)
  [渲染]       moderngl 真 GPU, Blinn-Phong 光照 + 半球环境光 +
               菲涅尔边缘光 + gamma + 非等比缩放逆转置法线 (M20)
  [光照]       光源实体(平行光/点光源, ≤8 个), 无默认光源需手动加光 (M21)
  [材质]       材质资产化(颜色/饱和度, 共享引用, 按 guid 复用) (M23)
  [资源]       资源浏览器(列资产/点选预览/拖到场景/存网格存材质为资产) (M24)
  [行为]       Python 脚本系统(类 MonoBehaviour, 11 个内置脚本, 坏脚本容错) (M27)
  [试玩]       编辑/播放模式, 播放期快照-还原, 编辑操作被拦截 (M26)
  [物理]       AABB/球体碰撞 + 碰撞体组件 + 子步防穿透 + 重力/弹跳脚本 (M28)
  [项目管理]   LoomHub: 项目列表/新建/导入/打开(默认解释器 --open)/移除;
               项目 = 场景文件 (2026-08-12 起: 新建=系统另存对话框建场景文件);
               解释器多版本管理: 扫描 C:\Program Files\Loom\<版本> / 导入目录 /
               .zip 安装(可自定义安装根) / 远程下载接口(预留) (2026-08-11)
  [UI 模块化]  编辑器 UI 彻底独立可更换 (2026-08-13): 接口契约
              IHubView/IEditorView + 控制器命令层 + 独立 UI 视图
              (默认: 编辑器 Qt 原生视图 ui/loom_gui.py (PySide6) +
               LoomHub tkinter TkHubView; pygame 版 LoomGUI/LoomHubGUI
               因 SDL 污染 IME 已弃用仅留参考); 换 UI 只换实现类,
               业务/引擎零改动; 播放器 HUD (RuntimeUI) 不分离
  [发布]       Nuitka standalone exe (Windows 单文件部署, 可拷给别人) +
               游戏封装 build_game.py (M38: 纯玩家 exe + .lsc 加密包;
               2026-08-27 起 --protection secure|open + --no-encrypt-content)

四、已经比 Unity 顺手的地方 (不吹不黑)
====================================================================
  1. 迭代速度: 改脚本 → 按播放 → 看到效果, 零编译等待。
     Unity 改 C# 至少等编译回编译, Python 是"编辑器即解释器"。
  2. 撤销能力: 全量命令模式 100 步, 改位置/材质/挂脚本/开碰撞都能 Ctrl+Z。
     Unity 默认撤销只覆盖有限编辑操作。
  3. 可读性: 整个引擎是你自己能读懂、能改的代码; Unity 是黑盒 + 许可。
  4. 轻量: 启动快、体积小、无账号/许可证/联网, 一个人可控全部逻辑。
  5. 学习价值: 引擎内部(渲染/撤销/序列化/脚本调度)全部透明可见,
     天然是"学游戏引擎架构"的教材 —— 这是 Unity 给不了的。

====================================================================
五、差距小结: 哪些真差距, 哪些对定位无关紧要
====================================================================
【无关紧要的差距】(对本引擎的定位"小游戏/原型/教育", 不是短板)
  - 性能/ECS: 几百物体不需要 DOTS; 到几万同质实体才该考虑。
  - 多平台: 发布 Windows exe 就够"给朋友看/自己用"。
  - 烘焙 GI/后处理/体积光: 教育演示用不上, 反而加重阅读负担。
  - 多场景/加性加载: 单场景原型是常态。
  - 版本控制集成: 目录即工程, 手动备份即可。

【真正限制创作深度的差距】(想做更复杂的东西, 按优先级排)
  —— 原第 1-6 项 (动画/运行时UI/音频/模型导入/刚体/输入) 已在 M30b~M39
     全部补齐 (见第七节), 现在剩余的:
  1. ❌ 纹理贴图 —— 只有顶点色+饱和度, 材质表现有限
  2. ❌ 粒子系统 —— 特效/拖尾无从下手
  3. ❌ 后处理 + 天空盒 —— gamma 是唯一固定后段, 默认清屏色
  4. ❌ 手柄/触屏 —— 输入动作层只有键鼠
  5. 🟡 fbx/骨骼模型 —— obj 导入已通 (M36), 无骨骼/蒙皮
